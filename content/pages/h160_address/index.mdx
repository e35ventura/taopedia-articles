# H160 Address

An H160 address is the Ethereum-style address format used by EVM wallets in the Bittensor EVM
runtime. The official [Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)
documentation distinguishes Bittensor wallets, which use Polkadot-style SS58 addresses, from
Ethereum wallets, which use H160 addresses.

In Taopedia terms, the key idea is address-space separation. Bittensor EVM smart contracts execute
on the Bittensor blockchain, but they use Ethereum-compatible account conventions for EVM activity.
That makes an H160 address relevant to the EVM runtime layer, while SS58 addresses remain the
native-facing Bittensor wallet representation.

## Address-Space Boundary

The Bittensor EVM overview says a full Ethereum Virtual Machine runtime operates as an application
layer on top of Subtensor. It also emphasizes that Bittensor EVM smart contracts execute on the
Bittensor blockchain, not on the Ethereum blockchain. The H160 address therefore belongs to an
Ethereum-compatible runtime running inside the Bittensor chain context.

This boundary prevents a common misunderstanding. Seeing an Ethereum-style address in a Bittensor
EVM workflow does not mean the account is acting on Ethereum mainnet. It means the EVM layer uses an
address model compatible with Ethereum tooling while the execution and balances live in the
Bittensor chain environment.

Reference: [Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)

## Relationship to SS58

SS58 is the public-facing Bittensor address format associated with native wallet addresses.
Bittensor's EVM documentation contrasts those SS58-style Bittensor wallets with H160-style EVM
wallets. The two formats can be related for address targeting, but they are not the same wallet
authority.

The official conversion tutorial explains that users can convert an H160 address to SS58, or the
reverse direction, but that conversion does not yield the corresponding private key. This is the
critical reader-facing distinction: converting an address representation is not the same thing as
gaining signing control over the other address family.

References: [Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials),
[Convert Ethereum H160 Address to Substrate SS58](https://docs.learnbittensor.org/evm-tutorials/convert-h160-to-ss58)

## Wallet Authority

The official EVM overview says an Ethereum wallet controls the private key for the corresponding
H160 public account, while a Bittensor wallet controls the key material for Bittensor transactions.
That means wallet authority follows the key family that created and signs for the account.

An H160 address can identify an EVM wallet, but it should not be treated as proof that the same user
can sign native Bittensor extrinsics with a matching SS58 address. Likewise, a Bittensor coldkey or
hotkey does not automatically become an EVM-signing wallet just because an address conversion can
produce a related representation.

Reference: [Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)

## EVM Wallet Role

The Bittensor EVM overview distinguishes EVM wallets from Bittensor wallets by what they can sign.
EVM wallets are created through EVM clients and can sign EVM smart-contract interactions on the
Bittensor blockchain. Bittensor wallets are created through the Bittensor toolchain and sign
Subtensor-facing transactions through Bittensor clients.

For readers, an H160 address should therefore be read as an EVM account identifier. It is the form
of address expected by Ethereum-style tools and smart-contract workflows, not the native coldkey or
hotkey identity used for mining, validation, staking management, and other Subtensor extrinsics.

Reference: [Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)

## Transfer Targeting Context

The H160-to-SS58 conversion tutorial demonstrates why conversion exists: it helps bridge the
address-format boundary when moving across EVM wallet and Subtensor wallet contexts on the same
Bittensor blockchain. In plain terms, conversion can help identify the SS58-side destination
associated with an EVM address for supported transfer workflows.

That should be read narrowly. Address conversion helps target the right representation; it does not
transfer a private key, merge wallet identities, or make every tool able to sign every kind of
transaction. A transfer-oriented use of a converted address is still separate from the signing
authority needed to spend from either account family.

Reference:
[Convert Ethereum H160 Address to Substrate SS58](https://docs.learnbittensor.org/evm-tutorials/convert-h160-to-ss58)

## Runtime Context

Bittensor EVM exists so users can deploy and interact with EVM smart contracts on Subtensor and
access standard Ethereum JSON-RPC methods. H160 addresses are part of that compatibility layer. They
let Ethereum-style tooling refer to accounts in a format those tools already expect.

The runtime context matters because Bittensor still has native wallet and subnet concepts outside
the EVM layer. H160 address vocabulary belongs to smart-contract account interaction. Native
Bittensor concepts such as coldkeys, hotkeys, validator roles, and subnet operations should not be
collapsed into the H160 term.

Reference: [Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)

## Relationship to Smart Contracts

An H160 address appears naturally in smart-contract workflows because EVM contracts and EVM wallets
use Ethereum-compatible addressing. The Bittensor EVM overview says the runtime lets users deploy
most EVM smart contracts on Subtensor without changing the code and interact with deployed smart
contracts on the Subtensor blockchain.

That makes H160 an account-address concept, not a contract feature by itself. It identifies an EVM
account in the smart-contract environment. Contract behavior, precompile behavior, gas, and network
configuration are separate topics.

Reference: [Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)

## Reader Boundary

An H160 address should not be read as a native Bittensor coldkey, a native hotkey, an SS58 address,
or a guarantee of private-key control after conversion. It is the Ethereum-style account address
used by the Bittensor EVM runtime.

When a workflow crosses between H160 and SS58 representations, readers should track which address is
being used for display, which account family can sign, and which chain layer the operation targets.
This prevents address conversion from being mistaken for wallet recovery, identity merging, or
authority transfer.
