# Weight Setting

Weight setting is the validator process of assigning numerical scores to miners in a Bittensor
subnet. Validators observe miner work and submit weights that reflect how well each miner performed
the subnet task ([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Subnet Metagraph](https://docs.learnbittensor.org/subnets/metagraph)).

## What It Represents

Weight setting names the on-chain `set_weights` action through which a validator records miner
scores for an epoch. It is process vocabulary for the evaluation side of subnet consensus. It does
not name the emission outcome or the miner incentive that follows from consensus
([Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch)).

The fee documentation lists `set_weights`, `commit_weights`, and `reveal_weights` as fee-free
extrinsics for the base transaction fee. That means the weight-setting path is still an on-chain
submission, but it is documented separately from ordinary state-changing actions that pay
weight-and-length transaction fees
([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees),
[Commit Reveal](https://docs.learnbittensor.org/concepts/commit-reveal)).

Readers should separate evaluation vocabulary from settlement vocabulary:

- **Weight setting** — validator action that submits miner scores on chain.
- **Weight vector** — structured payload inside one submission.
- **Weight matrix** — assembled collection of validator rows before settlement runs.
- **Subnet task** — work miners return inside the subnet.
- **Subnet protocol** — exchange rules for requesting and returning that work.
- **Subnet scoring model** — subnet-defined method for judging returned work.
- **Off-chain validation systems** — subnet-side evaluation layer before chain-facing signals.
- **Dividends** — validator-side emission outcomes after settlement.
- **Stake weight** — influence measure applied when recorded weights are aggregated.

[Subjective evaluation](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism) is why
multiple validators may score the same returned work differently. Weight setting is each validator's
own submission act; consensus aggregates those submissions rather than replacing them
([Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix)).

[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus) reads the weight matrix,
applies clipping and bonding, and credits miner incentives and validator dividends when the epoch
closes. Hyperparameters such as
[validator permit](https://docs.learnbittensor.org/resources/glossary#validator-permit),
[activity cutoff](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutoff),
[commit reveal](https://docs.learnbittensor.org/concepts/commit-reveal),
[min allowed weights](https://docs.learnbittensor.org/subnets/subnet-hyperparameters), and
[weights version key](https://docs.learnbittensor.org/subnets/subnet-hyperparameters) gate whether
and how a submission can count; they do not replace the scoring action itself
([Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch)).

Weight setting examples tied to netuid 1 illustrate one subnet's submission path. They should not be
read as representing production consensus behavior on another network
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

A submission also has to satisfy several subnet rules before it is accepted. The validator needs a
validator permit, the vector must include at least the minimum allowed weights, the call must
respect the weights rate limit since the validator's last update, and its declared version must meet
the subnet's weights version key
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit)).

## Distinction from Subnet Protocol

## Distinction from Weight Matrix

- **Weight setting** — per-validator submission act.
- **Weight matrix** — grouped consensus input built from many submissions.

## Distinction from Activity Cutoff

Weight setting is the validator action that records miner evaluation scores on chain. Activity
cutoff vocabulary names how long a validator may remain without an on-chain update before its stake
is masked inactive for consensus—not an early-epoch submission deadline
([Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch),
[Subnet Hyperparameters: Activity Cutoff](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutoff),
[Subnet Hyperparameters: Activity Cutoff Factor](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutofffactor),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

On dynamic-tempo subnets the fixed block hyperparameter is deprecated; the live inactivity span
comes from activity cutoff factor and tempo instead
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

Action vocabulary and inactivity-mask vocabulary answer different participation questions on the
same weight path. A validator can submit a fresh weight vector yet still be masked inactive when
last update exceeds the effective span, and a recent last update does not replace permit, pacing, or
structural validity rules elsewhere on the path
([Subnet Metagraph](https://docs.learnbittensor.org/subnets/metagraph),
[Implementation of the Yuma Consensus Epoch: Network State Collection](https://docs.learnbittensor.org/navigating-subtensor/epoch#1-network-state-collection)).

- **Weight setting** — the on-chain act that records miner evaluation scores.
- **Activity cutoff** — inactivity span before a stale validator is masked out of consensus.

## Distinction from Validator Permit

- **Validator permit** — authorization to submit weights that can count.
- **Weight setting** — evaluation act a permitted validator performs.

## Distinction from Commit Reveal

- **Commit reveal** — staged visibility for weight submissions.
- **Weight setting** — scoring action that produces a weight vector.

## Distinction from Min Allowed Weights

- **Min allowed weights** — structural minimum on submission shape.
- **Weight setting** — action that must satisfy that minimum.

## Distinction from Weights Rate Limit

Weight setting and weights rate limit govern different parts of the same validator submission path.
Weight setting is the scoring action that records miner evaluation through `set_weights`, while
weights rate limit sets how many blocks must pass between successive weight commits on a subnet
([Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

The rate limit paces how frequently a validator can change its on-chain weight signal. It does not
say how miners should be scored or how many targets a valid submission must include; those belong to
the subnet scoring model and min allowed weights. A validator can be permitted and structurally
valid yet still blocked from committing again until the required gap elapses
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit)).

Because the wait is counted in blocks while a subnet's consensus cycle length is its tempo, the
relationship between rate limit and tempo decides whether a validator can refresh its weights every
epoch. When the minimum wait is shorter than the tempo, a validator can commit new weights within
each cycle; when the wait is longer than the tempo, some epochs may pass without a fresh commit and
Yuma reads the validator's most recent stored weights instead
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Glossary: Tempo](https://docs.learnbittensor.org/resources/glossary#tempo),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

Readers should treat weight setting as the evaluation act and weights rate limit as the submission
pacing rule that bounds how often that act can be repeated
([Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch)).

- **Weight setting** — the on-chain act that records miner scores.
- **Weights rate limit** — blocks a validator must wait before the next weight commit.

## Distinction from Off-Chain Validation Systems

- **Off-chain validation systems** — subnet-side evaluation layer before chain-facing signals.
- **Weight setting** — on-chain submission that records those results.

## Distinction from Dividends

- **Weight setting** — action that records miner scores on chain.
- **Dividends** — validator-side outcome those scores help produce at epoch settlement.

## Distinction from Stake Weight

- **Weight setting** — action that records miner scores.
- **Stake weight** — influence measure applied during aggregation.

## Distinction from Yuma Consensus

- **Weight setting** — validator action that records evaluation scores on chain.
- **Yuma Consensus** — on-chain mechanism that uses validator weights to determine emission shares.

## Reader Boundary

Weight setting is concept vocabulary for the validator evaluation process in Bittensor subnets. The
term should not be read as a miner ranking table, a staking guide, an emission forecast, or as the
activity cutoff rule that masks stale validator stake. Activity cutoff names inactivity tolerance
measured from last update—not an early-epoch submission window—for whether a validator's stake still
counts in the pass ([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Subnet Hyperparameters: Activity Cutoff](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutoff)).
