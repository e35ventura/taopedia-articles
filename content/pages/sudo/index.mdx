# Sudo

Sudo is the Bittensor glossary term for privileged administrative authority. The
[Glossary](https://docs.learnbittensor.org/resources/glossary#sudo) describes it as a privileged key
for administrative actions that has been replaced by the governance protocol for enhanced security.

## Governance Context

The [Governance Overview](https://docs.learnbittensor.org/governance) explains that Bittensor
governance moves network management away from centralized control over time. In that model, the
Triumvirate creates proposals and the Senate reviews them, replacing single-authority administration
with proposal review.

## Security Transition

Before Bittensor governance, administrative actions required permission through a single privileged
sudo key. The [Governance Overview](https://docs.learnbittensor.org/governance#security) explains
that governance replaced that single-key model so approving privileged changes now requires both
Senate majority support and Triumvirate closure of a proposal.

## How Governance Replaced Single-Key Administration

Before Bittensor governance, privileged network changes could depend on a single administrative sudo
key. Hyperparameter updates, subnet creation, chain upgrades, and other high-impact configuration
could be authorized through that one privileged path rather than through a public review sequence.
The [Governance Overview](https://docs.learnbittensor.org/governance) and
[Glossary: Sudo](https://docs.learnbittensor.org/resources/glossary#sudo) describe that older model
as centralized administrative authority that governance is designed to replace over time.

The replacement process is proposal-based rather than instant. The Triumvirate creates a proposal
containing privileged call data. The Senate — stake-based delegates who review Triumvirate proposals
— votes to approve or reject it. If the Senate approves, a Triumvirate member still must close the
proposal before its call data executes. Successfully closed proposal call data then runs on
Subtensor, Bittensor's layer 1 blockchain, in the same block as the close action described in the
official governance documentation.

That sequence is why bicameral legislature vocabulary matters in the same article family as sudo.
The Triumvirate originates proposals; the Senate is the approval gate; neither step alone completes
execution. Senators use the proposal hash to vote on the correct item, while anyone can inspect
proposals currently before the Senate without special permissions. Voting authority and public
visibility therefore sit on different layers: seeing a proposal is not the same as approving it, and
Senate approval is not the same as final execution before close.

Sudo names the legacy single-key pattern, not the current review path for privileged changes in that
documented flow. It should not be read as identifying a live sudo holder, exposing key material, or
describing how privileged changes are approved today. When reading governance vocabulary together,
the useful mental model is sequential: sudo names what single-key administration used to mean;
Triumvirate and Senate name the two sides of review; a proposal carries the privileged change;
Subtensor is the chain layer where an approved and closed proposal may finally execute.

Taopedia articles should explain that sequence in plain prose rather than repeating the same
contrast six times across separate boilerplate sections. The point for readers is security and
review structure: privileged changes moved from one-key execution to a public proposal path with
Senate majority support and Triumvirate closure before on-chain execution.

The governance overview also frames why that shift matters for network participants. Privileged
changes can affect subnet creation, runtime parameters, chain upgrades, and other configuration that
shapes how Bittensor operates. Moving those changes behind proposal review raises the threshold for
execution and makes the approval path inspectable rather than dependent on one hidden administrative
action. Sudo vocabulary remains useful because it names the older threshold readers may still
encounter in historical docs or comparisons, not because it describes the normal approval path for
new privileged changes today. This article keeps that historical boundary explicit so sudo is not
mistaken for a live approval role in current governance flow. Operational proposal records and
Senate participation requirements belong in official governance references rather than in this
concept article.
