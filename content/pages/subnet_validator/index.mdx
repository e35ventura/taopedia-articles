# Subnet Validator

A subnet validator is the evaluation role inside a Bittensor subnet. Validators measure miner work
and set weights based on miner output
([Glossary: Subnet Validator](https://docs.learnbittensor.org/resources/glossary#subnet-validator),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

The term belongs to subnet incentive vocabulary. It names the role that evaluates work, not the
miner role and not the weight signal by itself.

Validator weight signals are an input to the Yuma Consensus process. The consensus documentation
describes how those signals are aggregated into miner incentives and validator dividends, making
evaluation the measurement step that connects task execution to emission allocation
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Emission](https://docs.learnbittensor.org/learn/emissions)).

## Role in a Subnet

Subnet validators operate relative to the standards of the subnet they serve. Different subnets can
pursue different goals, so useful evaluation depends on the subnet's task and incentive design
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets),
[Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism)).

This keeps validator vocabulary scoped to the subnet's definition of useful miner output. A
validator is not evaluating one universal task across every subnet.

For readers, validator language should carry the subnet context it belongs to. An evaluation
standard on one subnet does not transfer to another subnet with a different task. The subnet's
incentive mechanism defines what validators should measure; the validator role names who does the
measuring
([Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism)).

## Weight Signal Role

The glossary defines subnet validators around evaluating miner performance and setting weights from
miner output. Those weights then feed the subnet consensus process
([Glossary: Subnet Validator](https://docs.learnbittensor.org/resources/glossary#subnet-validator),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

Weights are therefore evaluation signals, not the miner work itself. The subnet validator is the
role that produces those signals after measuring miner output against subnet standards.

For readers, a weight signal names one validator's measurement of one miner; it does not describe
the miner's final emission outcome. The emission path follows from how all validator signals are
aggregated through the consensus process for that subnet epoch. Weight and emission are distinct:
weight is the evaluation input, emission is the distribution output
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Emission](https://docs.learnbittensor.org/learn/emissions)).

## Evaluation and Emission Path

The path from miner work to emission runs through validator evaluation. Validators measure miner
output and set weight signals; those signals feed the Yuma Consensus process for the subnet epoch;
the consensus output determines how emissions are allocated across miners and validators
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Emission](https://docs.learnbittensor.org/learn/emissions)).

That path makes validators the measurement layer, not the distribution layer. A validator does not
directly assign emissions; it produces the weight signals that become inputs to the consensus
calculation that determines emission allocation.

For readers, validator language should stay on the measurement side of that path. A claim about
validator evaluation is not automatically a claim about emission amounts or emission timing
([Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism),
[Glossary: Subnet Validator](https://docs.learnbittensor.org/resources/glossary#subnet-validator)).

## Relationship to Miners

Subnet miners and subnet validators form the core work-and-evaluation relationship inside a subnet.
Miners produce work for the subnet, and validators measure that work
([Glossary: Subnet Miner](https://docs.learnbittensor.org/resources/glossary#subnet-miner),
[Glossary: Subnet Validator](https://docs.learnbittensor.org/resources/glossary#subnet-validator)).

For readers, miner names the producing role and subnet validator names the evaluating role. The two
roles are related but not interchangeable.

## Relationship to Root Validator

Subnet validator and root validator share validator vocabulary but operate in different contexts.
The Root Subnet has no miner work to evaluate, while a subnet validator evaluates miner work inside
an ordinary subnet
([Glossary: Root Subnet/Subnet Zero](https://docs.learnbittensor.org/resources/glossary#root-subnetsubnet-zero),
[Glossary: Subnet Validator](https://docs.learnbittensor.org/resources/glossary#subnet-validator)).

This distinction matters when comparing staking and validation terms. Root validator belongs to the
root staking path; subnet validator belongs to the miner-evaluation path inside a subnet.

## Incentive Mechanism Scope

Validator evaluation is part of the subnet's incentive mechanism. The task defines what work is
requested, the protocol shapes miner-validator interaction, and the evaluation method gives
validators a way to judge results
([Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

When a subnet uses multiple mechanisms, validators evaluate miners separately for each mechanism.
That means the mechanism context should stay attached to any claim about validator work.

For readers, the incentive mechanism describes the full path from task through evaluation to
emission. Validator evaluation is the measurement step; the mechanism explains why particular miner
behaviors lead to higher or lower weights. A validator claim should identify which mechanism is in
scope when the subnet runs more than one evaluation path
([Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism),
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets)).

## Reader Boundary

Subnet validator should be read as a role concept. It is not a procedure, a validator list, a
ranking report, or a claim about a specific validator's performance
([Glossary: Subnet Validator](https://docs.learnbittensor.org/resources/glossary#subnet-validator),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

The stable article-level point is that a subnet validator evaluates miner work inside a Bittensor
subnet and expresses that evaluation as weights for the subnet consensus path.

That boundary also applies when comparing validators across subnets. A validator on one subnet
operates under the task and incentive design of that subnet; comparing it to a validator on another
subnet requires identifying both subnets' task definitions and evaluation methods. The stable
concept is the role itself, not any specific validator's performance or any specific subnet's
evaluation standard
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets),
[Glossary: Subnet Validator](https://docs.learnbittensor.org/resources/glossary#subnet-validator)).

## Development Stage Context

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. The subnet
validator role applies across the Bittensor lifecycle: validators can evaluate miner work in
localnet for isolated development, testnet for shared non-production testing, and mainnet for live
operation with real emissions.

The [Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet. Validator evaluation examples or weight outcomes from one
environment should not be read as representing production subnet performance in another environment.
