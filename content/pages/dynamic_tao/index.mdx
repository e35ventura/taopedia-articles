# Dynamic TAO (dTAO)

Dynamic TAO, often shortened to dTAO, is Bittensor's subnet-aware tokenomics system. It connects
network-level TAO with subnet-specific alpha tokens, subnet liquidity pools, emission routing, and
validator stake weight
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

The main shift is that subnet economics are not described only through network-wide TAO. Each subnet
has an alpha side as well as a TAO side, so staking, liquidity, and emission language needs
subnet-specific context.

## Subnet Alpha Model

Dynamic TAO gives each subnet its own alpha token. Subnet pools include TAO reserves, alpha
reserves, and alpha outstanding
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets),
[Glossary: Alpha Tokens](https://docs.learnbittensor.org/resources/glossary#alpha-tokens)).

That creates a two-asset subnet model. TAO remains the network asset, while alpha names the
subnet-specific asset used in that subnet's pool, stake, and reward context.

## Reserve and Outstanding Alpha

The alpha side is split by location. Alpha reserve is the subnet alpha inside the liquidity pool,
paired with the subnet's TAO reserve. Alpha outstanding is alpha outside that reserve side and is
connected to subnet stake and rewards ([Emissions](https://docs.learnbittensor.org/learn/emissions),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

This makes Dynamic TAO easier to read. A pool statement usually concerns TAO reserve and alpha
reserve, while a reward or stake statement usually concerns alpha outstanding.

## Emission Routing

Emissions move through subnet-specific paths. TAO can enter subnet reserve paths, alpha can enter
the reserve side, and alpha outstanding can be set aside for subnet rewards
([Emissions](https://docs.learnbittensor.org/learn/emissions),
[Emission: Distribution Across Subnets](https://docs.learnbittensor.org/learn/emissions#distribution-across-subnets)).

Dynamic TAO therefore links emission to subnet liquidity. Emission is not only a network supply
event; it also changes the TAO-and-alpha structure each subnet uses.

## Validator Stake Weight

Validator stake weight is one place where Dynamic TAO combines TAO and alpha. Bittensor defines a
validator's subnet stake weight as alpha stake plus TAO stake scaled by the subnet's TAO weight
parameter
([Understanding Subnets: Validator stake weight](https://docs.learnbittensor.org/subnets/understanding-subnets#validator-stake-weight)).

In plain terms, subnet alpha stake and TAO stake can both contribute to validator influence inside a
subnet. The TAO side is scaled, so the two assets are related without being identical.

## Cross-Subnet Allocation

Dynamic TAO also affects how emissions are compared across subnets. Flow-based emission logic uses
subnet demand signals when allocating TAO reserve injection across subnets
([Emission: Distribution Across Subnets](https://docs.learnbittensor.org/learn/emissions#distribution-across-subnets),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

This connects TAO flows, subnet alpha, and subnet weights. Dynamic TAO is the system in which those
pieces interact rather than a separate asset by itself.

## Pool Interaction Boundary

Dynamic TAO pool language should be separated from the result of a specific staking or unstaking
action. The pool model explains how TAO reserve and alpha reserve relate, while slippage explains
why a conversion can receive a different amount after interacting with that pool
([Understanding Slippage](https://docs.learnbittensor.org/learn/slippage)).

Price protection is the related guardrail for adverse price movement during staking-related
activity. It does not replace Dynamic TAO's reserve model; it describes how an action responds when
pool movement crosses the selected tolerance
([Price Protection](https://docs.learnbittensor.org/learn/price-protection)).

## Yuma Consensus Boundary

Dynamic TAO and Yuma Consensus describe different layers. Dynamic TAO describes TAO-and-alpha
tokenomics across subnets, while Yuma Consensus describes how validator signals combine inside a
subnet to determine reward outcomes
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Emissions](https://docs.learnbittensor.org/learn/emissions)).

The two are connected through emissions. Dynamic TAO provides the subnet tokenomics environment;
Yuma Consensus resolves within-subnet reward allocation.

## Development Stage Context

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. For Dynamic TAO,
that sequence changes how readers should interpret pool examples, subnet-reserve observations, and
slippage comparisons.

In localnet, Dynamic TAO examples can be exercised in an isolated environment. Localnet observations
reflect local chain state and local configuration rather than production Bittensor behavior.

On testnet, Dynamic TAO behavior can be observed in a shared, non-production network. Testnet
examples are useful for checking interactions under shared chain conditions while staying separate
from mainnet state.

On mainnet, Dynamic TAO describes live production Dynamic TAO behavior on the production Bittensor
network.

The [Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet. An example or outcome from one environment should not be
read as evidence of production behavior in another environment.

## Tokenomics Scope

Dynamic TAO describes the subnet tokenomics model around TAO reserves, alpha reserves, and
subnet-specific alpha assets. It should not be treated as a trading strategy or a promise about a
particular conversion result
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets),
[Understanding Slippage](https://docs.learnbittensor.org/learn/slippage)).

For readers, the stable concept is the reserve-based mechanism. Specific observed prices, slippage,
and pool state belong to the network and block context where they are queried.

## Root Subnet Keeps TAO-Denominated Stake

The [Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)
documentation describes the
[Root Subnet](https://docs.learnbittensor.org/resources/glossary#root-subnetsubnet-zero), also
called Subnet Zero, as the only subnet without its own alpha currency. No miners can register there,
and no validation work is performed on that market path.

Validators can still register on the Root Subnet, and
[TAO](https://docs.learnbittensor.org/resources/glossary#tao) holders can stake to them as they
would on any other subnet. That creates a subnet-agnostic staking route where support remains
expressed in network TAO rather than in a subnet-specific
[alpha token](https://docs.learnbittensor.org/resources/glossary#alpha-tokens).

Dynamic TAO therefore needs a clear exception at subnet zero. On alpha subnets, stake held by a
hotkey is tracked in that subnet's alpha units. On the Root Subnet, the same staking vocabulary
stays on the TAO side only
([Staking and delegation overview](https://docs.learnbittensor.org/staking-and-delegation/delegation)).

That exception also changes which pool pieces apply. Alpha subnets pair TAO reserve with alpha
reserve inside an
[automated market maker (AMM)](https://docs.learnbittensor.org/resources/glossary#automated-market-maker-amm).
Root does not introduce a second subnet token side, so reserve-ratio and alpha-price language from
alpha markets does not transfer directly to subnet zero reading.

References: [Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets),
[Glossary: Root Subnet/Subnet Zero](https://docs.learnbittensor.org/resources/glossary#root-subnetsubnet-zero)

## Staking Positions Stay Subnet-Local

Official [staking and delegation](https://docs.learnbittensor.org/staking-and-delegation/delegation)
guidance states that staking is always local to a subnet. Each subnet operates its own AMM with
paired TAO and alpha reserves, so a stake action belongs to the selected
[netuid](https://docs.learnbittensor.org/resources/glossary#netuid) rather than to the network as
one undivided balance.

That locality also applies to validator choice. Staking to the same validator's hotkey on one subnet
does not move or merge stake on another subnet; those positions remain independent even when the
validator identity looks the same across markets.

When TAO is staked on an alpha subnet, the documentation describes a reserve-side sequence rather
than a direct balance rename. The TAO enters that subnet's TAO reserve, the pool applies the current
exchange rate, and the matching alpha amount is drawn from alpha reserve and credited to the
validator hotkey as subnet stake. Unstaking reverses that path by returning alpha to reserve before
TAO is sent back to the holder's
[coldkey](https://docs.learnbittensor.org/resources/glossary#coldkey).

The sum of alpha held across hotkeys on that subnet is the subnet's alpha outstanding reading.
Dynamic TAO therefore treats each subnet market as carrying its own stake ledger even when the same
participant appears in several places.

References:
[Staking and delegation overview](https://docs.learnbittensor.org/staking-and-delegation/delegation),
[Glossary: Staking](https://docs.learnbittensor.org/resources/glossary#staking)

## Alpha Reserve Injection Preserves Pool Price

The [Emissions](https://docs.learnbittensor.org/learn/emissions) documentation separates block-level
injection from later reward distribution. During the injection stage, new TAO can enter a subnet's
TAO reserve based on that subnet's emission share, and new alpha can enter the paired alpha reserve
in proportion to that TAO injection so pool price stays stable
([Emission: Alpha reserve injection](https://docs.learnbittensor.org/learn/emissions#alpha-reserve-injection)).

That proportional alpha reserve injection is a distinct injection path from alpha allocated to alpha
outstanding for participant rewards. TAO reserve injection grows one reserve side according to
cross-subnet allocation, while the matched alpha reserve injection grows the other side by the
amount needed to preserve the existing reserve ratio rather than to pay miners, validators, or
stakers directly.

[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets) ties alpha
price to the ratio of TAO in reserve to alpha in reserve. Keeping those sides growing together
during emission injection therefore protects the pricing context that later staking and unstaking
actions will read, instead of letting reserve growth on only one side rewrite the quote by itself.

Injection still changes subnet liquidity, but the matched reserve growth explains why emission
routing can add tokens to a pool without treating that step as an ordinary user swap.

References:
[Emission: Alpha reserve injection](https://docs.learnbittensor.org/learn/emissions#alpha-reserve-injection),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)
