# Subnet 14: Cacheon

Cacheon is Bittensor Subnet 14 (SN14), operated by latent-to. The subnet runs a live inference
optimization competition: miners submit customized LLM inference servers that are benchmarked
against a pinned baseline, and the fastest correct implementation earns the majority of subnet
emissions. The V1 arena targets `Qwen2.5-72B-Instruct` on identical 8-GPU pods against a pinned vLLM
baseline ([Cacheon repository](https://github.com/latent-to/cacheon),
[cacheon.ai/docs](https://cacheon.ai/docs)).

## How the Mechanism Works

According to the [Cacheon repository](https://github.com/latent-to/cacheon), Cacheon uses a
challenger model with a seated winner. The current leading inference server holds the winner
position and earns the top share of emissions. A new submission must exceed the winner's performance
score by a fixed 1% margin to take the seat, preventing minor fluctuations from causing constant
turnover.

Each submission is evaluated in two stages on identical hardware. The harness first measures median
end-to-end response-time improvement over the pinned vLLM generation baseline—the score uses wall
time to an aligned output-token count, not decode-only throughput, so buffering tricks cannot earn
extra credit ([cacheon.ai/docs/evaluation/scoring](https://cacheon.ai/docs/evaluation/scoring)). A
separate correctness gate then teacher-forces the same outputs on a scoring vLLM; submissions that
fail correctness verification score zero regardless of speed. Only servers that pass the correctness
gate compete on performance.

The winner earns approximately 80% of the competition pool; the runner-up earns the remaining 20%.
Weight vectors from validator scoring feed into
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus), distributing emissions via
Dynamic TAO.

## Participating as a Miner

Miners on Cacheon build and submit optimized inference servers for the target open-source model. The
[Cacheon repository](https://github.com/latent-to/cacheon) describes their economic role as finding
inference optimizations — whether through memory management, batching strategies, or algorithmic
improvements — that make their server measurably faster than the current winner while maintaining
correct output. A miner whose submission passes correctness checks and beats the winner's speed by
the required margin takes the winning seat and begins earning the top emissions share.

The competition is open to any inference approach, and miners compete on the technical merit of
their implementation. A submission that cannot dethrone the current winner still earns the runner-up
share if it ranks second.

## Participating as a Validator

Validators on Cacheon run the evaluation harness that scores each new challenger submission. The
[Cacheon repository](https://github.com/latent-to/cacheon) describes validators pulling each
submission, running it under controlled conditions on standard hardware, and executing both the
speed measurement and the correctness verification pass. Results are compared against the pinned
baseline, and validators submit weight vectors reflecting each submission's relative performance to
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus).

Because evaluations are triggered by new submissions rather than running continuously, validators
operate infrastructure that can scale to run evaluations on demand when challengers arrive.

## Winner Seat Concentrates the Competition Pool

The Cacheon repository describes a seated winner model in which the leading server earns roughly
eighty percent of the competition pool until displaced
([Cacheon repository](https://github.com/latent-to/cacheon)).

The runner-up share compensates second-place performance rather than replacing the seated winner
role.

## Correctness Verification Precedes Speed Ranking

Each challenger submission must pass a teacher-forcing correctness gate on a scoring vLLM before
end-to-end speed metrics count toward the score
([cacheon.ai/docs/evaluation/scoring](https://cacheon.ai/docs/evaluation/scoring)).

A fast but incorrect server therefore scores zero rather than trading accuracy for throughput.

## Distinction from Dynamic TAO

Subnet 14 (Cacheon) is one subnet market inside Bittensor's broader Dynamic TAO context. Dynamic TAO
names the protocol setting where subnet-level alpha and TAO interact across subnet markets; this
article covers optimized LLM inference server competition rather than the full tokenomics model
([Emission](https://docs.learnbittensor.org/learn/emissions),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

- **Subnet 14 (Cacheon)** — subnet market covered in this article.
- **Dynamic TAO** — protocol context for subnet markets, alpha, and TAO interaction.

## Distinction from Yuma Consensus

Cacheon on netuid 14 is an LLM inference optimization subnet where miners submit customized
inference servers and validators benchmark speed against a seated winner after a correctness gate.
That inference-competition vocabulary names how Cacheon measures server performance on netuid 14,
not the on-chain step that turns validator weight submissions into emission shares each tempo
([Cacheon repository](https://github.com/latent-to/cacheon),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

Yuma Consensus is the on-chain mechanism that runs at the epoch boundary on the selected netuid. It
reads the weight matrix from eligible validators, applies clipping and bonding, and converts the
result into miner incentives and validator dividend shares
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Emission](https://docs.learnbittensor.org/learn/emissions)).

Earlier sections separate median end-to-end wall-time speedup from teacher-forcing correctness
verification. A challenger must beat the seated winner by a fixed 1% margin on identical hardware
before taking the top emission share. Yuma aggregates the weight signals that flow from that
two-stage evaluation rather than running inference servers itself
([Cacheon README](https://raw.githubusercontent.com/latent-to/cacheon/main/README.md),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

Winner-stays-in optimization rewards therefore sit upstream of settlement. Yuma still credits
emissions from included validator weights on netuid 14 once the tempo closes
([Cacheon repository](https://github.com/latent-to/cacheon),
[Emission](https://docs.learnbittensor.org/learn/emissions)).

Readers should treat Cacheon as the LLM inference optimization protocol on netuid 14, and Yuma
Consensus as the recurring mechanism that allocates rewards from validator weights each tempo.

- **Subnet 14 (Cacheon)** — seated-winner LLM inference speed competition subnet.
- **Yuma Consensus** — epoch-boundary settlement from validator weights to emission shares on a task
  subnet
  ([Yuma Consensus: Validator emissions](https://docs.learnbittensor.org/learn/yuma-consensus#validator-emissions)).

## Reader Boundary

Subnet 14 Cacheon should not be read as generic Bittensor subnet documentation, a universal
inference hosting service, or proof that one speed score applies to every model size. It names one
subnet's seated inference-optimization competition on netuid 14
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets),
[Glossary: Netuid](https://docs.learnbittensor.org/resources/glossary#netuid)).
