# Bittensor CLI: Permissions Guide

The Bittensor CLI permissions guide explains why different BTCLI actions require different forms of
authority. The official
[Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions) says
some actions require a coldkey private key, some require a hotkey private key, and some require no
private key at all. It also notes that some actions depend on balances, validator permits, subnet
roles, or Senate participation.

This article summarizes that permission model without reproducing the command matrix.

## What It Represents

"Can run BTCLI" is not the same as "can perform every BTCLI action." Authority depends on which key
is present, what role the account has, and whether the action is a read, a signature, or an on-chain
state change
([Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions)).

The model is easiest to read as layers:

- **Permissionless reads** — public chain data without private wallet material.
- **Hotkey authority** — miner and validator operational signing.
- **Coldkey authority** — ownership-sensitive actions such as balances, stake, hotkey management,
  subnet ownership, and some governance actions.

Those layers are about authority, not software installation. The same CLI can run on different
workstations, but a machine with only public keys cannot sign the same actions as one that holds
hotkey or coldkey material
([Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions)).

Readers should also separate three "permission" ideas that sound similar:

- **Signing permission** — whether BTCLI has the private key needed to authorize an extrinsic.
- **Role permission** — whether the account has network status such as a validator permit or Senate
  eligibility.
- **Economic capacity** — whether the wallet holds enough TAO, alpha stake, or burn budget for the
  action.

An action may have the right signer and still fail when the required role or balance condition is
not met
([Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions)).

Permissionless work separates observation from action. If a task only answers what is visible on
chain, it should not require private signing authority
([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)).

Coldkey-required actions affect TAO, alpha stake, subnet ownership, or coldkey-hotkey relationships.
Hotkey-required actions affect operational reputation and subnet behavior without granting custody
authority. A hotkey leak is serious but not equivalent to coldkey compromise; a coldkey should not
be placed on a hotkey workstation simply because both keys appear somewhere in BTCLI
([Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions),
[Coldkey and hotkey workstation security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).

## Config Setup Is Not Signing Authority

The official permissions guide treats configuration setup as separate from signing authority.
Choosing a target network and setting where wallet material is stored does not require a coldkey
private key, a hotkey private key, or any other signing credential
([Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions)).

Those setup actions are meant to run on every BTCLI workstation type because they initialize the
tool rather than authorize on-chain changes. Network selection and wallet storage location belong to
CLI preparation, not to the same layer as transfers, staking, registration, or weight setting
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).

A machine can therefore be correctly configured for BTCLI and still unable to perform signed
actions. Configuration answers where the CLI looks and which chain it targets;
[Coldkey](https://docs.learnbittensor.org/resources/glossary#coldkey) and
[Hotkey](https://docs.learnbittensor.org/resources/glossary#hotkey) authority still determine
whether private signing material is present when a state-changing action is attempted.

## Hotkey Workstations Keep Public Coldkey Context

Official guidance describes a hotkey workstation as carrying two different key materials at once:
the hotkey private key needed for miner or validator signing, and the corresponding coldkey public
key for the wallet that owns that hotkey
([Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions)).

That pairing is not the same as loading a coldkey private key onto an operational server. The
public-side coldkey material links the workstation to the correct wallet identity while operational
signing still flows through the hotkey layer
([Glossary: Hotkey-Coldkey Pair](https://docs.learnbittensor.org/resources/glossary#coldkey-hotkey-pair)).

TAO and alpha stake can move only with coldkey authority, while a leaked hotkey can be replaced
through coldkey-controlled recovery. A hotkey workstation supports subnet operation without granting
custody authority
([Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions)).

## Subnet Creation Burns Are a Moving Economic Gate

Some BTCLI actions fail for economic reasons even when the correct signer is present. Subnet
creation burn cost is dynamic: the price doubles whenever a new subnet is created and then lowers
gradually over time ([Create a Subnet](https://docs.learnbittensor.org/subnets/create-a-subnet),
[Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions)).

That is a different resource question from ordinary transfer balance checks or the
[neuron registration burn](https://docs.learnbittensor.org/resources/glossary#register) paid when a
hotkey registers on an existing subnet. A coldkey with signing authority can still fail subnet
creation if the wallet does not hold enough TAO for the current burn cost at submission time
([Glossary: Burn cost](https://docs.learnbittensor.org/resources/glossary#burn-cost)).

## Public Identifier Scope

A permissionless BTCLI lookup can still name a wallet, hotkey, subnet, or other public identifier.
That identifier helps select public chain data; it is not the same thing as loading private wallet
material for a signed action
([Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions),
[Wallets, Coldkeys and Hotkeys in Bittensor](https://docs.learnbittensor.org/keys/wallets)).

The permission boundary is crossed when BTCLI needs hotkey or coldkey authority, not when a public
identifier is used for inspection.

## Development Stage Context

BTCLI permission examples should be read against the network boundary. Localnet and testnet runs can
exercise CLI workflows without representing production signing requirements on mainnet, where
coldkey authority governs actual TAO transfers, staking, and subnet registration
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks),
[Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions)).

## Distinction from Coldkeys

A coldkey is the security-sensitive key that controls TAO and stake. BTCLI permissions name which
command-line actions require coldkey authority versus hotkey authority or permissionless reads
([Glossary: Coldkey](https://docs.learnbittensor.org/resources/glossary#coldkey),
[Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions)).

- **Coldkey** — security-sensitive key that controls TAO and stake.
- **BTCLI permissions** — which CLI actions require coldkey authority.

## Distinction from Hotkeys

A hotkey is the operational key used for routine on-chain actions. BTCLI permissions name which
command-line actions require hotkey authority for miner and validator activity
([Glossary: Hotkey](https://docs.learnbittensor.org/resources/glossary#hotkey),
[Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions)).

- **Hotkey** — operational key used for routine on-chain actions.
- **BTCLI permissions** — which CLI actions require hotkey authority.

## Distinction from Chain Reads

Chain reads name observation of public chain state without submitting a new action. BTCLI
permissions place permissionless reads in the lowest-risk category of the CLI permission model
([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees),
[Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions)).

- **Chain reads** — observation of public chain state without submitting an action.
- **BTCLI permissions** — which CLI tasks require no private key.

## Distinction from Subtensor

Subtensor names Bittensor's layer 1 blockchain and system of record. BTCLI permissions name which
forms of wallet authority are required before CLI actions can interact with that chain layer
([Glossary: Subtensor](https://docs.learnbittensor.org/resources/glossary#subtensor),
[Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions)).

- **Subtensor** — Bittensor's layer 1 blockchain and system of record.
- **BTCLI permissions** — wallet authority required before CLI actions interact with chain.

## Distinction from Yuma Consensus

BTCLI permissions describe which wallet roles the CLI may use when signing actions. Yuma Consensus
converts submitted validator weights into emission shares on a subnet
([Bittensor CLI](https://docs.learnbittensor.org/btcli),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **BTCLI permissions** — local scopes the CLI may use when signing.
- **Yuma Consensus** — on-chain weight aggregation that settles emissions.

## Distinction from Coldkey and Hotkey Workstation Security

BTCLI permissions name which authority level a CLI action requires. Workstation-security guidance
names where that authority should live across permissionless, hotkey, and coldkey environments
([Bittensor CLI: Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions),
[Coldkey and hotkey workstation security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).

- **BTCLI permissions** — which authority a CLI action requires.
- **Workstation security** — which environment should hold that authority.

## Reader Boundary

This article explains the permission model. It does not list every BTCLI subcommand, duplicate the
reference table, or provide wallet procedures. For the exact current command requirements, readers
should use the official BTCLI permissions guide and reference documentation.
