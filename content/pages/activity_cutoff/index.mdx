# Activity Cutoff

Activity cutoff is legacy subnet hyperparameter vocabulary for how long a validator may remain
without an on-chain update before its stake is masked inactive for Yuma Consensus. Documentation
originally expressed that tolerance as a fixed block count; on dynamic-tempo subnets the effective
span is derived from
[activity cutoff factor](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutofffactor)
and tempo instead
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## What It Controls

Activity cutoff vocabulary ties consensus participation to validator freshness measured from
[last update](https://docs.learnbittensor.org/subnets/metagraph). Each neuron carries a last-update
block; when the gap since that timestamp exceeds the effective inactivity span, the validator is
treated as inactive for the epoch pass and its stake is masked out of stake-weighted consensus until
it updates again
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

## Effect on Consensus

When an epoch runs, the subnet builds an inactive mask by comparing each neuron's last update block
to the current block: a neuron is inactive when its last update plus the activity cutoff is still
below the current block. Inactive neurons are then removed from the stake vector used for consensus,
their stake masked to zero before the active stake is normalized, so a stale validator carries no
weight in that epoch's stake-weighted consensus
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Subnet Metagraph](https://docs.learnbittensor.org/subnets/metagraph)).

This is why missing the cutoff costs influence and not just status: an inactive validator's weights
do not move consensus until it updates again and re-enters the active set
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

On subnets with dynamic tempos, the span used in that comparison is derived from activity cutoff
factor and tempo rather than from the legacy fixed block setting alone, so the inactive mask applies
the effective cutoff computed for that subnet
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

## Configured Per Subnet

Each subnet stores its own activity cutoff value as legacy hyperparameter state. The stored figure
on netuid 1 applies only to that subnet's table and can differ from the documented default and from
another netuid's setting
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Glossary: Activity Cutoff](https://docs.learnbittensor.org/resources/glossary#activity-cutoff)).

Examples that name netuid 1 illustrate one subnet's hyperparameter table. They should not be read as
proof that every subnet uses the same live cutoff
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

## Deprecated Under Dynamic Tempos

With the introduction of dynamic tempos, the activity cutoff hyperparameter is no longer settable.
Subnets now express validator inactivity tolerance through the
[activity cutoff factor](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutofffactor),
given in per-mille epochs rather than a fixed block count. Its default of 13,889 works out to about
13.889 tempos, which preserves the legacy 5,000-block cutoff at the default tempo of 360 blocks
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

The constants reference exposes that legacy startup default as
`api.consts.subtensorModule.initialActivityCutoff`, listed as `5000`. That constant names the
initial fixed block cutoff, while current dynamic-tempo subnets derive the effective inactivity span
from activity cutoff factor and tempo
([Subtensor Constants: initialActivityCutoff](https://docs.learnbittensor.org/subtensor-api/constants#initialactivitycutoff),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## Distinction from Last Update

Activity cutoff and last update are read as a pair on metagraph rows. Last update is the per-neuron
block field recording the neuron's most recent on-chain change, while activity cutoff vocabulary
names the allowed inactivity span readers compare against that timestamp
([Subnet Hyperparameters: Activity Cutoff](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutoff),
[Subnet Metagraph](https://docs.learnbittensor.org/subnets/metagraph)).

On its own neither value decides activity. Activity cutoff supplies the allowed inactivity span and
last update supplies the block timestamp from which that span is measured. On subnets with dynamic
tempos that span is derived from
[activity cutoff factor](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutofffactor)
and tempo rather than a legacy fixed block count alone, and a neuron counts as inactive only when
the gap since its last update exceeds the effective cutoff
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

- **Activity cutoff** — the allowed inactivity span applied for epoch purposes.
- **Last update** — the per-neuron block timestamp measured against that span.

## Distinction from Tempo

Activity cutoff names validator inactivity tolerance relative to tempo. Tempo names the recurring
block interval between subnet emission steps. On dynamic-tempo subnets the effective inactivity span
is derived from activity cutoff factor and tempo rather than a fixed block count alone
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Glossary: Tempo](https://docs.learnbittensor.org/resources/glossary#tempo)).

- **Activity cutoff** — inactivity span before a stale validator is masked out of consensus.
- **Tempo** — recurring interval between emission steps.

## Distinction from Epoch

Activity cutoff gates whether a validator's stake still counts in the current pass based on
last-update freshness. Epoch names the wider consensus window that groups those blocks and
submissions ([Glossary: Epoch](https://docs.learnbittensor.org/resources/glossary#epoch),
[Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch)).

- **Activity cutoff** — inactivity span measured from last update before stake is masked.
- **Epoch** — wider consensus window grouping tempo blocks.

## Distinction from Activity Cutoff Factor

Activity cutoff is the legacy fixed-block hyperparameter that dynamic tempos replaced. Activity
cutoff factor is the live per-mille setting that derives the effective inactivity span from tempo on
current subnets
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Subnet Hyperparameters: Activity Cutoff Factor](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutofffactor),
[Glossary: Activity Cutoff](https://docs.learnbittensor.org/resources/glossary#activity-cutoff)).

- **Activity cutoff** — legacy fixed-block inactivity window vocabulary.
- **Activity cutoff factor** — live per-mille input under dynamic tempos.

## Distinction from Weights Rate Limit

Activity cutoff is the hyperparameter that defines how many blocks stake may remain inactive for
epoch purposes in Yuma Consensus. Weights rate limit is the blocks a validator must wait between
weight commits
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Subnet Hyperparameters: Activity Cutoff](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutoff)).

- **Activity cutoff** — block-count rule for epoch participation in hyperparameter documentation.
- **Weights rate limit** — blocks between weight commits from the same validator.

## Distinction from Immunity Period

Immunity period shields a newly registered neuron from deregistration for a fixed number of blocks.
Activity cutoff is separate vocabulary for how long a validator may remain without an on-chain
update before its stake is masked inactive for consensus—not a post-registration displacement shield
([Glossary: Immunity Period](https://docs.learnbittensor.org/resources/glossary#immunity-period),
[Subnet Hyperparameters: Activity Cutoff](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutoff)).

- **Immunity period** — deregistration shield for a new neuron.
- **Activity cutoff** — inactivity span before a stale validator is masked out of consensus.

## Distinction from Validator Permit

Validator permit records whether a UID may submit validator weights at all. Activity cutoff is a
separate hyperparameter read from subnet state
([Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit),
[Subnet Hyperparameters: Activity Cutoff](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutoff)).

Readers tracing a failed participation check should compare permit status and cutoff hyperparameter
values on the same netuid rather than treating either field as a full activity verdict by itself
([Subnet Metagraph](https://docs.learnbittensor.org/subnets/metagraph)).

- **Validator permit** — whether a UID may submit validator weights.
- **Activity cutoff** — inactivity span before a stale validator is masked out of consensus.

## Distinction from Commit Reveal

Commit reveal and activity cutoff are different weight-timing rules. Commit reveal delays when
submitted validator weights become visible, concealing fresh weights for a reveal window, while
activity cutoff names how long a validator may remain without an on-chain update before its stake is
masked inactive for consensus
([Commit Reveal](https://docs.learnbittensor.org/concepts/commit-reveal),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Commit reveal** — delays when submitted weights become visible.
- **Activity cutoff** — inactivity span before a stale validator is masked out of consensus.

## Distinction from Pruning Score

Activity cutoff names validator inactivity tolerance measured from last update. Pruning score ranks
miners when a full subnet must displace one incumbent slot
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Glossary: Pruning Score](https://docs.learnbittensor.org/resources/glossary#pruning-score)).

- **Activity cutoff** — inactivity span before a stale validator is masked out of consensus.
- **Pruning score** — miner ranking input when one slot must open.

Validator-timing vocabulary and displacement-ranking vocabulary answer different subnet questions
([Mining: Miner deregistration](https://docs.learnbittensor.org/miners#miner-deregistration)).

## Distinction from Serving Rate Limit

Serving rate limit and activity cutoff are both counted in blocks but govern different actors.
Serving rate limit paces how often a miner may update its axon and prometheus serving metadata,
while activity cutoff names how long a validator may remain without an on-chain update before its
stake is masked inactive for consensus
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Serving rate limit** — paces miner endpoint metadata updates.
- **Activity cutoff** — inactivity span before a stale validator is masked out of consensus.

## Distinction from Weight Setting

Activity cutoff names validator inactivity tolerance measured from last update. Weight setting is
the validator action of assigning scores to miners in weight submissions
([Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch),
[Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Activity cutoff** — inactivity span before a stale validator is masked out of consensus.
- **Weight setting** — how validators score miners in those submissions.

## Distinction from Yuma Consensus

Activity cutoff names how long a validator may remain without an on-chain update before its stake is
masked inactive for the upcoming epoch pass. It is not the full mechanism that credits emission
shares at the epoch boundary
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Glossary: Activity Cutoff](https://docs.learnbittensor.org/resources/glossary#activity-cutoff),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Activity cutoff** — inactivity span measured from last update before stake is masked.
- **Yuma Consensus** — on-chain mechanism that uses validator weights to determine emission shares.

## Reader Boundary

This page defines the concept at a high level. It does not report the activity-cutoff value set on
any particular subnet, current epoch timing, or which validators are active right now. Those are
live chain state that should be checked for the relevant netuid.

The 5,000-block figure names the documented default for the legacy fixed-block hyperparameter. Under
dynamic tempos, that parameter is no longer settable; live inactivity tolerance is configured
through
[activity cutoff factor](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutofffactor)
on each netuid instead
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Glossary: Activity Cutoff](https://docs.learnbittensor.org/resources/glossary#activity-cutoff)).
