# Pure Proxies

Pure proxies are a Bittensor account-indirection concept. The official
[Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies)
documentation describes them as keyless accounts whose main use is multisignature wallet structures
with swappable members. In plain terms, a pure proxy is useful when the account address should stay
stable even if the person or key arrangement behind it changes.

## What It Represents

Pure proxies solve a continuity problem inside shared-control wallet designs. Multisig wallets
require approval from multiple
[signatories](https://docs.learnbittensor.org/resources/glossary#signatory) before an action
proceeds, but a naive multisig is tied to its visible member keys. If membership changes, the shared
wallet address may need to change too
([Secure a Coldkey with a Multisig Wallet](https://docs.learnbittensor.org/keys/multisig),
[Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies)).

Readers should separate two "proxy" ideas that sound similar:

- **Proxy wallet** — scoped delegation where one account performs limited operations for a protected
  coldkey.
- **Pure proxy** — keyless stand-in account that keeps a multisig member slot stable when signers
  rotate.

Proxy wallets answer routine delegated access. Pure proxies answer stable shared-wallet membership.
Choosing between them depends on whether the problem is limiting coldkey exposure or keeping one
multisig address fixed while humans behind a slot change
([Proxies overview](https://docs.learnbittensor.org/keys/proxies),
[Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies)).

Keyless describes the absence of a user-held signing key on the stand-in account itself. It does not
mean no one controls the pure proxy, that the design is risk-free, or that threshold approval can be
skipped. Control still flows through the accounts that manage the pure proxy inside the broader
multisig approval model
([Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies),
[Secure a Coldkey with a Multisig Wallet](https://docs.learnbittensor.org/keys/multisig)).

Pure proxies change how member slots stay stable, not how many signatures are required before an
action can proceed. A simple multisig without pure proxies may be easier to operate; a pure-proxy
multisig may be worth the added complexity when membership turnover would otherwise force frequent
address changes and counterpart reconfiguration.

## Multisig Continuity Without Changing the Shared Address

The pure-proxy guide highlights multisig continuity as the primary use case. If a team member leaves
and a new member joins, pure proxies can serve as stable stand-in members while control behind one
slot changes. The visible pure-proxy member stays in the multisig list; what changes is who controls
the underlying account that acts as that member
([Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies)).

That continuity can matter for counterparties, treasury records, and subnet or validator operations
that already reference one shared multisig address. Pure proxies reduce the need to re-register or
reconfigure every external dependency each time one human signer rotates off the team.

## Killing a Pure Proxy Is Permanent

Removing a pure proxy is destructive rather than reversible. The pure proxies documentation warns
that killing a pure proxy permanently deletes the account, and any funds remaining in it are
permanently lost, so the account should be emptied before it is killed
([Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies)).

## Development Stage Context

Pure-proxy examples should be read against the network boundary. Localnet and testnet setups
exercise keyless account and multisig structure without representing production wallet configuration
on mainnet ([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks),
[Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies)).

## Distinction from Proxy Wallets

Proxy wallets delegate limited authority for day-to-day operations. Pure proxies are keyless
stand-ins used mainly in multisig structures to keep an address stable when membership changes
([Proxies overview](https://docs.learnbittensor.org/keys/proxies),
[Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies)).

- **Proxy wallets** — delegated authority from a protected account to a less sensitive one.
- **Pure proxies** — keyless stand-ins that preserve multisig address stability.

## Distinction from Multisig

Multisig names how many signatories must approve before an action proceeds. Pure proxies name
stand-in member slots that keep the shared address fixed when membership changes
([Secure a Coldkey with a Multisig Wallet](https://docs.learnbittensor.org/keys/multisig),
[Glossary: Signatory](https://docs.learnbittensor.org/resources/glossary#signatory),
[Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies)).

- **Multisig** — shared control requiring multiple signatory approvals.
- **Pure proxies** — keyless stand-in members that preserve multisig address continuity.

## Distinction from Coldkey

A pure proxy is a keyless stand-in member that keeps a multisig address stable. A coldkey is the
primary ownership key that controls wallet authority
([Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies),
[Glossary: Coldkey](https://docs.learnbittensor.org/resources/glossary#coldkey)).

- **Pure proxy** — keyless stand-in member inside a shared-control structure.
- **Coldkey** — primary ownership key controlling wallet authority.

## Distinction from Hotkey

A pure proxy is a keyless stand-in account used for multisig continuity. A hotkey is an operational
signing key used for frequent network operations such as validation and mining
([Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies),
[Glossary: Hotkey](https://docs.learnbittensor.org/resources/glossary#hotkey)).

- **Pure proxy** — keyless stand-in member that keeps a multisig address stable.
- **Hotkey** — operational signing key used for frequent network operations.

## Distinction from Seed Phrase

A pure proxy deliberately has no user-held private key to back up or recover for the stand-in
itself. A seed phrase is recovery material that can restore a coldkey private key
([Glossary: Seed Phrase](https://docs.learnbittensor.org/resources/glossary#seed-phrase)).

- **Pure proxy** — keyless stand-in with no private key to back up for the stand-in itself.
- **Seed phrase** — recovery words that restore the coldkey private key.

## Distinction from SS58 Encoded Addresses

A pure proxy keeps a shared wallet's account identity stable when membership rotates. An SS58
encoded address is the compact representation of a public key used as a wallet address for TAO
transfers
([Glossary: SS58 Encoded](https://docs.learnbittensor.org/resources/glossary#ss58-encoded)).

- **Pure proxy** — keyless stand-in that preserves multisig address continuity.
- **SS58 encoded address** — encoded public-key representation used as a wallet address.

## Distinction from Yuma Consensus

Pure proxies are keyless stand-in accounts used in multisig wallet structures. Yuma Consensus
converts submitted validator weights into emission shares on a subnet
([Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Pure proxy** — keyless stand-in member for multisig continuity.
- **Yuma Consensus** — on-chain weight aggregation that settles emissions.

## Reader Boundary

Pure proxies should not be read as ordinary proxy wallets, coldkey replacements, or accounts with
their own spendable private keys. They name keyless stand-in accounts used mainly to keep multisig
membership stable when signers rotate
([Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies)).
