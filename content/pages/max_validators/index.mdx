# Max Validators

Max validators is a per-subnet hyperparameter that sets the maximum number of validators a subnet
allows. Official documentation describes it as the maximum validators on a subnet, making it a cap
on how many neurons can act as validators there at once.

References: [Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)

## What It Controls

The hyperparameter bounds the size of a subnet's validator set. A subnet can hold many registered
neurons, but only up to this maximum may serve as validators at the same time. It does not decide
which specific neurons validate; it only sets the ceiling on how many can.

Reference: [Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)

## Default and Setting

The documentation lists a default of 64 and marks the parameter as set at the root level rather than
by the subnet owner. The value actually in force is per-subnet chain state and can differ from the
documented default, so a subnet's real cap should be read for that subnet.

Reference: [Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)

## Subnet Context

Max validators is one of the subnet hyperparameters, the on-chain state variables that configure a
single subnet, for example netuid 1. Because each subnet carries its own hyperparameters, the
validator cap is defined per subnet and applies only within that subnet.

Reference: [Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)

## Relationship to Validator Permits

Validator status on a subnet is granted through validator permits, which go to the higher-stake
neurons. The maximum-validators cap bounds how many of those permits can exist at once: it sets the
ceiling that the permit system fills, so it connects directly to how many neurons end up validating
on the subnet.

References:
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit)

## Reader Boundary

This page defines the concept at a high level. It does not report the max-validators value set on
any particular subnet or which neurons currently hold validator permits. Those are live chain state
and should be checked for the relevant netuid. The default of 64 is the documented value, and the
parameter is governed at the root level.

Reference: [Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)

## Permit Ranking Can Change Between Epochs

The
[Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit)
describes permits as going to top
[stake](https://docs.learnbittensor.org/resources/glossary#stake)-weight neurons on a subnet.
Official epoch documentation explains that permit ordering can shift as stake ranking changes across
epochs, so the specific neurons holding permits is not fixed forever even when the max-validators
cap stays the same.

Max validators therefore limits how many permits can exist, while stake ranking decides which
neurons occupy those permit slots at a given time
([Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch)).

References:
[Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit),
[Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch)

## Lost Permits Clear Validator-Miner Bonds

Official bond documentation states that neurons retain
[validator-miner bonds](https://docs.learnbittensor.org/resources/glossary#validator-miner-bonds)
only while they keep validator permits. If a neuron loses its permit, its bonds are cleared.

That retention rule links validator-cap vocabulary to bond state. Max validators bounds how many
neurons can hold permits at once, and permit loss removes the bond history tied to validation rights
even if the neuron remains registered on the subnet.

References:
[Glossary: Validator-Miner Bonds](https://docs.learnbittensor.org/resources/glossary#validator-miner-bonds),
[Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit)

## Permitted Validators Still Face Activity Timing Rules

Holding a validator permit does not remove the activity cutoff rule for weight submission. Subnet
[hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters) still require
permitted validators to submit
[validator weights](https://docs.learnbittensor.org/resources/glossary#validator-weights) within the
early blocks of each [epoch](https://docs.learnbittensor.org/resources/glossary#epoch) to
participate in that epoch's consensus pass.

Max validators reading should therefore keep capacity separate from participation timing. The cap
decides how many validators may hold permits, while activity cutoff decides whether those validators
acted soon enough in the current epoch.

References:
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Glossary: Epoch](https://docs.learnbittensor.org/resources/glossary#epoch)
