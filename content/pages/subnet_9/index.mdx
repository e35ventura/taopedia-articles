# Subnet 9: IOTA

IOTA — **I**ncentivized **O**rchestrated **T**raining **A**rchitecture — is Bittensor Subnet 9
(SN9), operated by [Macrocosmos](https://iota.macrocosmos.ai/). It is the first subnet designed for
collaborative, permissionless pretraining of large language models (LLMs) across a network of
heterogeneous, independently-operated machines. Rather than requiring any single participant to hold
a full model in memory, IOTA distributes model layers across many miners and streams intermediate
activations between them. The technical design is described in Macrocosmos's research paper, which
is available on [ArXiv](https://arxiv.org/abs/2507.17766) and on the
[Macrocosmos research page](https://www.macrocosmos.ai/research/iota_primer.pdf).

## How the Mechanism Works

IOTA divides a language model into distinct pipeline stages — a head, one or more body layers, and a
tail — and assigns each stage to a different group of miners. During a training run, input data
flows through the head, whose output activations are passed to the body, which in turn passes to the
tail. This sequential, pipeline-parallel flow means that each miner only needs enough compute and
memory for its assigned layer rather than for the entire model.

An orchestrator manages the overall pipeline: it distributes which miners hold which layers, routes
activation data between stages, and coordinates weight synchronization. All network communication
passes through the orchestrator, and layer weights are periodically synchronized across the network
using a variant of Butterfly All-Reduce, a technique that merges locally-trained weights from
multiple nodes into a single consistent model state ([source](https://arxiv.org/abs/2507.17766)).

Miners compete to process as many activations as possible during each training round. Validators
perform spot-checks by replaying portions of the computation and comparing the miner's output
against expected values. Miners whose outputs fail these checks or who are unresponsive receive
lower scores. Final scores flow into [[Yuma Consensus]] to set per-epoch emissions in the subnet's
alpha token.

The current training run targets a 1.5B parameter Llama-inspired architecture split across three
pipeline stages. Macrocosmos plans to scale subsequent runs to 15B, 50B, and 100B parameter models
([source](https://github.com/macrocosm-os/iota)).

A live dashboard tracking active miners, layer assignments, training throughput, and general network
metrics is available at
[iota.macrocosmos.ai/dashboard/mainnet](https://iota.macrocosmos.ai/dashboard/mainnet).

## Participating as a Miner

Miners take responsibility for one or more pipeline stages of the current model. Each miner receives
activations from the preceding stage (or raw input data if assigned the head), performs the forward
and backward pass for its layers, and forwards the result to the next stage. Between training
rounds, miners upload their locally-updated weights so the network can merge them.

The hardware bar scales with the size of the layer assigned. Macrocosmos recommends a CUDA GPU with
at least 16 GB of VRAM for current runs, alongside a modern Ubuntu Linux environment. Setup and
onboarding details are documented in the
[official mining guide](https://docs.macrocosmos.ai/subnets/subnet-9-pre-training/subnet-9-iota-mining-setup-guide).

Miners register a hotkey on SN9 and then run the miner process provided in the
[macrocosm-os/iota repository](https://github.com/macrocosm-os/iota). Because the role of each miner
in the pipeline changes dynamically as the orchestrator rebalances load, miners must remain online
and responsive; extended downtime results in reassignment and score penalties.

## Participating as a Validator

Validators on IOTA perform statistical spot-checks against the miners processing activations in each
pipeline stage. After a miner reports that it has completed its assigned computation, a validator
may replay a subset of the same input through the expected layer and compare the result.
Discrepancies indicate either a faulty implementation or deliberate misreporting, and the miner's
score is penalized accordingly.

Because validators are checking correctness rather than reproducing the entire training run, their
compute requirements are substantially lower than those of miners. Validators submit weight vectors
to the chain, and [[Yuma Consensus]] aggregates those weights into the final emission distribution
for the epoch. Validator setup is documented in the
[official validator guide](https://docs.macrocosmos.ai/subnets/subnet-9-pre-training/subnet-9-validating).
