# Subtensor Nodes

Subtensor nodes are public chain-access nodes that synchronize with the Bittensor network. They let
software read and serve blockchain state without turning every Bittensor user into a separate chain
operator. The [Subtensor Node Basics](https://docs.learnbittensor.org/subtensor-nodes) documentation
frames these nodes as public Subtensor nodes that can connect with Bittensor networks and can be
either lite nodes or archive nodes.

## Public node versus local chain

A public Subtensor node is different from a local blockchain used for offline development. A public
node synchronizes with a Bittensor network, while a local chain is isolated and used for testing.
That distinction matters because a public node is part of chain access, not a private sandbox. The
[Subtensor Node Basics](https://docs.learnbittensor.org/subtensor-nodes) page makes this boundary
explicit when it compares public Subtensor nodes with local blockchains.

## Lite nodes

A lite node is the lower-storage public-node option. It is designed to reach useful synchronized
state without storing the entire history in the same way as an archive node. In reader terms, a lite
node is usually about practical chain access with a smaller storage footprint. The
[Subtensor Node Basics](https://docs.learnbittensor.org/subtensor-nodes) documentation describes
lite nodes as using finalized-block synchronization and retaining less historical data than archive
nodes.

## Archive nodes

An archive node stores the full blockchain history and supports use cases that need older state.
That makes archive nodes more suitable for explorers, indexers, analytics, audits, and other
history-heavy services. The [Subtensor Node Basics](https://docs.learnbittensor.org/subtensor-nodes)
page explains that archive nodes download and validate the full block history and provide fuller
historical access.

## Resource boundary

The practical difference between lite and archive nodes is not only what they serve, but also the
resources they require. Archive nodes need substantially more storage because they preserve the full
history, while lite nodes trade some historical depth for lower storage demand. The
[Subtensor Node Basics](https://docs.learnbittensor.org/subtensor-nodes) page explains this
tradeoff, and the
[Subtensor Node Requirements](https://docs.learnbittensor.org/subtensor-nodes/subtensor-node-requirements)
page separates node requirements by node type.

## Relation to nearby concepts

Subtensor nodes sit near [[dynamic_tao|Dynamic TAO]],
[[staking_and_delegation|Staking and Delegation]], and [[wallets|Wallets]]. Dynamic TAO and staking
activity depend on chain state being available to Bittensor-facing software. Wallets are where users
hold keys and balances, but a node is infrastructure for reading and serving chain state rather than
a wallet. The [Subtensor Node Basics](https://docs.learnbittensor.org/subtensor-nodes) page defines
the public node role and the lite/archive distinction.
