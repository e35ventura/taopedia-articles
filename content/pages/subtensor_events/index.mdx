# Subtensor Events

Subtensor events are named records emitted by Bittensor's Subtensor runtime
([Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events),
[Inspecting the Chain with Polkadot.js](https://docs.learnbittensor.org/concepts/inspecting-the-chain)).

The term belongs to runtime-record vocabulary. It should be read separately from storage entries,
which expose state, and extrinsics, which name submitted runtime actions.

## Runtime Records

An event name identifies a type of record emitted during runtime processing. It can show that a
runtime record exists, but it does not by itself explain every rule that produced the record
([Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events),
[Subtensor Error Codes](https://docs.learnbittensor.org/errors)).

This keeps event vocabulary separate from mechanism explanation. When an article explains why an
event matters, the surrounding mechanism still needs its own context.

Events also need outcome context when they appear near a failed or successful submitted action. In
that case, the event record should be read beside the extrinsic and any relevant error-code
information rather than as the whole explanation by itself
([Subtensor extrinsics](https://docs.learnbittensor.org/subtensor-api/extrinsics),
[Subtensor Error Codes](https://docs.learnbittensor.org/errors)).

## Runtime Areas

Event names are grouped by runtime area. The area is part of the meaning because similar-looking
records can carry different context when they belong to different areas
([Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events),
[Subtensor Storage](https://docs.learnbittensor.org/subtensor-api/storage)).

Reading the area and event name together is more precise than reading the event name alone. It also
keeps an event from one area from becoming a statement about every Subtensor event.

## Event Records and Chain Inspection

The event reference names event types. Chain inspection can show an emitted record in a selected
network and block context ([Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events),
[Inspecting the Chain with Polkadot.js](https://docs.learnbittensor.org/concepts/inspecting-the-chain),
[Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

That distinction matters: the event type is reusable vocabulary, while an emitted record belongs to
the history that produced it. A concrete record should stay attached to its network, block, and
runtime context.

## Storage and Extrinsics

Storage, events, and extrinsics describe different Subtensor surfaces. Storage exposes state, events
name emitted runtime records, and extrinsics name submitted runtime actions
([Subtensor Storage](https://docs.learnbittensor.org/subtensor-api/storage),
[Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events),
[Subtensor extrinsics](https://docs.learnbittensor.org/subtensor-api/extrinsics)).

A single feature can involve all three surfaces without making them interchangeable. The submitted
action, emitted record, and resulting state are connected, but each one answers a different
reference question.

## Network and Block Context

Events are interpreted inside chain history. The same event name can appear across network
environments, but emitted records belong to the chain context where they were produced
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks),
[Inspecting the Chain with Polkadot.js](https://docs.learnbittensor.org/concepts/inspecting-the-chain)).

A localnet or testnet event example can illustrate event vocabulary, but it should not stand in for
another network's chain history. The environment and block context should stay attached when the
article discusses an observed record.

## Interpretation Limits

Subtensor events should be read as runtime-record vocabulary. They are not proof of off-chain
intent, not a complete mechanism explanation, and not a substitute for storage or extrinsic context
([Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events),
[Subtensor Storage](https://docs.learnbittensor.org/subtensor-api/storage)).

The stable article-level point is that Subtensor events name records emitted during runtime
processing. Event names should not be presented as instructions about which record a reader should
search for in a particular decision.
