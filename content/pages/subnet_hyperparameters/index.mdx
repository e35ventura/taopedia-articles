# Subnet Hyperparameters

Subnet hyperparameters are protocol state variables that shape how a Bittensor subnet behaves. They
cover timing, validator-weight flow, consensus behavior, emission handling, and lifecycle limits for
a selected subnet
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## What It Represents

Subnet hyperparameters name the owner-settable protocol envelope around a selected
[netuid](https://docs.learnbittensor.org/resources/glossary#netuid). They set timing, limits, and
processing boundaries; they do not define the subnet task, scoring model, or domain-specific
evaluation goal
([Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

Readers should separate four layers that hyperparameter vocabulary often mixes:

- **Hyperparameters versus incentive mechanism** — hyperparameters change when or how signals are
  processed; the incentive mechanism defines what miners produce and how validators evaluate it.
- **Live hyperparameter versus Subtensor constant** — a hyperparameter is the live per-subnet value
  after creation; `initial` constants name compile-time defaults the runtime starts from
  ([Subtensor Constants](https://docs.learnbittensor.org/subtensor-api/constants)).
- **Selected setting versus subnet task** — tempo, activity cutoff, and burn bounds answer protocol
  envelope questions; they do not replace mechanism design.
- **Timing families** — different hyperparameters count different units. Tempo counts blocks per
  epoch; activity cutoff counts blocks within an epoch; weights rate limit counts blocks between
  commits; commit reveal period counts tempos before reveal; serving rate limit paces endpoint
  registration separately from weight submission.

A hyperparameter claim should name the specific setting, subnet, and network context. A tempo claim
concerns epoch cadence; a commit-reveal claim concerns weight-submission timing; neither replaces
the work target.

## Development Stage Context

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. For subnet
hyperparameters on a subnet such as netuid 1, that sequence changes how readers should interpret
configuration values and activity-window settings.

In localnet, subnet hyperparameters can be tested in an isolated environment. Local parameter values
reflect local chain configuration rather than production subnet rules.

On testnet, subnet hyperparameters can be observed in a shared, non-production network. Testnet
parameter tables on a selected netuid are separate from mainnet subnet state
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

On mainnet, subnet hyperparameters are the live configuration fields that govern subnet behavior on
the production Bittensor network.

The [Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet. A hyperparameter example from one environment should not
be read as representing production subnet configuration on another network.

## Activity Cutoff Sets the Early Weight Window

Subnet [hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters) include
activity cutoff measured in blocks within each
[epoch](https://docs.learnbittensor.org/resources/glossary#epoch). On a subnet such as netuid 1, a
validator must submit
[validator weights](https://docs.learnbittensor.org/resources/glossary#weight-vector) within the
first activity-cutoff blocks of an epoch or wait until the next epoch to participate.

That setting shapes validator signal timing. It is one example of how hyperparameters constrain
consensus input without defining what miners produce
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## Min and Max Burn Bound Neuron Registration Cost

The hyperparameter reference lists `MinBurn` and `MaxBurn` as the lower and upper bounds on the
dynamic TAO burn required to register a neuron. The live registration price moves inside that band
rather than staying fixed at either bound
([Register](https://docs.learnbittensor.org/resources/glossary#register),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

Burn hyperparameters therefore belong to the registration envelope. They limit how low or high entry
cost can fall without replacing the registration process itself.

## Tempo Counts Blocks in Each Epoch

The `tempo` hyperparameter sets the block-based cadence for subnet epochs. The
[Glossary: Tempo](https://docs.learnbittensor.org/resources/glossary#tempo) defines tempo as the
interval over which [Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)
calculates [emissions](https://docs.learnbittensor.org/resources/glossary#emission) from the latest
ranking [weight matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix).

Tempo is a timing hyperparameter, not a scoring rule. It tells readers how many blocks group epoch
processing on a subnet such as netuid 1; the incentive mechanism still defines the subnet task
inside that cadence.

## Kappa Sets the Stake Threshold for Clipping

The kappa hyperparameter sets how much of a subnet's validator stake must support a weight level
before that level becomes the clipping ceiling for a miner during Yuma Consensus. With the default
kappa of 0.5, at least half of stake-weighted validator support must agree that a miner deserves
weight above a given level before more generous weights are left unclipped
([Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

Readers should not treat kappa as a miner-quality score. It governs how aggressively outlier weights
are trimmed relative to stake-backed consensus, not how useful a miner's subnet work was in
isolation
([Glossary: Consensus Score](https://docs.learnbittensor.org/resources/glossary#consensus-score)).

## Commit Reveal Period Counts Tempos Before Reveal

The hyperparameter reference lists `CommitRevealPeriod` as the number of tempos that must elapse
before validator weights submitted under Commit Reveal become readable
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Commit Reveal](https://docs.learnbittensor.org/concepts/commit-reveal)).

This is a tempo-counted delay, not a block-counted one like activity cutoff. A longer commit-reveal
period means more full epochs pass before a given submission's weights can be read.

## Weights Rate Limit Spaces Out Weight Commits

The hyperparameter reference lists `WeightsRateLimit` as the number of blocks a validator must wait
between weight commits
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

That setting bounds how often a single validator can resubmit weights, separate from activity
cutoff, which bounds when a submission must arrive to count for the current epoch.

## Serving Rate Limit Paces Miner Endpoint Registration

The hyperparameter reference lists `ServingRateLimit` as the rate limit on how often a miner can
register or update its network endpoint information on the subnet
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

This setting paces endpoint-registration activity specifically. It is separate from
weight-submission pacing, which the weights rate limit and activity cutoff hyperparameters govern
instead.

## Max Allowed UIDs Caps Total Registered Neurons

The hyperparameter reference lists `MaxAllowedUids` as the maximum number of neurons a subnet can
hold, distinct from `MaxAllowedValidators`, which caps how many of those neurons may act as
validators at once
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

That split separates the overall registration ceiling from the validator-specific ceiling already
covered by max validators. A subnet's total neuron slots and its validator slots are two different
configured limits.

## Subnet Is Active Marks Whether Emissions Have Started

The hyperparameter reference lists `SubnetIsActive` as a flag indicating whether a subnet's
emissions have started
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

This flag is a lifecycle marker rather than a performance or ranking value. A subnet can exist and
hold registered neurons before this flag reflects that emissions are flowing.

## Toggle Transfer Controls Stake Movement Between Coldkeys

The hyperparameter reference lists `ToggleTransfer` as the setting that allows or disallows
transferring stake between coldkeys on a subnet
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

That setting governs a transfer pathway specifically. It does not change staking, unstaking, or
delegation behavior, which are separate actions from moving already-staked balances between
coldkeys.

## Distinction from Subtensor Constants

- **Subnet hyperparameter** — live per-subnet value used after creation.
- **Subtensor constant** — compile-time runtime default or bound
  ([Subtensor Constants](https://docs.learnbittensor.org/subtensor-api/constants)).

## Distinction from Incentive Mechanism

- **Subnet hyperparameter** — protocol envelope of timing and limits.
- **Incentive mechanism** — task and scoring that define the subnet's work
  ([Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism)).

## Distinction from Validator-Miner Bonds

- **Bonds penalty / bonds reset hyperparameters** — adjust how bonds behave on a subnet.
- **Validator-miner bonds** — bond vocabulary for validator-miner relationship tracking
  ([Glossary: Validator-Miner Bonds](https://docs.learnbittensor.org/resources/glossary#validator-miner-bonds)).

## Distinction from Yuma Consensus

- **Subnet hyperparameters** — owner-settable protocol envelope for a subnet.
- **Yuma Consensus** — epoch-boundary settlement from eligible validator weights to emission shares
  ([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

## Reader Boundary

A hyperparameter claim should name the behavior being described and stay separate from the subnet
task, incentive mechanism, or live value source. Tempo claims concern epoch cadence; Commit Reveal
claims concern weight-submission timing; neither replaces the work target
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism)).

Subnet hyperparameters are best used as context around timing, weights, consensus, emissions, and
limits. They are not an operator manual, deployment status label, or substitute for the subnet's
incentive design.
