# VPermit

VPermit is a Bittensor validation term for the subnets where a delegate is authorized to validate.
The [Glossary](https://docs.learnbittensor.org/resources/glossary#vpermit) defines VPermit as a list
of subnet IDs that indicate which subnets a delegate is authorized to validate on.

## Delegate Context

A delegate can validate in more than one subnet. VPermit is the delegate-level view of that
authorization, while a
[validator permit](https://docs.learnbittensor.org/resources/glossary#validator-permit) is the
subnet-level permission flag for validation rights.

## Subnet ID List Authorization

The [Glossary: VPermit](https://docs.learnbittensor.org/resources/glossary#vpermit) defines VPermit
as a list of subnet IDs that indicate which subnets a delegate is authorized to validate on. That
list format is the core data shape behind the term rather than a single on-or-off flag for the whole
network.

Readers should read VPermit as a delegate-level authorization list keyed by netuid. Checking one
subnet still requires subnet-level validator permit vocabulary for that netuid. Empty or missing
list entries should be read against live chain state rather than inferred from unrelated staking
totals.

References: [Glossary: VPermit](https://docs.learnbittensor.org/resources/glossary#vpermit),
[Glossary: Netuid](https://docs.learnbittensor.org/resources/glossary#netuid)

## Cross-Subnet Permission Summary

VPermit rolls up subnet validation authorization for one delegate across the netuids where that
delegate may validate. The
[Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit)
describes the subnet-level permission flag, while VPermit summarizes which of those subnet-level
permissions apply to the same delegate identity.

Readers should use VPermit when a passage needs the delegate-wide view and validator permit when the
question is limited to one subnet's validation rights. A delegate can hold different authorization
states on different netuids, so the list should be read netuid by netuid when precision matters.

References: [Glossary: VPermit](https://docs.learnbittensor.org/resources/glossary#vpermit),
[Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit)

## Permission Scope Versus Emission Outcome

VPermit names where a delegate may validate, not how much emission the delegate earns on those
subnets. The [Glossary: VPermit](https://docs.learnbittensor.org/resources/glossary#vpermit) stays
on the authorization side, while [Emission](https://docs.learnbittensor.org/learn/emissions) and
dividend vocabulary describe reward distribution after validation and consensus processes run.

Readers should not read a VPermit list as a payout schedule or validator ranking. Live permissions,
stake weight, and emission outcomes belong in current official validator and chain references. A
delegate may be authorized on a subnet while still needing stake-weight context before validation
rights take effect there.

References: [Glossary: VPermit](https://docs.learnbittensor.org/resources/glossary#vpermit),
[Emission](https://docs.learnbittensor.org/learn/emissions)

## Relationship to Validator Permits

The glossary describes VPermits as aggregating individual validator permits across multiple subnets.
At Taopedia level, the useful distinction is scope: a validator permit answers whether validation
rights apply inside one subnet, while VPermit summarizes the subnets where those rights apply for a
delegate.

## Stake Weight Context

Individual validator permits are tied to stake-weight position inside each subnet. The
[Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit)
describes those permits as awarded to the top neurons by stake weight within a subnet. VPermit is
the delegate-level summary of which subnets carry that authorization, so a delegate's VPermit
reflects where those stake-weight-based subnet permits apply across the subnets they validate on.

References: [Glossary: VPermit](https://docs.learnbittensor.org/resources/glossary#vpermit),
[Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit),
[Glossary: Stake Weight](https://docs.learnbittensor.org/resources/glossary#stake-weight)

## Relationship to Multiple Mechanisms

VPermit summarizes the subnets where a delegate is authorized to validate. The
[Glossary](https://docs.learnbittensor.org/resources/glossary#multiple-incentive-mechanisms) notes
that validators must evaluate miners separately for each mechanism.

For readers, VPermit still names delegate-level subnet authorization. Validation rights on a subnet
that runs more than one incentive mechanism still span separate evaluation contexts inside that
netuid.

References:
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets),
[Glossary: Multiple Incentive Mechanisms](https://docs.learnbittensor.org/resources/glossary#multiple-incentive-mechanisms)

## Relationship to Child Hotkeys

VPermit and child hotkeys both concern which keys may validate, but they describe different things.
VPermit is the list of subnet IDs a delegate is authorized to validate on, as the
[Glossary](https://docs.learnbittensor.org/resources/glossary#vpermit) defines it. A child hotkey,
by the [Child Hotkeys](https://docs.learnbittensor.org/validators/child-hotkeys) documentation, is a
separate key that a parent hotkey authorizes to validate on its behalf by re-delegating a portion of
the parent's stake to it, without transferring ownership of that stake.

For readers, VPermit answers which subnets a delegate is permitted to validate on, while a child
hotkey answers which key carries out that validation for a parent. The two are not interchangeable:
VPermit is a per-delegate summary of authorized subnets, whereas a child hotkey is a delegated key
that performs validation using the parent's re-delegated stake-weight. VPermit describes where a
delegate may validate; a child hotkey is one way the validation itself can be carried out on a
parent's behalf.

References: [Glossary: VPermit](https://docs.learnbittensor.org/resources/glossary#vpermit),
[Child Hotkeys](https://docs.learnbittensor.org/validators/child-hotkeys)

## Reader Boundary

This article defines the term at a high level. It does not list live permissions, rank validators,
describe staking or registration steps, or restate validator requirements. Readers should use
official validator references for those details.

## Relationship to Coinbase

VPermit and coinbase are related but different concepts that sit on different layers of Bittensor.
VPermit is the delegate-level summary of which subnets a delegate is authorized to validate on. The
[Coinbase Implementation](https://docs.learnbittensor.org/navigating-subtensor/emissions-coinbase)
documentation describes coinbase as the per-block protocol mechanism that drives TAO emission,
accumulates pending emissions, and triggers Yuma Consensus rounds at epoch boundaries, while the
[Glossary: VPermit](https://docs.learnbittensor.org/resources/glossary#vpermit) describes the
delegate-level permission summary.

The two answer different questions. VPermit is a permission-scope concept: it records, across
subnets, where a delegate is authorized to validate. Coinbase is an emission concept: it is the
recurring per-subnet process that produces and distributes emissions each epoch on the subnets where
validation takes place. VPermit does not itself perform or allocate any emission, and coinbase is
not a permission record; one summarizes authorization across subnets, while the other names the
mechanism that generates each subnet's emissions.
