# Bittensor Tools

Bittensor tools are software interfaces around the network. They include the Bittensor SDK, BTCLI,
wallet-facing interfaces, and read-oriented utilities for network inspection
([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools),
[Wallets](https://docs.learnbittensor.org/keys/wallets)).

The central distinction is interface versus mechanism. Tools expose ways to reach Bittensor
features; protocol, subnet, and consensus documentation explain the rules those features follow
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

## Interface Layer

Tooling sits around the protocol. A tool can present subnet information, network activity, or
role-facing views, but the tool does not define the subnet task or consensus rule
([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

That boundary keeps tool articles from becoming operating manuals. The useful article-level point is
that Bittensor tools are the software layer readers meet before moving into more specific wallet,
subnet, staking, or chain articles.

## Tool Families

Bittensor tooling includes developer libraries, terminal interfaces, and user-facing interfaces
([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools)). Those families differ by
audience and shape: libraries serve software projects, terminal interfaces serve text-based use, and
user interfaces guide human interaction.

The family distinction helps readers choose the right article context. A library article should be
read as developer-facing tooling, while a terminal or user-interface article should be read as a
human-facing interaction topic.

## SDK Context

The Bittensor SDK belongs to the developer-library side of the tool family. It is a Python library
for software that works with Bittensor network features
([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools),
[SDK Reference](https://docs.learnbittensor.org/sdk/bt-api-ref)).

At article level, the SDK category points to application building and network queries. It should not
be read as a subnet, a consensus rule, or a replacement for the mechanism article that defines a
network feature.

## BTCLI Context

BTCLI is the terminal-facing member of the tool family. It groups several Bittensor areas, including
staking, subnet, and network-status topics, into one interface
([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools),
[BTCLI Reference](https://docs.learnbittensor.org/btcli)).

That grouping is useful for orientation, but it does not make BTCLI the rule for every area it
touches. Wallet, staking, subnet, and network-status concepts still belong to their own articles and
official references.

## Wallet and Inspection Context

Wallet-facing tools sit on the user-interface side of the Bittensor tool map. They help readers
place wallet and key topics inside the broader tool family without replacing the wallet articles
([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools),
[Wallets](https://docs.learnbittensor.org/keys/wallets)).

Read-oriented utilities help readers inspect chain or network information without changing the
meaning of the underlying state. The Tools page places network querying and monitoring in the tool
family, while the chain-inspection material belongs to the broader read-only context for Bittensor
state ([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools),
[Inspecting the Chain](https://docs.learnbittensor.org/concepts/inspecting-the-chain)).

That makes inspection utilities useful for orientation. They can surface network information, but
they should not be treated as the protocol rule that creates that information.

## Network Context

Tools can show information from different network environments. Bittensor documentation separates
mainnet, testnet, and localnet, so tool information should be interpreted with the connected
environment attached
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

This does not make the tool family environment-specific. It means the same kind of interface can
point at different network contexts, and the context affects how the displayed information should be
read.

## Relationship to Roles and Subnets

Miners, validators, subnet creators, and developers can all use tools, but the tool does not define
the role. The [Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction) frames
Bittensor around subnets, miners, validators, and digital commodities; tools are the software
surfaces around that structure.

Subnets still provide the work-and-evaluation context. The
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets) article is
the better place for the subnet model, while the tools article explains the interface layer around
that model.

## Reader Boundary

Bittensor tools should be read as interface terms
([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools)). They are not shortcuts around
protocol rules, guarantees of readiness for a role, or proof that the same result applies in every
environment.

This page defines the interface layer around Bittensor features rather than replacing tool manuals,
wallet-safety articles, subnet articles, or mechanism articles.
