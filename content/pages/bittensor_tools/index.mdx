# Bittensor Tools

Bittensor tools are software interfaces around the network. They give developers, miners,
validators, and other readers ways to work with Bittensor features without making the interface
itself part of the protocol ([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools)).

The central distinction is interface versus mechanism. Tools expose ways to reach Bittensor
features; protocol, subnet, and consensus documentation explain the rules those features follow
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

## Interface Layer

Tooling sits around the protocol. A tool can present subnet information, role context, or network
views, but the tool does not define the subnet task or consensus rule
([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

That boundary keeps tool articles from becoming operating manuals. The useful article-level point is
that Bittensor tools are interface context around network features, while the protocol articles
explain the rules behind those features.

A tool can make a feature easier to reach, inspect, or organize, but it does not change what the
feature means. That separation helps readers avoid treating a convenient interface as network
authority.

## Tool Families

Bittensor tooling includes developer libraries, terminal interfaces, and user-facing interfaces
([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools)). Those families differ by
audience and shape: libraries serve software projects, terminal interfaces serve text-based use, and
user interfaces guide interaction.

The family distinction helps readers choose the right article context. A library article belongs to
developer-facing tools, while a terminal or user-interface article belongs to the interaction layer.

## Developer Library Context

Developer libraries belong to the integration side of the tool family. They provide software-facing
context for Bittensor features ([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools),
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction)).

For readers, a developer library should be read as an integration interface. It is not a subnet, a
consensus rule, or a replacement for the mechanism documentation that defines what a network feature
means.

## Terminal Interface Context

Terminal tooling belongs to the direct-interaction side of the tool family
([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools)). It can expose many Bittensor
features through one interface, but those exposed features still belong to their underlying protocol
or subnet context.

That means a terminal surface should not be treated as the rule that validates a feature. It is an
interface for reaching Bittensor functionality; the network and subnet mechanisms determine the
meaning of the underlying concept.

This distinction is useful because a single terminal surface can group several kinds of network
context. The grouping is an interface convenience, not a statement that every exposed feature
belongs to one protocol category.

## Network Context

Tools can show information from different network environments. Bittensor documentation separates
mainnet, testnet, and localnet, so tool information should be interpreted with the connected
environment attached
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

This does not make the tool family environment-specific. It means the same kind of interface can
point at different network contexts, and the context affects how the displayed information should be
read.

For a reader, the network label is part of the tool context. A result seen through a localnet,
testnet, or mainnet interface should stay attached to that environment rather than being generalized
across all Bittensor networks.

## Relationship to Roles and Subnets

Miners, validators, subnet creators, and developers can all use tools, but the tool does not define
the role. The [Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction) frames
Bittensor around subnets, miners, validators, and digital commodities; tools are the software
surfaces around that structure.

Subnets still provide the work-and-evaluation context. The
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets) article is
the better place for the subnet model, while the tools article explains the interface layer around
that model.

## Reader Boundary

Bittensor tools should be read as interface terms
([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools)). They are not shortcuts around
protocol rules, guarantees of readiness for a role, or proof that the same result applies in every
environment.

This page defines the interface layer around Bittensor features rather than replacing tool manuals
or mechanism articles.

## Environment Context

Tool descriptions inherit the environment they point at. Bittensor documentation separates localnet,
testnet, and mainnet, so a tool description is strongest when the environment is clear
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks),
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)).

Localnet descriptions belong to an isolated setting. They can illustrate how an interface presents a
feature, but they should not be read as broad network evidence.

Testnet descriptions belong to a shared testing environment. They can show how a tool surface
behaves with shared chain context while staying separate from mainnet.

Mainnet descriptions belong to the main Bittensor environment. They should still be read through the
tool's interface role rather than as a replacement for the mechanism article.

An environment-specific description should not be read as evidence for another environment. The same
interface family can appear across environments, but the network context changes how the result
should be understood.
