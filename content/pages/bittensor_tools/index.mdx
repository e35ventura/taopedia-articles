# Bittensor Tools

Bittensor tools are software interfaces for working with the Bittensor network. They help separate
the software used to reach a feature from the network mechanism that gives the feature meaning.

The tools overview groups the topic around the SDK, the terminal interface, and wallet/key material
for developers, miners, and validators
([Bittensor Tools: SDK](https://docs.learnbittensor.org/concepts/tools#bittensor-sdk),
[Bittensor Tools: CLI](https://docs.learnbittensor.org/concepts/tools#bittensor-cli),
[Wallets and Keys](https://docs.learnbittensor.org/keys/wallets)). Those interfaces provide access
to Bittensor features, while subnet, consensus, and governance references explain the rules behind
the features being accessed
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets),
[Governance](https://docs.learnbittensor.org/governance)).

## Interface Layer

Tooling sits around the protocol. A tool can present subnet information, role-related views, or
network-facing context, while the underlying references define the subnet task, consensus rule, or
governance process being reached ([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets),
[Governance](https://docs.learnbittensor.org/governance)).

This boundary matters for interpretation. A tool reference explains the interface role for a
feature. A mechanism reference explains why the feature behaves the way it does inside Bittensor.

## Tool Families

Bittensor tooling includes developer libraries, terminal interfaces, and wallet/key documentation.
The tools page names the SDK, the Bittensor terminal interface, and wallet/key material as core
entry points ([Bittensor Tools: SDK](https://docs.learnbittensor.org/concepts/tools#bittensor-sdk),
[Bittensor Tools: CLI](https://docs.learnbittensor.org/concepts/tools#bittensor-cli),
[Wallets and Keys](https://docs.learnbittensor.org/keys/wallets)).

Those families differ by audience and reading context. A library reference usually points to
software integration, a terminal reference points to direct terminal interaction, and a wallet/key
reference points to account and signing context. The family distinction helps readers understand the
interface category before moving to the underlying network mechanism.

## SDK Context

The SDK belongs to the developer-library side of the tool family. It is the programmatic interface
for software that needs to work with Bittensor features
([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools),
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction)).

That makes SDK context most useful when the topic is integration shape. When the topic is the
meaning of a subnet rule, incentive mechanism, or governance decision, the SDK belongs beside the
mechanism-specific source rather than replacing it.

## CLI and Wallet Context

The terminal interface is the terminal-facing member of the tool family. It provides a direct way to
work with wallet, subnet, and network-status contexts without changing what those underlying network
concepts mean
([Bittensor Tools: CLI](https://docs.learnbittensor.org/concepts/tools#bittensor-cli)).

Wallet and key material is adjacent because Bittensor accounts rely on cryptographic keys for
signing context. That makes wallet/key references useful for account context, while terminal
references are useful for the interface through which a user may inspect network-facing information
([Wallets and Keys](https://docs.learnbittensor.org/keys/wallets),
[Working with Keys](https://docs.learnbittensor.org/keys/working-with-keys)).

The distinction keeps tool prose from turning into usage instructions. A terminal or wallet/key
reference can explain the interface category, while protocol and subnet references explain what the
workflow means inside Bittensor.

## Role and Subnet Context

Miners, validators, subnet creators, and developers can all use tools, but the tool does not define
the role. The Bittensor introduction frames the network around subnets, miners, validators, and
digital commodities; tools are the software interfaces around that structure
([Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

Subnets still provide the work-and-evaluation context. The subnet model explains what is being
coordinated, miners and validators explain the work loop, and tools explain the surrounding access
path.

## Subnet Boundary

Tool references should not flatten subnet vocabulary. A tool may expose subnet status or management
information, while the subnet task, subnet protocol, and scoring model remain separate concepts
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets),
[Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism)).

That boundary helps when reading articles about specific subnet behavior. A tool can show
information related to a subnet, while the subnet's own design explains why that information
matters.

## Network Scope

Bittensor documentation separates mainnet, testnet, and localnet contexts
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

A tooling example from one environment should not be treated as proof about another environment.
Localnet examples can show controlled behavior, testnet examples can show shared non-production
conditions, and mainnet references need separate support from mainnet-specific material.

Tool descriptions should therefore carry their environment when the environment matters. A tool
interface can exist across networks, but an observed result from one network is not automatically
evidence about another network.

## Reader Boundary

Bittensor tools should be read as interface vocabulary. The term supports access-layer context:
which kind of software interface is involved, who is likely to use it, and what neighboring network
concept it touches ([Bittensor Tools](https://docs.learnbittensor.org/concepts/tools),
[Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

The stable reference point is that Bittensor tools provide ways to interact with the network. When a
description moves into protocol behavior, role status, governance outcome, subnet quality, or
network-specific results, it needs the neighboring mechanism source as well.
