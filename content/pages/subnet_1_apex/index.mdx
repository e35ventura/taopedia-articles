# Subnet 1: Apex

Apex is Bittensor's first subnet (netuid 1), operated by [Macrocosmos](https://macrocosmos.ai). Its
incentive mechanism runs open competitions where miners submit Python-based algorithms and
validators continuously score those submissions against benchmarks. Rewards flow to miners whose
solutions perform best, creating a permissionless environment for algorithmic and agentic
optimization research. The [Apex overview](https://docs.macrocosmos.ai/subnets/subnet-1-apex) and
[macrocosm-os/apex](https://github.com/macrocosm-os/apex) repository describe the live subnet
mechanism.

## How the Mechanism Works

The Apex mechanism is structured around three layers:

- **Competition:** A defined problem domain with scoring criteria. Multiple competitions can run
  simultaneously on the subnet.
- **Round:** A discrete evaluation cycle within a competition. Submissions are scored each round,
  and cumulative performance across rounds determines a miner's rank.
- **Submission:** A Python algorithm uploaded by a miner via the Apex CLI. Validators pull the
  latest submission from each miner and score it against the competition's benchmark.

Validators run continuously and score all active miner submissions. The
[incentive mechanism](https://docs.macrocosmos.ai/subnets/new-subnet-1-apex/incentive-mechanism)
documentation and [macrocosm-os/apex](https://github.com/macrocosm-os/apex) repository describe how
those scores become reward-relevant signals on netuid 1.

## Current Competitions

Competitions rotate over time. The current active list is maintained at the
[Macrocosmos current competitions page](https://docs.macrocosmos.ai/subnets/new-subnet-1-apex/subnet-1-base-miner-setup/current-competitions).

Active competitions at time of writing include:

### Iota Simulator

Miners submit routing and load-balancing algorithms for a simulated distributed training pipeline.
The simulator models a heterogeneous network of nodes moving forward and backward activation tensors
across layers. Miners are scored on throughput under realistic conditions: node churn, variable
latency, and bandwidth constraints. See the
[Iota Simulator](https://docs.macrocosmos.ai/subnets/subnet-1-apex/subnet-1-current-competitions#id-2.-iota-simulator)
entry for the current task definition.

### Energy Arbitrage

Miners submit algorithms that optimize energy trading decisions across simulated markets. Scoring
rewards efficient arbitrage strategies under realistic supply and demand conditions. The
[current competitions](https://docs.macrocosmos.ai/subnets/new-subnet-1-apex/subnet-1-base-miner-setup/current-competitions)
page lists active task details.

### RL Tron

Miners train reinforcement learning agents to play a Tron-style grid competition. Agents compete
head-to-head in the game environment; validators score submissions on win rate and efficiency. Task
details appear on the same
[current competitions](https://docs.macrocosmos.ai/subnets/new-subnet-1-apex/subnet-1-base-miner-setup/current-competitions)
page.

## Participating as a Miner

Miners interact with Apex through the Apex CLI. The general flow is:

1. Register a hotkey on SN1 using `btcli`.
2. Install the Apex CLI via the
   [miner setup docs](https://docs.macrocosmos.ai/subnets/new-subnet-1-apex/subnet-1-base-miner-setup).
3. Choose an active competition and implement an algorithm meeting the submission spec.
4. Submit via the
   [Apex CLI](https://docs.macrocosmos.ai/subnets/new-subnet-1-apex/subnet-1-base-miner-setup/apex-cli);
   validators pick up the latest submission automatically.
5. Monitor round scores to iterate on the algorithm.

## Participating as a Validator

Validators on Apex run the subnet's scoring logic locally, pulling miner submissions and evaluating
them against each competition's benchmark environment. Scores are submitted as weights to the chain.
The [validator setup](https://docs.macrocosmos.ai/subnets/new-subnet-1-apex/validating)
documentation covers the local evaluation workflow.

## Miner and Validator Roles

Subnet 1 operates under the standard Bittensor two-role structure. Miners supply the subnet's
capability and validators evaluate those contributions and set weights. Reward distribution follows
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus).

## Incentive Task and Miner Evaluation Pipeline

Apex's incentive task is competition-specific work: miners implement Python algorithms for the
active competition, upload them through the Apex CLI, and validators benchmark each submission
against that competition's environment. The
[incentive mechanism](https://docs.macrocosmos.ai/subnets/new-subnet-1-apex/incentive-mechanism)
documentation describes how round scores accumulate into miner rank within a competition rather than
as a one-off score.

That evaluation layer sits upstream of chain-facing signals. Validators judge submitted algorithms
off chain, translate round performance into weight signals, and those signals become the input
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus) reads on netuid 1
([Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism)).

For readers, competition rank vocabulary and validator evaluation vocabulary answer how Apex judges
work, while consensus vocabulary answers how those judgments become emissions.

## Yuma Scoring Pipeline

Apex competition scoring feeds the same subnet consensus path as other Bittensor subnets. Validators
evaluate miner submissions, submit
[validator weights](https://docs.learnbittensor.org/resources/glossary#validator-weights), and
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus) aggregates those signals into
miner incentives and validator dividends on netuid 1
([Emission](https://docs.learnbittensor.org/learn/emissions)).

The useful pipeline order is therefore competition submission, off-chain benchmark scoring, weight
submission, and Yuma aggregation at the tempo boundary. Apex scoring sits upstream of that consensus
layer rather than replacing it
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

Competition rank vocabulary and consensus reward vocabulary answer different questions. A high round
score explains validator preference; Yuma explains how those preferences become emission shares.

## Development Stage Context

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. For Subnet 1 Apex
on netuid 1, that sequence changes how readers should interpret competition examples, on-chain
identity fields, and scoring outcomes.

In localnet, Apex-compatible miners and validators can be developed in an isolated environment.
Localnet competition scores and owner-key examples on netuid 1 reflect local chain state and local
configuration rather than production Bittensor behavior.

On testnet, Apex submission and validator scoring workflows can be exercised in a shared,
non-production network. Testnet competition ranks and weight signals on netuid 1 are separate from
mainnet subnet state
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

On mainnet, Subnet 1 Apex is the live production subnet where miners submit competition algorithms
and validators score them to determine real Bittensor emissions on netuid 1.

The [Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet. An Apex example from one environment should not be read as
representing production subnet behavior in another environment.

## On-Chain Identity Examples Stay Environment-Bound

Observed owner keys, neuron counts, and repository links belong to the network context where they
were queried. Bittensor documentation separates mainnet, testnet, and localnet, so Apex examples
from one environment should not be treated as evidence in another
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks),
[Introduction to Bittensor: Subnet development](https://docs.learnbittensor.org/learn/introduction#subnet-development)).

## Reader Boundary

Subnet 1 Apex should not be read as generic Bittensor subnet documentation, a guarantee of current
competition results, or proof that every subnet behaves like Apex. It names one mainnet subnet's
competition-based incentive context on netuid 1
