# Subnet 1: Apex

Apex is Bittensor's first subnet (netuid 1), operated by [Macrocosmos](https://macrocosmos.ai). Its
incentive mechanism runs open competitions where miners submit Python-based algorithms and
validators continuously score those submissions against benchmarks. Rewards flow to miners whose
solutions perform best, creating a permissionless environment for algorithmic and agentic
optimization research.

## How the Mechanism Works

The [Apex overview](https://docs.macrocosmos.ai/subnets/subnet-1-apex) describes the subnet around
three layers:

- **Competition:** A defined problem domain with scoring criteria. Multiple competitions can run
  simultaneously on the subnet.
- **Round:** A discrete evaluation cycle within a competition. Submissions are scored each round,
  and cumulative performance across rounds determines a miner's rank.
- **Submission:** A Python algorithm a miner contributes for evaluation. Validators pull the latest
  submission from each miner and score it against the competition's benchmark.

Validators run continuously and score active miner submissions. Scores feed into
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus), which translates them into
per-round emissions. Miners with consistently high-performing submissions earn the larger share.

## Competition Context

Apex runs rotating benchmark competitions across domains such as simulated distributed training,
market optimization, and reinforcement-learning game environments. The active competition set
changes over time, so readers should treat the competition list as documentation-maintained context
rather than fixed protocol vocabulary
([Apex overview](https://docs.macrocosmos.ai/subnets/subnet-1-apex)). The live competition registry
is maintained on the
[Macrocosmos current competitions page](https://docs.macrocosmos.ai/subnets/subnet-1-apex/subnet-1-current-competitions).

## Miner and Validator Roles

Subnet 1 operates under the standard Bittensor two-role structure. Miners supply algorithmic
submissions for the active competition, and validators evaluate those contributions against each
competition's benchmark before setting weights
([Apex overview](https://docs.macrocosmos.ai/subnets/subnet-1-apex),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

Validators run the subnet's scoring logic locally, submit the resulting weights on-chain, and
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus) aggregates those signals into
emissions. Operational setup details belong in the
[Subnet 1 base miner setup guide](https://docs.macrocosmos.ai/subnets/new-subnet-1-apex/subnet-1-base-miner-setup)
and [macrocosm-os/apex](https://github.com/macrocosm-os/apex) repository rather than in Taopedia
concept vocabulary.

## On-Chain Identity

Subnet 1 is registered at netuid 1 with 256 neurons. Live identity fields, owner keys, and
repository links are available on [TaoStats](https://taostats.io/subnets/1) and in the
[macrocosm-os/apex](https://github.com/macrocosm-os/apex) repository
([Apex overview](https://docs.macrocosmos.ai/subnets/subnet-1-apex)).

## On-Chain Identity Examples Stay Environment-Bound

Observed owner keys, neuron counts, and repository links belong to the network context where they
were queried. Bittensor documentation separates mainnet, testnet, and localnet, so Apex examples
from one environment should not be treated as evidence in another
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks),
[Introduction to Bittensor: Subnet development](https://docs.learnbittensor.org/learn/introduction#subnet-development)).

## Development Stage Context

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. For Subnet 1 Apex,
this sequence gives readers a boundary for interpreting subnet examples and network-context notes.

Localnet examples are isolated and reflect local chain state, so they are useful for controlled
experiments rather than evidence of live Bittensor behavior. Testnet examples add shared
non-production conditions, which can reveal integration behavior without touching mainnet state.

On mainnet, Subnet 1 Apex examples should be read as live production subnet behavior on the
production Bittensor network.

The [Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet, so outcomes from one environment should not be treated as
proof of behavior in another.

## Distinction from Yuma Consensus

Apex on netuid 1 is a competition-based subnet where miners submit Python algorithms and validators
continuously score those submissions against rotating benchmark tasks
([Apex overview](https://docs.macrocosmos.ai/subnets/subnet-1-apex)). That competition-scoring
vocabulary names how Apex ranks miner performance on netuid 1, not the on-chain step that turns
validator weight submissions into emission shares each tempo
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

Subnet participation still ends in validator weight signals that Yuma Consensus aggregates inside
the subnet before emissions are allocated. Apex competition scoring therefore sits upstream of that
consensus layer rather than replacing it
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Emission](https://docs.learnbittensor.org/learn/emissions)).

For readers, competition rank vocabulary and consensus reward vocabulary answer different questions:
Apex names benchmark competition outcomes, while Yuma names how included validator weights become
miner incentives and validator dividends each tempo
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

- **Subnet 1 (Apex)** — competition-scored benchmark subnet.
- **Yuma Consensus** — epoch-boundary settlement from validator weights to emission shares on a task
  subnet
  ([Yuma Consensus: Validator emissions](https://docs.learnbittensor.org/learn/yuma-consensus#validator-emissions)).

## Reader Boundary

Subnet 1 Apex should not be read as generic Bittensor subnet documentation, a guarantee of current
competition results, or proof that every subnet behaves like Apex. It names one mainnet subnet's
competition-based incentive context
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).
