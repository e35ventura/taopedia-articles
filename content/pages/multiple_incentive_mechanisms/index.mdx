# Multiple Incentive Mechanisms

Multiple incentive mechanisms let a Bittensor subnet distribute its emissions across more than one
independent evaluation system inside the same subnet. The official glossary defines the feature as a
way for subnets to implement multiple independent evaluation systems, each with its own bond pool
for Yuma Consensus calculations, so subnet creators can distribute emissions across different types
of work or evaluation criteria.

References:
[Glossary: Multiple Incentive Mechanisms](https://docs.learnbittensor.org/resources/glossary#multiple-incentive-mechanisms),
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets)

## Subnet Context

A Bittensor subnet is already a market where miners produce work and validators evaluate it.
Multiple incentive mechanisms extend that market so one subnet can reward more than one kind of task
without registering a separate subnet. The official documentation describes this as transparent,
on-chain control over how subnet emissions are divided among evaluation paths.

Reference:
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets)

## What Stays Shared

Miners, validators, and stakers still participate through one subnet registration. The same
validators evaluate across mechanisms with the same stake weight, and the subnet's total emissions
do not increase. Multiple mechanisms only change how those emissions are divided internally among
evaluation paths.

Reference:
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets)

## What Stays Separate

Each incentive mechanism keeps its own bond pools, weight matrix, and incentive accounting. A
miner's performance in one mechanism does not change their rating in another, and a miner's total
emissions for an epoch are the sum across the mechanisms where they participate. Validators evaluate
miners separately for each mechanism according to that mechanism's criteria.

References:
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets),
[Glossary: Multiple Incentive Mechanisms](https://docs.learnbittensor.org/resources/glossary#multiple-incentive-mechanisms)

## Why It Matters

Multiple incentive mechanisms give subnet creators a way to focus miner effort on more than one kind
of valuable work inside a single competitive market. The official documentation frames this as a
design choice for subnets that need parallel evaluation paths while keeping one shared participant
set. Readers should treat the feature as subnet-design context, not as a universal reward upgrade.

References:
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets),
[Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism)

## Example on netuid 109

Subnet 109, Academia, is a documented example of multiple incentive mechanisms in live use. The
[Academia README](https://raw.githubusercontent.com/fx-integral/academia/main/README.md) describes
separate research-and-design and prototype-and-arena tracks inside one subnet, with emissions
flowing according to measured performance in each track. Live SN109 subnet data is available on
[TaoStats](https://taostats.io/subnets/109).

References:
[Academia README](https://raw.githubusercontent.com/fx-integral/academia/main/README.md),
[Subnet 109 on TaoStats](https://taostats.io/subnets/109),
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets)

## Reader Boundary

This page defines the term at a high level. It does not report current mechanism counts, emission
splits, evaluation rules, subnet membership, or live chain settings for any netuid. Those values
change with protocol and subnet state and should be checked in current official documentation and
chain references when operational detail is needed.
