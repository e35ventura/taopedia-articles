# Multiple Incentive Mechanisms

Multiple incentive mechanisms let a Bittensor subnet evaluate more than one kind of miner work
inside the same subnet. Instead of treating one score as the whole subnet result, the subnet can
separate evaluation paths so different tasks, metrics, or reward streams can be judged on their own
terms before rewards are combined.

References:
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets),
[Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism)

## Why multiple mechanisms exist

A single subnet can need more than one useful work signal. One mechanism might reward accuracy,
another might reward speed, and another might reward a different task family. Keeping those signals
separate helps the subnet avoid collapsing unlike work into one score before validators have judged
each work stream.

References:
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets),
[Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism),
[[subnet_creation_mechanisms|Subnet Creation and Incentive Mechanisms]]

## Independent evaluation paths

Each mechanism has its own validator weight path and its own miner incentive result. A miner's
result in one mechanism is not meant to erase or redefine the result from another mechanism. This
keeps evaluation local to the task being measured while still letting the subnet combine outcomes
into a total reward result.

References:
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)

## Reward allocation inside the subnet

Multiple mechanisms do not create a separate subnet for every task. They divide the subnet's
internal reward allocation across mechanism-specific results. This means a miner can be strong in
one work stream and weaker in another, while the final result depends on both the mechanism's reward
share and the miner's relative performance within that mechanism.

References:
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets),
[Emission](https://docs.learnbittensor.org/learn/emissions), [[dynamic_tao|Dynamic TAO]]

## Consensus context

The subnet still needs consensus over validator-submitted signals. Multiple mechanisms add more than
one evaluation matrix, but the broader reason for [[yuma_consensus|Yuma Consensus]] remains the
same: combine validator judgments into reward outcomes while accounting for validator stake and bond
behavior.

References: [Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets),
[Exponential Moving Averages](https://docs.learnbittensor.org/learn/ema)

## Design tradeoffs

More mechanisms can make a subnet more expressive, but they also raise the burden on mechanism
design. Validators need clear criteria for each work stream, miners need to understand which work is
being rewarded, and the reward split needs to match the subnet's actual goals. A poor split can
overreward an easy task or underreward the signal the subnet most needs.

References:
[Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism),
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets),
[[mining_and_validating|Mining and Validating]]

## How to read mechanism claims

A claim about multiple mechanisms should make clear whether it is describing the concept, a subnet's
evaluation design, or the way rewards are split among mechanisms. The stable idea is that different
mechanism paths can evaluate different work inside one subnet. Exact reward shares, task
definitions, and validator scoring rules belong next to the source that defines that subnet's
mechanism.
