# Max Tempo

Max tempo is a subtensorModule runtime constant, listed in the chain's constants metadata as
maxTempo, with the value 50400 and the summary "Upper bound for owner-set tempo"
([Subtensor API Constants: maxTempo](https://docs.learnbittensor.org/subtensor-api/constants#maxtempo-u16)).
It defines the largest tempo a subnet owner is allowed to configure for a subnet.

## What It Means

Tempo is the number of blocks between Yuma Consensus epoch transitions for a subnet
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)). Max
tempo does not set that value; it caps how large an owner may set it. The constant works together
with minTempo, whose value is 360 and whose summary is "Lower bound for owner-set tempo"
([Subtensor API Constants: minTempo](https://docs.learnbittensor.org/subtensor-api/constants#mintempo-u16)).
Together the two constants bound the owner-settable tempo to the range 360 through 50400 blocks.

## Owner Setting Versus Root Setting

The bound applies to the owner path. When a subnet owner changes tempo, the value is required to
fall within the minTempo–maxTempo range; a root-level tempo change is not held to these bounds and
may set any value
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)). For
example, a subnet owner configuring tempo on a subnet such as netuid 1 must choose a value inside
the 360–50400 band, whereas a root-level change on the same subnet is not constrained by it. Max
tempo is therefore a guard on owner configuration rather than a hard limit on every tempo the chain
can hold.

## Wall-Clock Meaning

Because tempo counts blocks, the effective duration depends on block time. The chain's slotDuration
constant is 12000 milliseconds, or twelve seconds per block
([Subtensor API Constants: slotDuration](https://docs.learnbittensor.org/subtensor-api/constants#slotduration-u64)).
At that rate the maximum owner tempo of 50400 blocks is about seven days, while the minimum of 360
blocks is about seventy-two minutes. Max tempo thus sets the longest epoch cadence a subnet owner
can choose for a subnet.

## Distinction from Tempo

Max tempo and tempo are different kinds of value. Tempo is the per-subnet hyperparameter a subnet
carries and applies at each epoch boundary, while max tempo is a fixed network-wide runtime constant
that only bounds what an owner may set that hyperparameter to
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Subtensor API Constants: maxTempo](https://docs.learnbittensor.org/subtensor-api/constants#maxtempo-u16)).
One is the ceiling; the other is the chosen value that must sit under it on the owner path.

## Distinction from Min Tempo

Max tempo and min tempo are the two ends of the same owner-settable band. Min tempo, valued at 360,
is the smallest tempo an owner may set, and max tempo, valued at 50400, is the largest
([Subtensor API Constants: minTempo](https://docs.learnbittensor.org/subtensor-api/constants#mintempo-u16),
[Subtensor API Constants: maxTempo](https://docs.learnbittensor.org/subtensor-api/constants#maxtempo-u16)).
A smaller tempo means shorter, more frequent epochs; a larger tempo means longer, less frequent
epochs. The two bounds keep an owner's chosen cadence inside a documented range rather than allowing
either extreme.

## Reader Boundary

Max tempo is a single network-wide constant, not a per-subnet value, and it reflects the current
runtime configuration rather than a fixed protocol rule; the bound could change in a future runtime
upgrade. It is not the live tempo of any subnet, and it does not by itself describe how emissions
are distributed at the epoch boundary
([Subtensor API Constants: maxTempo](https://docs.learnbittensor.org/subtensor-api/constants#maxtempo-u16)).
