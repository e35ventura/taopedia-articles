# Mempool

The Bittensor mempool is the pending-transaction holding area before block inclusion. It names the
state where unconfirmed transactions wait before they become part of a block
([Glossary: Mempool](https://docs.learnbittensor.org/resources/glossary#mempool),
[Glossary: Block](https://docs.learnbittensor.org/resources/glossary#block)).

The useful distinction is pending versus included. A mempool entry is not yet final chain history; a
block is the unit that records included transactions.

## Pending Transaction Context

Mempool vocabulary belongs to the interval after a transaction enters the pending area and before
block inclusion. During that interval, the transaction is waiting to be processed into chain history
([Glossary: Mempool](https://docs.learnbittensor.org/resources/glossary#mempool),
[Glossary: Block](https://docs.learnbittensor.org/resources/glossary#block)).

This makes the mempool a timing and state concept rather than a reward mechanism. It explains where
pending transactions sit, not whether an action will ultimately succeed.

## Submission Versus Inclusion

Submitting an extrinsic and seeing final chain history are separate moments. The Subtensor
extrinsics reference describes extrinsics as calls submitted to the chain, while the glossary
defines the mempool as the waiting area for transactions before block inclusion
([Subtensor extrinsics](https://docs.learnbittensor.org/subtensor-api/extrinsics),
[Glossary: Mempool](https://docs.learnbittensor.org/resources/glossary#mempool)).

For readers, that means a submitted action should not be treated as recorded just because it has
entered the pending stage. The stronger claim starts after inclusion in a block, when the
transaction belongs to chain history rather than the mempool.

## Block Boundary

Blocks are the chain units that contain transactions. The mempool is the waiting area before that
inclusion happens ([Glossary: Block](https://docs.learnbittensor.org/resources/glossary#block),
[Glossary: Mempool](https://docs.learnbittensor.org/resources/glossary#mempool)).

Once a transaction is included in a block, it should be treated as block history rather than a
merely pending mempool entry.

## Extrinsic Boundary

Extrinsics are runtime actions. In Bittensor context, an accepted extrinsic can pass through the
pending-transaction stage before block inclusion
([Subtensor extrinsics](https://docs.learnbittensor.org/subtensor-api/extrinsics),
[Glossary: Mempool](https://docs.learnbittensor.org/resources/glossary#mempool)).

This keeps the concepts separate. Extrinsic names the action surface; mempool names the pending
state before inclusion.

## Fee Boundary

Some state-changing actions carry transaction fees. The fee model belongs to the action being
processed, while the mempool names the pending area where unconfirmed transactions wait
([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees),
[Glossary: Mempool](https://docs.learnbittensor.org/resources/glossary#mempool)).

The mempool does not set fee rules. It sits before the block-processing stage where the chain
evaluates the action.

## Visibility Context

Pending transactions can create an information-exposure window before block inclusion. MEV Shield
documentation treats sensitive pending details as something that can be protected before processing
([MEV Shield](https://docs.learnbittensor.org/concepts/mev-shield/),
[Glossary: Mempool](https://docs.learnbittensor.org/resources/glossary#mempool)).

That makes mempool vocabulary important to safety articles, but the mempool itself is not the same
thing as MEV Shield or any other protection mechanism.

## Network Boundary

Bittensor network vocabulary separates mainnet, testnet, and localnet contexts
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

A mempool example from one environment should not be treated as proof about another environment. The
same mempool concept can apply across environments, but each environment has its own pending
transaction context.

## What Mempool Does Not Mean

Mempool does not name a transaction tutorial, monitoring guide, source for final chain status, or
guarantee that a pending transaction will be included
([Glossary: Mempool](https://docs.learnbittensor.org/resources/glossary#mempool),
[Subtensor extrinsics](https://docs.learnbittensor.org/subtensor-api/extrinsics)).

Keeping that boundary preserves the term's narrower meaning. Mempool identifies pending transaction
state before block inclusion, while block records, extrinsics, fees, MEV Shield, and network context
describe neighboring parts of the system.

## All Participants Can Observe Pending Entries

The official [Glossary: Mempool](https://docs.learnbittensor.org/resources/glossary#mempool) states
that when a transaction is submitted, it first enters the mempool and becomes visible to all network
participants. That wording names a shared observation surface rather than a private staging area
tied to one wallet, node, or interface.

Pending and unconfirmed both appear in the same glossary definition, which reinforces that the
waiting period is open to network-wide inspection before
[block](https://docs.learnbittensor.org/resources/glossary#block) inclusion. A mempool entry
therefore describes a transaction that others can observe while it is still outside chain history.

That visibility scope is separate from whether the action will succeed, fail, or later pay a fee.
Observation during the wait does not by itself prove final outcome; it only shows that the
transaction is still in the pending area.

References: [Glossary: Mempool](https://docs.learnbittensor.org/resources/glossary#mempool),
[Glossary: Block](https://docs.learnbittensor.org/resources/glossary#block)

## MEV Profit Depends on Pre-Inclusion Knowledge

The
[Glossary: MEV (Maximal Extractable Value)](https://docs.learnbittensor.org/resources/glossary#mev-maximal-extractable-value)
defines MEV as profit that can be extracted by reordering, inserting, or censoring transactions
within a block. The same entry lists front-running, sandwich attacks, and back-running as common
patterns that depend on seeing or anticipating pending activity.

Official glossary guidance adds a Bittensor-specific boundary: MEV attacks can affect
[staking](https://docs.learnbittensor.org/resources/glossary#staking) and
[unstaking](https://docs.learnbittensor.org/resources/glossary#unstaking) operations when attackers
exploit knowledge of pending transactions.
[Price Protection](https://docs.learnbittensor.org/learn/price-protection) documentation reinforces
that picture by noting that other users' transactions can shift subnet pool conditions even while a
user's own action is still pending, and it names sandwich attacks among the risks around real-value
liquidity moves.

Mempool vocabulary marks the pre-inclusion stage where that foreknowledge can matter. It names the
waiting context, not the attack pattern itself or any single defense choice.

References:
[Glossary: MEV (Maximal Extractable Value)](https://docs.learnbittensor.org/resources/glossary#mev-maximal-extractable-value),
[Price Protection](https://docs.learnbittensor.org/learn/price-protection)

## Runtime Events Start After Pending Resolution

[Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events) documentation states that
runtime events are emitted only for successful calls and that failed calls roll back storage
changes, including events. That places event evidence on the post-processing side of the mempool
boundary rather than in the pending waiting area.

A transaction that is still waiting before block inclusion has not yet produced that event record.
Mempool vocabulary describes the interval before chain history absorbs the action; events describe
recorded outcomes after a successful inclusion and execution path on chain.

The inspecting-the-chain guide lists events alongside blocks and storage as read-oriented surfaces
for observing public chain activity
([Inspecting the Chain with Polkadot.js](https://docs.learnbittensor.org/concepts/inspecting-the-chain)).
Those surfaces answer what the chain later recorded, while mempool vocabulary answers where a
transaction sits before that recording step.

References: [Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events),
[Inspecting the Chain with Polkadot.js](https://docs.learnbittensor.org/concepts/inspecting-the-chain)
