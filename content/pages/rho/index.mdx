# Rho

Rho is a Yuma Consensus hyperparameter, listed in Bittensor documentation as `Rho`, that controls
how strongly validator bond relationships are normalized during each consensus epoch. The
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters) reference
lists `Rho` as a bonding-related hyperparameter alongside `Kappa`, the trust ratio threshold that
governs which validators participate in the bonding update path
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

The term belongs to the validator-bond layer of Yuma Consensus. It does not name a stake amount, a
weight signal, or a miner-side result. It names the normalization constant that shapes how bond
relationships between validators are updated as each subnet epoch runs.

## What It Controls

Rho governs the normalization applied when updating inter-validator bonds inside the Yuma Consensus
process. The normalization role prevents runaway bond behavior: without a normalization constant, a
single epoch's weight pattern could cause bond relationships to diverge rapidly. Rho limits that
divergence by controlling the update scale each round on netuid 1 and other active subnets
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

Bond updates in Yuma Consensus depend on how validators rate miners relative to each other. Rho sits
inside that update path as the normalization constant, not as a weight input or a miner-side output
rank value.

The parameter belongs to the bonding step of the Yuma algorithm rather than to the weight-setting or
rank-output steps. Validators set weights before bonding runs; rho applies during the bonding update
calculation that runs inside each epoch.

## Relation to Kappa

Kappa and rho are both Yuma Consensus hyperparameters in the bonding layer, and both appear in the
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters) reference
alongside each other. Kappa sets the trust ratio threshold that controls which validator-to-miner
weight relationships enter the bonding update; rho controls the normalization strength applied when
those bond relationships are updated
([Glossary: Kappa](https://docs.learnbittensor.org/resources/glossary#kappa)).

The two parameters operate on different parts of the bonding path. Kappa determines which
relationships enter the bonded set; rho shapes how strongly those updates are applied in each
consensus round.

A subnet owner can configure both parameters per subnet. Changing rho without changing kappa adjusts
the bond update strength for validators already inside the bonded set on netuid 1. Changing kappa
shifts which validators enter that set in the first place.

## Documented Type and Setter

The [Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)
reference lists `Rho` among the Yuma Consensus hyperparameters that subnet owners can configure.
Each subnet carries its own hyperparameter state, so the rho value for one subnet can differ from
the rho value on another subnet.

The active value for a selected netuid is the per-subnet chain state for that subnet. A rho reading
from netuid 1 belongs to that subnet's Yuma Consensus configuration and should not be assumed to
apply to any other subnet.

## Consensus-Based Weights Context

Consensus-based weights, also known as liquid alpha, depend on how bond relationships develop over
repeated consensus rounds
([Consensus-based Weights](https://docs.learnbittensor.org/concepts/consensus-based-weights)). Rho
affects how quickly or slowly those bond relationships shift between rounds by controlling the
normalization applied at each update step.

That connection places rho inside the longer-running bond-behavior picture. Rho shapes one bonding
update step; consensus-based weights describe how alignment patterns compound across many steps on
the same subnet ([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

## Network and Environment Scope

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. Rho applies across
that lifecycle: subnet owners can set it in isolated localnet development, shared testnet
environments, and live mainnet subnets.

The [Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet environments. A rho value observed on one environment
should not be treated as evidence for the bonding normalization behavior on another environment,
because each network's subnet state is independent.

On mainnet, rho is the live per-subnet chain parameter that shapes production Yuma Consensus bonding
behavior for the selected netuid.

## Evidence Boundary

Rho is a bonding normalization constant in Yuma Consensus. It does not name a validator's current
bond level, a miner's rank, or a trust outcome. Those are result terms inside the consensus process;
rho is an input hyperparameter that shapes how bond updates proceed each epoch
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

A precise claim about rho should identify the relevant subnet and its current hyperparameter
configuration. The rho value in force for netuid 1 is that subnet's own chain state and should not
be used as a proxy for rho on other subnets.
