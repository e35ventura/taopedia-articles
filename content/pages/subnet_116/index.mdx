## Understanding Subnet Information Sources

Bittensor subnet information comes from multiple sources, including on-chain metadata, public
documentation, repositories, and community channels. The on-chain identity record provides the
officially registered information attached to a subnet
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)), while
external resources may provide additional technical details such as architecture, miner
requirements, validator scoring methods, and development progress.

When documenting a subnet, publicly verifiable sources are prioritized. If certain information is
not available from official records or linked resources, the article only describes confirmed
network-level behavior rather than assuming unpublished mechanisms
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

## Miner and Validator Roles

Subnet 116 operates under the standard Bittensor two-role structure. Miners supply a capability to
the network, and validators evaluate those contributions and set weights. Those weights feed into
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus), whose consensus weights then
help determine per-tempo [emissions](https://docs.learnbittensor.org/learn/emissions) for the
strongest performers.

Without a registered repository or public README linked on chain, this article cannot state what
capability miners supply or how validators score it beyond that standard weight flow
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

## Development Stage Context

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. For Subnet 116,
that sequence applies to the standard Bittensor lifecycle: localnet for isolated development,
testnet for shared non-production testing, and mainnet for live operation with real emissions.

On mainnet, Subnet 116 is registered as the live production subnet at netuid 116. The
[Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet. Participation examples or emission outcomes from one
environment should not be read as representing production subnet performance in another environment.

## Distinction from Yuma Consensus

Subnet 116 is an unnamed netuid slot with no registered on-chain identity fields. Yuma Consensus is
the separate mechanism that converts validator weight submissions into emission shares each tempo
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Emission](https://docs.learnbittensor.org/learn/emissions)).

- **Subnet 116** — netuid slot without registered project identity.
- **Yuma Consensus** — mechanism that turns validator weights into emission shares.
