# Subtensor API

The Subtensor API is an optional interface in the Bittensor Python SDK that groups blockchain
operations into functional modules.

The official guide refers to the interface as `SubtensorAPI`, while the current SDK implementation
exposes the Python class as `SubtensorApi`. The naming difference does not identify a separate
protocol. `SubtensorApi` is a client-side interface used by applications to interact with
[[Subtensor]], Bittensor's blockchain layer.

Sources: [Subtensor API](https://docs.learnbittensor.org/sdk/subtensor-api),
[current SDK implementation](https://github.com/latent-to/bittensor/blob/master/bittensor/extras/subtensor_api/__init__.py)

## Unified Client Interface

By default, `SubtensorApi` wraps the synchronous `Subtensor` client. When asynchronous mode is
enabled, it wraps `AsyncSubtensor`.

This gives applications one organized entry point while preserving the execution model of the
underlying client. Asynchronous operations still require asynchronous calling and context-management
patterns. Selecting asynchronous mode does not make ordinary synchronous code concurrent
automatically.

Sources: [Subtensor API](https://docs.learnbittensor.org/sdk/subtensor-api),
[current SDK implementation](https://github.com/latent-to/bittensor/blob/master/bittensor/extras/subtensor_api/__init__.py)

## Module Organization

The interface groups related methods behind module properties instead of exposing every operation
through one flat method list.

The current implementation includes modules for:

- chain interaction;
- commitments and reveals;
- crowdloans;
- delegates;
- extrinsics;
- metagraphs;
- MEV Shield;
- neurons;
- proxies;
- queries;
- staking;
- subnets;
- wallets.

These modules organize SDK methods for discoverability. They do not create new runtime pallets,
consensus rules, blockchain services, or subnet mechanisms.

Sources: [Subtensor API](https://docs.learnbittensor.org/sdk/subtensor-api),
[Subtensor API source directory](https://github.com/latent-to/bittensor/tree/master/bittensor/extras/subtensor_api)

## Import Location and Compatibility

In Bittensor SDK v10, `SubtensorApi` is provided through the optional
`bittensor.extras.subtensor_api` package. The SDK also provides a top-level convenience import for
the class.

The `legacy_methods` setting can add methods from the traditional `Subtensor` interface to the root
level of `SubtensorApi`. This supports applications that depend on the older method-access pattern
while allowing newer code to use the grouped module structure.

Compatibility mode changes how client code reaches SDK methods. It does not change the corresponding
runtime rules or chain state.

Sources: [Bittensor SDK v10 Migration Guide](https://docs.learnbittensor.org/sdk/migration-guide),
[current SDK implementation](https://github.com/latent-to/bittensor/blob/master/bittensor/extras/subtensor_api/__init__.py)

## Endpoint Configuration

`SubtensorApi` accepts configuration for the selected network, fallback endpoints, archive
endpoints, connection retries, verbose logging, mock operation, and asynchronous websocket shutdown
behavior.

Fallback endpoints provide alternative connections when the primary endpoint is unavailable. Archive
endpoints can be used when an application requests historical blocks that are no longer available
from the current node.

These are client connection settings. They do not guarantee that an endpoint is available, that
submitted extrinsics will succeed, or that returned information belongs to a different network than
the endpoint being queried.

Sources: [Subtensor API](https://docs.learnbittensor.org/sdk/subtensor-api),
[current SDK implementation](https://github.com/latent-to/bittensor/blob/master/bittensor/extras/subtensor_api/__init__.py)

## Context Management

The interface supports context management for both client modes.

A synchronous instance can be used with a synchronous context manager, while an asynchronous
instance can be used with an asynchronous context manager. Mixing the synchronous instance with an
asynchronous context manager, or the asynchronous instance with a synchronous context manager, is
not supported.

Context management matters because each underlying Subtensor client maintains a blockchain
connection that should be closed when it is no longer needed.

Sources:
[Managing Subtensor Connections](https://docs.learnbittensor.org/sdk/managing-subtensor-connections),
[current SDK implementation](https://github.com/latent-to/bittensor/blob/master/bittensor/extras/subtensor_api/__init__.py)

## Relationship to Bittensor Tools

`SubtensorApi` belongs to the developer-library side of [[Bittensor Tools]].

The distinction is:

- [[Subtensor]] is the blockchain layer being accessed;
- `SubtensorApi` is a Python SDK access interface;
- its modules organize related client operations;
- [[Extrinsics]] are submitted chain actions available through parts of that interface;
- command-line and wallet interfaces provide different ways to interact with the same broader
  ecosystem.

A client interface can expose protocol operations without becoming the protocol rule that validates
those operations.

## Reader Boundary

This article explains the purpose and structure of `SubtensorApi`. It is not a complete method
reference or a substitute for the current SDK documentation.

Exact method signatures, available module properties, connection parameters, and import paths can
change between SDK releases. Applications should use documentation matching their installed SDK
version and verify implementation-specific behavior against the current source.
