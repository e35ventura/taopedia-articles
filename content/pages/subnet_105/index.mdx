Beam is Bittensor Subnet 105. The live Finney identity lists its subnet name as Beam, its GitHub
source as the Beam-Network organization repositories page, its subnet URL as https://b1m.ai, and its
description as "Decentralized bandwidth. A global network. Powering the open internet."

The Beam README describes the project as an open coordination layer for bandwidth and
machine-to-machine data transfer. It says Beam aggregates distributed bandwidth, coordinates data
transfers across participants, and uses Proof-of-Bandwidth to measure delivery performance during
transfers.

## What Beam Provides

Beam provides a coordination layer for moving data between sources and destinations. The README
describes transfer patterns that include one-to-one movement, fan-out from one source to multiple
destinations, aggregation from multiple sources, and mesh-style transfers.

BeamCore is the coordination stack behind this workflow. The public BeamCore transparency README
identifies reference code for transfer assignment and PRISM scoring, including orchestrator
selection, chunk allocation, stale reassignment, score computation, and scheduled metrics refresh.

## Transfer Lifecycle Context

The [Beam README source](https://raw.githubusercontent.com/Beam-Network/beam/main/README.md)
separates BeamCore coordination from the actual data path. BeamCore manages the HTTP API,
orchestrator gateway, transfer lifecycle, payment evidence, and PRISM scoring services, but object
bytes do not pass through BeamCore. Workers receive task-scoped source and destination URLs for the
chunks assigned to them, so the bandwidth work happens between the storage endpoints involved in a
task.

That boundary is useful when reading Beam as a subnet. Beam is not only measuring whether a miner is
online or publishing a claimed capacity number. Its workflow is organized around assigned transfer
work, chunk execution, and evidence returned from workers after the work is attempted. The transfer
patterns listed in the README explain why this can cover more than a single sender and receiver:
tasks may move data one-to-one, fan out from one source, aggregate from multiple sources, or use a
mesh-style pattern.

This also clarifies the role of the orchestrator. In Beam's participant model, an orchestrator
maintains the connection to BeamCore, advertises a worker gateway, routes task offers to workers,
and reports worker decisions and results. The worker gateway and worker processes are the execution
side of the subnet, while BeamCore supplies the coordination and scoring context that validators
later consume.

[Beam participant README](https://raw.githubusercontent.com/Beam-Network/beam/main/README.md)

## Proof and Weight Context

The
[BeamCore transparency README](https://raw.githubusercontent.com/Beam-Network/beam-core-public/main/README.md)
identifies public reference code for transfer assignment and PRISM scoring. Its assignment files
cover orchestrator selection, chunk allocation, and stale reassignment, while its PRISM files cover
score computation and scheduled metric refresh.

Beam's validator path is described as reading BeamCore epoch summaries, setting subnet weights, and
posting weight proofs. The practical result is a two-step evidence chain: workers produce
Proof-of-Bandwidth evidence for assigned transfer work, and validators use BeamCore and PRISM
outputs to decide how miners should be weighted.

For readers comparing Beam with other subnets, the important distinction is that the evaluated
signal is tied to completed transfer work and scored performance evidence, not merely to a static
bandwidth claim. On-chain weights remain the Bittensor-facing output, but the Beam-specific evidence
comes from the off-chain transfer lifecycle and PRISM scoring path.

References:
[Beam README source](https://raw.githubusercontent.com/Beam-Network/beam/main/README.md),
[BeamCore transparency README source](https://raw.githubusercontent.com/Beam-Network/beam-core-public/main/README.md)

## Miner and Validator Roles

Beam's public materials describe miners as orchestrators and workers. Orchestrators coordinate
bandwidth work through BeamCore, while workers move data directly between source and destination
connectors and submit Proof-of-Bandwidth evidence.

Validators read BeamCore scores and PRISM inputs and set weights on Bittensor. This maps Beam's
bandwidth-transfer workflow onto the broader [[Mining and Validating]] pattern, with validator
weights ultimately flowing through [[Yuma Consensus]].

## On-Chain Identity

Readers can reproduce the live identity fields with the Bittensor CLI command documented in the
[btcli reference](https://docs.learnbittensor.org/btcli/#btcli-subnets-get-identity):
`btcli subnets get-identity --netuid 105 --network finney`.

That Finney identity reports the subnet name as Beam, the GitHub source as the Beam-Network
repositories page, the subnet URL as https://b1m.ai, and the description "Decentralized bandwidth. A
global network. Powering the open internet."
