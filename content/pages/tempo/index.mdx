# Tempo

A tempo is a block-based timing interval used by Bittensor subnets. Rewards accumulate during a
tempo and are distributed at the interval boundary through
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)
([Emission](https://docs.learnbittensor.org/learn/emissions)).

As a subnet hyperparameter, `tempo` gives subnet processes a cadence measured in blocks. It is a
timing concept rather than a definition of what useful subnet work means
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## What It Represents

Tempo names how many blocks make up one consensus epoch on a selected subnet. The stable concept is
block-based cadence; live values belong to that subnet's hyperparameter table rather than to every
subnet at once
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Glossary: Tempo](https://docs.learnbittensor.org/resources/glossary#tempo)).

Readers should separate four timing ideas that tempo vocabulary often mixes:

- **Tempo versus epoch** — tempo is the block count for one cycle; epoch names the full window from
  weight submission through boundary settlement
  ([Glossary: Epoch](https://docs.learnbittensor.org/resources/glossary#epoch)).
- **Tempo versus block** — blocks advance continuously; tempo groups them into the interval used for
  periodic distribution
  ([Glossary: Block](https://docs.learnbittensor.org/resources/glossary#block)).
- **Injection versus distribution** — emission injection can run every block, while distribution
  from accumulated alpha waits for the tempo boundary
  ([Emission: Injection and distribution](https://docs.learnbittensor.org/learn/emissions#injection-and-distribution-two-stages-of-the-emissions-process)).
- **Per-subnet anchoring** — epoch boundaries are tracked from each subnet's own last-epoch block,
  so two subnets with the same tempo value can settle on different absolute blocks. See
  [Epoch Scheduling](#epoch-scheduling) below.

Tempo is measured in blocks, not seconds. Fast-block local modes change wall-clock length without
changing the block count
([Glossary: Fast blocks](https://docs.learnbittensor.org/resources/glossary#fast-blocks),
[Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

## Commit Reveal Timing

Commit Reveal uses tempo-based timing for delayed weight visibility. Its reveal period is expressed
in tempos, making tempo relevant to when concealed validator weights become usable
([Commit Reveal](https://docs.learnbittensor.org/concepts/commit-reveal)).

This is a timing relationship, not a new definition of tempo. Tempo remains the block-based cadence;
Commit Reveal uses that cadence as part of delayed weight submission and reveal timing
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## Multiple Mechanisms Scope

When a subnet has multiple incentive mechanisms, tempo still names the shared subnet cadence. The
mechanisms can have separate weight and consensus paths, but that does not require treating tempo as
a separate schedule for each mechanism
([Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets)).

Multiple mechanisms clarify how evaluation is organized; tempo clarifies when periodic processing
occurs
([Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix)).

## Epoch Scheduling

On chain, the tempo boundary is tracked per subnet from the block of the previous epoch rather than
from a network-wide block formula. The next epoch becomes due once the number of blocks since that
recorded last-epoch block reaches the tempo, so the cadence is a per-subnet period measured from the
prior boundary
([`should_run_epoch`](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/coinbase/run_coinbase.rs)).

This anchoring is the reason two subnets that share the same tempo value can settle on different
blocks: each one counts from its own last-epoch block, not from a shared schedule
([Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch)).

## Development Stage Context

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. For tempo on a
subnet such as netuid 1, that sequence changes how readers should interpret block cadence, epoch
boundaries, and reward timing.

In localnet, tempo behavior can be tested in an isolated environment. Local examples reflect local
block production and subnet parameters rather than production timing.

On testnet, tempo can be observed in a shared, non-production network. Testnet interval boundaries
on a selected netuid are separate from mainnet emission and consensus outcomes
([Glossary: Tempo](https://docs.learnbittensor.org/resources/glossary#tempo)).

On mainnet, tempo is the production block cadence that groups subnet processes into periodic reward
and consensus timing on the connected Bittensor network.

The [Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet. A tempo example from one environment should not be read as
representing block cadence or emission timing in another environment.

## Distinction from Epoch

- **Tempo** — block count for one consensus cycle on a subnet.
- **Epoch** — full window from weight submission through boundary settlement
  ([Glossary: Epoch](https://docs.learnbittensor.org/resources/glossary#epoch),
  [Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch)).

## Distinction from Block

- **Block** — one step of chain progression.
- **Tempo** — number of blocks grouped before the next subnet emission step
  ([Glossary: Block](https://docs.learnbittensor.org/resources/glossary#block)).

## Distinction from Emission

- **Emission** — injection and distribution of TAO and alpha into reward flows.
- **Tempo** — block interval at which accumulated subnet rewards are distributed at the boundary
  ([Emission](https://docs.learnbittensor.org/learn/emissions)).

## Distinction from Yuma Consensus

- **Tempo** — block count per consensus epoch on a subnet.
- **Yuma Consensus** — on-chain settlement that turns validator weights into emission shares at the
  boundary ([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

## Distinction from Weights Rate Limit and Activity Cutoff

These block-count settings are easy to confuse with tempo because all are measured in blocks:

| Term               | What it names                                                               |
| ------------------ | --------------------------------------------------------------------------- |
| Tempo              | Block interval for accumulation and distribution at the boundary            |
| Weights rate limit | Blocks a validator must wait between weight commits                         |
| Activity cutoff    | Early blocks in the epoch when weights must arrive to join the current pass |

([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Subnet Hyperparameters: Activity Cutoff](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutoff)).

Tempo sets how long the epoch lasts. Activity cutoff sets how early a validator must act inside that
epoch. Weights rate limit spaces repeated commits from the same validator.

Commit reveal period is tempo-counted, not block-counted: it names how many full tempos pass before
committed weights reveal ([Commit Reveal](https://docs.learnbittensor.org/concepts/commit-reveal),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## Distinction from Subnet Task

- **Subnet task** — work miners are expected to produce.
- **Tempo** — block cadence that groups periodic subnet processing
  ([Glossary: Subnet Task](https://docs.learnbittensor.org/resources/glossary#subnet-task)).

## Distinction from Delegation Rewards

- **Tempo** — subnet epoch boundary when finalized rewards are distributed.
- **Delegation rewards** — one share credited during that distribution step
  ([Emission](https://docs.learnbittensor.org/learn/emissions)).

## Distinction from Emission Split

- **Tempo** — recurring subnet interval in blocks.
- **Emission split** — role partition applied when that interval ends
  ([Emission](https://docs.learnbittensor.org/learn/emissions)).

## Distinction from Fast Blocks

- **Tempo** — block count per epoch.
- **Fast blocks** — accelerated block production in local development, shortening wall-clock time
  for the same block count
  ([Run a Local Bittensor Blockchain Instance](https://docs.learnbittensor.org/local-build/deploy)).

## Distinction from Rate Limits

- **Tempo** — paces each subnet epoch's consensus and emission in blocks.
- **Rate limits** — space repeated chain actions from the same key
  ([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits)).

## Distinction from Commit Reveal Period

- **Tempo** — block-length cadence of one subnet epoch.
- **Commit reveal period** — count of tempos before a committed weight set is revealed
  ([Commit Reveal](https://docs.learnbittensor.org/concepts/commit-reveal)).

## Distinction from Subnet Weights

- **Subnet weights** — relative cross-subnet share of TAO injection.
- **Tempo** — block interval on which a subnet distributes accumulated rewards
  ([Glossary: Subnet Weights](https://docs.learnbittensor.org/resources/glossary#subnet-weights)).

## Distinction from Alpha Distribution Ratio

- **Alpha distribution ratio** — distribution-versus-injection ratio for subnet alpha.
- **Tempo** — block interval that paces subnet epoch and emission release
  ([Glossary: ADR](https://docs.learnbittensor.org/resources/glossary#adr-alpha-distribution-ratio)).

## Distinction from Bittensor Emissions

- **Bittensor emissions** — newly created TAO and alpha entering reward flows.
- **Tempo** — block interval that paces subnet epoch and distribution
  ([Emission](https://docs.learnbittensor.org/learn/emissions)).

## Distinction from Emission Timing

- **Emission timing** — accumulation-and-distribution rhythm across the protocol flow.
- **Tempo** — block interval that marks when subnet distribution runs.

## Distinction from Coinbase

- **Tempo** — block interval between a subnet's epoch distributions.
- **Coinbase** — per-block routine that mints TAO and advances emission each block regardless of
  tempo
  ([Coinbase documentation](https://docs.learnbittensor.org/navigating-subtensor/emissions-coinbase)).

Readers watching coinbase activity see per-block injection into subnet emission pools; tempo still
marks when Yuma turns accumulated weights into miner and validator payouts at the epoch boundary—not
every coinbase block closes an epoch
([Emission: Injection and distribution](https://docs.learnbittensor.org/learn/emissions#injection-and-distribution-two-stages-of-the-emissions-process)).

## Reader Boundary

Tempo should be read as a block-count cadence for subnet processes. It is not a wall-clock promise,
a subnet quality signal, or a substitute for Yuma Consensus. It tells readers how timing is grouped
for rewards, epochs, and related subnet processes
([Glossary: Tempo](https://docs.learnbittensor.org/resources/glossary#tempo)).

The article-level point is stable even when specific values differ by subnet: tempo is the cadence
that helps turn block progression into periodic subnet consensus and emission timing
([Emission](https://docs.learnbittensor.org/learn/emissions)).
