# Subnet 22: Desearch

Desearch is Bittensor Subnet 22, a subnet for web, X/Twitter, and multi-source search retrieval.
SN22 is presented as the subnet behind Desearch's decentralized real-time intelligence layer,
coordinating miners and validators around search data for Desearch products
([Desearch repository](https://github.com/Desearch-ai/subnet-22),
[Subnet 22 on TaoStats](https://taostats.io/subnets/22)).

## What the Subnet Provides

Desearch turns search retrieval into a Bittensor subnet task. Miners provide search responses across
web, X/Twitter, and multi-source contexts, while validators compare returned results and convert
that assessment into subnet weights
([Desearch README](https://raw.githubusercontent.com/Desearch-ai/subnet-22/main/README.md)).

This places Subnet 22 in the data-access part of the Bittensor ecosystem. Its useful output is fresh
external context for products or agents that need retrieved information rather than only a static
model response.

## Retrieval Context

Retrieval work has different quality boundaries from model training or inference. A useful Desearch
response needs to be timely, relevant, and checkable against external providers. The repository's
architecture table separates miner search service, validator scoring, and shared protocol models,
which keeps the retrieval task distinct from a general AI application
([Desearch README](https://raw.githubusercontent.com/Desearch-ai/subnet-22/main/README.md)).

That distinction matters for readers. Subnet 22 is not mainly described by the model that consumes
search results later. It is described by the retrieval service being measured and rewarded inside
Bittensor.

## Miner and Validator Roles

Desearch's repository separates miner and validator responsibilities. Miners serve search synapses
and declare search capacity. Validators send synthetic and organic queries, verify results with
independent providers, store scoring windows, and write weights for the subnet
([Desearch README](https://raw.githubusercontent.com/Desearch-ai/subnet-22/main/README.md)).

The simple role boundary is that miners supply retrieval capability, while validators decide how
that capability should be weighted. That keeps the article focused on the subnet's service loop
instead of the repository's runbooks.

## Relationship to Yuma Consensus

Subnet 22 still fits the ordinary Bittensor incentive path. Validators turn Desearch retrieval
scores into weights, and those weights feed into Yuma Consensus. Yuma aggregates validator weight
submissions, and the emission system uses the resulting consensus weights to distribute subnet
emissions ([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Emission](https://docs.learnbittensor.org/learn/emissions)).

For Desearch, this connects search quality to Bittensor incentives. The subnet-specific work is
retrieval and scoring; the protocol relationship to rewards still runs through validator weights and
Yuma Consensus.

## Environment Context

Desearch examples can belong to localnet, testnet, or mainnet contexts, and those environments
should not be mixed. A local example can help explain the retrieval loop, while testnet and mainnet
are separate Bittensor network environments with separate histories
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks),
[Introduction to Bittensor: Subnet development](https://docs.learnbittensor.org/learn/introduction#subnet-development)).

Keeping the environment attached prevents overreading examples. A search result, validator score, or
emission outcome from one environment should not be treated as proof of behavior in another.

## Concept Boundaries

Subnet 22 should be read as a Desearch overview, not as miner onboarding material, validator
operations notes, or route documentation. The stable concept is Bittensor-incentivized search
retrieval: miners answer search tasks, validators score retrieval quality, and Yuma Consensus turns
those weights into emission allocation
([Desearch README](https://raw.githubusercontent.com/Desearch-ai/subnet-22/main/README.md),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

Project-specific credentials, route names, dashboards, and deployment details belong in Desearch's
own repository. The stable distinction is that Desearch is a retrieval subnet, not a generic search
product article.
