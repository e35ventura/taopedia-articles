Desearch is Bittensor Subnet 22, the subnet behind Desearch's decentralized real-time intelligence
layer. The official repository describes SN22 as coordinating miners and validators that serve live
web, X/Twitter, and multi-source search data for Desearch API and console products. The public
product is [desearch.ai](https://desearch.ai), and the subnet runtime is maintained in the
[Desearch-ai/subnet-22 repository](https://github.com/Desearch-ai/subnet-22).

The subnet's basic job is to turn search and social-data retrieval into a Bittensor incentive
market. Miners run services that answer search requests. Validators query miners, compare returned
results with external providers, track miner performance, and submit weights to [[Yuma Consensus]].
For readers, the important distinction is that Desearch is not only a public search product; SN22 is
the network layer that rewards participants for supplying and checking search data.

## How the Mechanism Works

The public SN22 repository breaks the system into miner, validator, validator API, and shared
protocol components. Miners run a Bittensor axon and serve AI, X/Twitter, and web search synapses.
Validators send synthetic and organic queries to miners, verify results with independent providers,
store scoring windows, and write weights on chain. A protected FastAPI service runs beside
validators so trusted Desearch services can route organic search requests through the subnet.

This gives SN22 both benchmark-style validator traffic and organic search traffic from the Desearch
platform. Synthetic validator queries give validators a controlled way to measure miner behavior.
Organic requests connect the Bittensor network to the Desearch API and console. The
[API reference](https://github.com/Desearch-ai/subnet-22/blob/main/docs/api.md) also documents
public miner-status routes, which expose the miner state observed by a validator without opening the
protected search routes.

The final reward path is the standard Bittensor one: validators convert their scoring view into
weights, and [[Yuma Consensus]] uses those weights to determine how emissions are distributed inside
the subnet.

## Participating as a Miner

A Desearch miner runs a Bittensor axon on netuid 22 and responds to health checks plus search
synapses. The official
[miner guide](https://github.com/Desearch-ai/subnet-22/blob/main/docs/running_a_miner.md) describes
a manifest file for declaring per-search-type concurrency, with web search, X/Twitter search, and AI
search as the example capacity categories. The
[environment reference](https://github.com/Desearch-ai/subnet-22/blob/main/docs/env_variables.md)
lists keys used by miner processes, including SerpAPI for web search and Apify for X/Twitter
scraping; a Twitter API bearer token is optional when the miner relies on Apify.

For Taopedia readers, the main takeaway is that miners are data providers rather than model-training
workers. They need reliable search infrastructure, valid Bittensor wallet and hotkey configuration,
and enough capacity to answer validator requests consistently.

## Participating as a Validator

A Desearch validator runs the scoring service that queries miners and writes weights, plus a
protected validator API used by trusted Desearch services. The official
[validator guide](https://github.com/Desearch-ai/subnet-22/blob/main/docs/running_a_validator.md)
describes Redis, PM2, validator hotkey registration, and provider credentials such as OpenAI, Apify,
ScrapingDog, and Weights & Biases as part of the operator setup.

Validators keep local miner scoring state in SQLite with rolling retention, according to the
validator runbook. That operational detail matters at a high level because SN22 rewards are based on
an ongoing view of miner responses rather than a single public submission. The code and docs should
remain the source of truth for anyone preparing to operate a validator.
