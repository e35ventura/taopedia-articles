# Weights Rate Limit

Weights rate limit is a per-subnet hyperparameter, listed in the documentation as `WeightsRateLimit`
and also referred to as `CommitmentRateLimit`, that sets how long, in blocks, a validator must wait
between [weight setting](https://docs.learnbittensor.org/resources/glossary#weight-setting) commits
on a subnet
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## What It Controls

The hyperparameter paces how often a single validator can resubmit
[validator weights](https://docs.learnbittensor.org/resources/glossary#validator-weights). It does
not define what those weights mean, how
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus) aggregates them, or which
miners a validator should score. It only sets the minimum block interval between one weight commit
and the next from the same validator on the selected subnet.

That makes weights rate limit a submission-pacing rule. It limits how frequently a validator can
change its on-chain weight signal on a subnet such as netuid 1, rather than deciding whether a
particular submission counts in the current
[epoch](https://docs.learnbittensor.org/resources/glossary#epoch).

## Documented Type, Default, and Setter

The [Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)
reference lists `WeightsRateLimit` / `CommitmentRateLimit` as a `u64` with a default of `100` and
the description "How long, in blocks, a validator must wait between weight commits on a subnet." It
is changed through the `sudo_set_weights_set_rate_limit` extrinsic, exposed in tooling as
`btcli sudo set --param weights_rate_limit`, and the reference marks the permission required to set
it as root rather than subnet owner
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

The live value is per-subnet chain state and can differ from the documented default, so the current
limit for a selected netuid should be read from that subnet's hyperparameter table rather than
assumed from the reference default alone.

## Subnet Context

Weights rate limit is one of the
[subnet hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters), the
on-chain state variables that configure a single
[subnet](https://docs.learnbittensor.org/resources/glossary#subnet), for example netuid 1. Because
each subnet carries its own hyperparameters, the pacing rule is defined per subnet and applies only
within that subnet's weight-submission path.

The parameter therefore belongs to the protocol envelope around validator evaluation, not to the
subnet task itself. It shapes how often a validator can update its signal, while the incentive
mechanism still defines what work miners produce and how validators should evaluate it
([Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism)).

## Development Stage Context

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. For weights rate
limit on a subnet such as netuid 1, that sequence changes how readers should interpret
weight-submission pacing examples.

In localnet, weights-rate-limit hyperparameters can be tested in an isolated environment. Local
pacing values reflect local chain configuration rather than production validator submission rules.

On testnet, weight-setting cadence can be exercised in a shared non-production network. Testnet
weights-rate-limit values are separate from mainnet subnet state
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

On mainnet, weights rate limit is a live per-subnet hyperparameter on production subnets. Observed
pacing rules depend on the selected subnet's on-chain hyperparameter state.

The [Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet. A weights-rate-limit example from one environment should
not be read as representing production validator pacing in another environment.

## BTCLI Reads the Live Hyperparameter for a netuid

Any user can read subnet hyperparameters for a selected netuid with
`btcli subnet hyperparameters --netuid 1`. The command output includes the live `WeightsRateLimit`
value for that subnet at query time, along with other owner-set and root-set fields
([Subnet Hyperparameters: View hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#view-hyperparameters)).

That read path keeps live pacing claims tied to a parseable netuid. A statement about weights rate
limit on netuid 1 should be checked with the hyperparameter table for netuid 1 rather than inferred
from the documented default alone.

## Distinction from Activity Cutoff

Weights rate limit and
[activity cutoff](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutoff)
answer different timing questions on a subnet such as netuid 1. Activity cutoff is measured in
blocks within each epoch and governs whether a validator's weight submission arrives early enough to
count for the current Yuma Consensus pass. Weights rate limit is measured in blocks between commits
and governs how soon the same validator can submit again after a prior weight commit
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

- **Activity cutoff** — whether a submission arrives inside the current epoch window.
- **Weights rate limit** — how long a validator must wait before the next commit.

Both settings shape validator signal timing, but one bounds intra-epoch participation while the
other bounds inter-commit spacing.

## Relationship to Weight Setting

[Weight setting](https://docs.learnbittensor.org/resources/glossary#weight-setting) is the
validator-side process of assigning scores to miners. Weights rate limit sits on the submission path
for that process: it does not change how a validator evaluates miners, but it can delay when the
validator's next on-chain weight update is accepted after an earlier commit
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

For readers, weight setting names the evaluation act, while weights rate limit names the minimum
block wait between successive commits from one validator on netuid 1.

## Relationship to Commit Reveal

[Commit Reveal](https://docs.learnbittensor.org/concepts/commit-reveal) changes when committed
weights become visible, while weights rate limit changes how frequently a validator can submit new
commits. Commit reveal is a visibility-timing mechanism; weights rate limit is a submission-pacing
hyperparameter. A subnet can use both concepts together, but they address different parts of the
weight flow ([Commit Reveal](https://docs.learnbittensor.org/concepts/commit-reveal),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

Readers should not treat commit-reveal delay and weights-rate-limit spacing as interchangeable. One
concerns encrypted concealment and later reveal; the other concerns the minimum block gap between
accepted commits from the same validator.

## Distinction from Serving Rate Limit

The hyperparameters reference also lists
[ServingRateLimit](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#servingratelimit),
which rate-limits miner calls to `serve_axon` and `serve_prometheus`. That setting paces miner
endpoint registration, not validator weight commits. Weights rate limit belongs to the validator
weight-submission path; serving rate limit belongs to the miner serving path on the same subnet
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## Reader Boundary

This page defines the concept at a high level. It does not report the live weights-rate-limit value
on any particular subnet or whether a specific validator is currently rate-limited. Those are
on-chain state values that should be checked for the relevant netuid with
`btcli subnet hyperparameters --netuid 1`. The documented default is 100 blocks, the type is `u64`,
and the parameter is governed at the root level
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

That reading keeps weights rate limit separate from scoring quality and emission outcomes. It paces
how often one validator can commit new weights; it does not predict consensus results or miner
rewards.
