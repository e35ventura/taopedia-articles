# Yuma3 Enabled

Yuma3 enabled names the per-subnet choice to run
[Yuma Consensus 3 (YC3)](https://docs.learnbittensor.org/learn/yuma3-migration-guide) rather than
the earlier v2 bonding path. Until an owner turns v3 on for a netuid, that subnet keeps the v2
settlement rules; after the switch, epoch timing and the subnet task stay the same while consensus
bonding follows the v3 model described in the migration guide
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[YC3 Migration Guide](https://docs.learnbittensor.org/learn/yuma3-migration-guide)).

The on-chain toggle itself is documented under the [[Yuma Version]] hyperparameter. That sibling
page covers the boolean default, owner permission, and how to read the live value for a specific
netuid. This page stays at the migration and behavior layer so readers understand why the opt-in
exists and what changes once v3 is active
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## Why Adoption Is Opt-In

Subnets do not move to YC3 network-wide. The migration guide states that each subnet keeps its
current consensus version until its owner explicitly enables v3, which lets Finney and other
networks run mixed versions at the same time
([YC3 Migration Guide](https://docs.learnbittensor.org/learn/yuma3-migration-guide),
[Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

Because the choice is per netuid, netuid 1 can follow one path while another subnet remains on v2.
The infobox example label is only a reading anchor; every subnet stores its own live setting in that
subnet's hyperparameter table rather than inheriting a single network constant
([Subnet Hyperparameters: View hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#view-hyperparameters)).

## What Changes When v3 Is On

[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus) still computes validator and
miner emissions and still maintains
[validator-miner bonds](https://docs.learnbittensor.org/resources/glossary#validator-miner-bonds) as
the starting point of each epoch pass. Enabling v3 changes how those bonds evolve inside consensus.
The migration guide and YC3 overview describe the refinement as improving validator fairness, bond
mechanics, and numerical precision relative to the v2 path
([YC3 Migration Guide](https://docs.learnbittensor.org/learn/yuma3-migration-guide),
[How Yuma Consensus 3 Makes Bittensor More Fair](https://docs.learnbittensor.org/learn/yc3-blog)).

The switch does not replace tempo, epoch boundaries, or the work miners perform. It selects which
consensus implementation settles validator weights when an epoch closes on the chosen netuid
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch)).

## Distinction from Yuma Consensus 3

Yuma3 enabled is the owner-controlled opt-in that moves one subnet onto the v3 path. Yuma Consensus
3 is the bonding and settlement refinement that runs after that opt-in. Readers who need the exact
hyperparameter name, default, and read path should use [[Yuma Version]]; readers who need the
consensus model itself should use the YC3 overview
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[How Yuma Consensus 3 Makes Bittensor More Fair](https://docs.learnbittensor.org/learn/yc3-blog)).

## Distinction from Liquid Alpha Enabled

[[Liquid Alpha Enabled]] is a separate subnet flag that controls whether bond-smoothing alpha varies
with consensus alignment on the v3 path. Yuma3 enabled only selects the consensus version. The
migration guide notes that liquid-alpha behavior applies only when liquid alpha is itself enabled
and the required consensus values and activity are present
([YC3 Migration Guide](https://docs.learnbittensor.org/learn/yuma3-migration-guide),
[Consensus-based Weights](https://docs.learnbittensor.org/concepts/consensus-based-weights),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## Verifying the Setting on netuid 1

Any live claim about whether v3 is active must name a netuid. For the documented example netuid 1 on
Finney mainnet, the reference describes reading that subnet's hyperparameter table to see whether
the v3 toggle is on or off for that netuid alone
([Subnet Hyperparameters: View hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#view-hyperparameters),
[Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

This page does not substitute for that table read. It explains the migration meaning of the toggle;
[[Yuma Version]] documents how the boolean is stored, defaulted, and changed on chain.

## Reader Boundary

This page explains the v3 opt-in at a high level. It does not report liquid-alpha status, validator
ranks, coldkey ownership, neuron counts, or the live toggle on any netuid other than naming netuid 1
as the infobox example. For current on-chain values, use the hyperparameter table for the subnet you
care about
([Subnet Hyperparameters: View hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#view-hyperparameters)).
