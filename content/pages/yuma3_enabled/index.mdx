# Yuma3 Enabled

Yuma3 enabled is the per-subnet switch that opts a subnet into
[Yuma Consensus 3 (YC3)](https://docs.learnbittensor.org/learn/yuma3-migration-guide), the latest
version of the consensus mechanism. It is a boolean set by the subnet owner, and on chain the choice
is tracked per netuid
([YC3 Migration Guide](https://docs.learnbittensor.org/learn/yuma3-migration-guide)).

## What It Switches

[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus) computes validator and miner
emissions and maintains the
[validator-miner bonds](https://docs.learnbittensor.org/resources/glossary#validator-miner-bonds)
that reward validators for aligning with consensus. The migration guide describes YC3 as bringing
improvements to validator fairness, bond mechanics, and precision, including assigning a per-pair
adjustment rate so each validator-miner bond can smooth at its own rate rather than all bonds
sharing one ([YC3 Migration Guide](https://docs.learnbittensor.org/learn/yuma3-migration-guide)).
This toggle decides which of those two bond paths a subnet runs under.

## When It Matters

A common misconception is that subnets move to YC3 automatically. They do not: the migration guide
states a subnet keeps functioning under the previous consensus until its owner explicitly enables
YC3, so the upgrade is opt-in per subnet rather than a network-wide flag day
([YC3 Migration Guide](https://docs.learnbittensor.org/learn/yuma3-migration-guide)).

The toggle also sets the foundation for
[liquid alpha](https://docs.learnbittensor.org/concepts/consensus-based-weights). The guide notes
YC3 works with liquid alpha only when liquid alpha is itself enabled and consensus values and
activity are present, so turning on liquid alpha is not a substitute for moving to YC3; the per-pair
bond behavior comes from the YC3 path that this switch selects
([YC3 Migration Guide](https://docs.learnbittensor.org/learn/yuma3-migration-guide)).

## Reading the Live Setting

Because the choice is recorded per netuid, the active value is read per subnet. On netuid 1, for
example, checking netuid 1's `yuma3_enabled` tells you whether that subnet is running the YC3 bond
mechanics or the original consensus, which in turn determines whether its liquid alpha and per-pair
smoothing settings have any effect
([YC3 Migration Guide](https://docs.learnbittensor.org/learn/yuma3-migration-guide),
[Consensus-based Weights](https://docs.learnbittensor.org/concepts/consensus-based-weights)).

## Distinction from Liquid Alpha Enabled

The two toggles stack but are not the same. Yuma3 enabled selects the consensus version and its bond
path, while liquid alpha enabled, layered on top of YC3, lets the per-pair alpha vary across its
configured range
([YC3 Migration Guide](https://docs.learnbittensor.org/learn/yuma3-migration-guide)).

- **Yuma3 enabled** — which consensus version and bond path the subnet uses.
- **Liquid alpha enabled** — whether the per-pair alpha varies once YC3 is active.
