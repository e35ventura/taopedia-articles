# Min Allowed Weights

Min allowed weights is a per-subnet hyperparameter that sets the minimum number of weights a
validator must include when it sets weights on a subnet. Documentation describes it as the minimum
number of weights for a validator to set when setting weights
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## What It Controls

The hyperparameter is a floor on the size of a validator's weight submission. When a validator
submits weights, the number of entries it assigns must meet this minimum. It does not say how a
validator should score miners; it only sets how few weights a valid submission may contain
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## How the Floor Is Enforced

Documentation describes a length check that does not apply the configured minimum blindly. It first
takes the smaller of the configured minimum and the subnet's current neuron count, so a subnet with
fewer registered UIDs than the configured minimum only requires as many weights as there are
neurons. A submission passes when its number of weights is at least that effective minimum
([Subnet Hyperparameters: MinAllowedWeights](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#minallowedweights),
[Glossary: Weight Vector](https://docs.learnbittensor.org/resources/glossary#weight-vector),
[Implementation of the Yuma Consensus Epoch: Weight Processing](https://docs.learnbittensor.org/navigating-subtensor/epoch#5-weight-processing)).

One submission path is exempt from the floor on non-root subnets: a validator setting only its own
single self-weight is accepted regardless of the configured minimum
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Glossary: Weight Setting](https://docs.learnbittensor.org/resources/glossary#weight-setting)).

## Default and Setting

The documentation lists min allowed weights as a `u16` value with a default of 1, and marks it as
owner-settable, so a subnet owner can raise it for their subnet. A value above one means a single
weight submission must cover more than one target. The value in force is per-subnet chain state and
can differ from the default, so the minimum configured on netuid 1 can differ from another subnet's
floor ([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## Why It Matters

The minimum interacts with how validator weights feed Yuma Consensus. Weights are the validator
inputs that get aggregated into a consensus result, and a higher minimum requires each validator's
submission to spread across more targets rather than concentrate on a single one. The hyperparameter
constrains the form of valid weight input without dictating the scores themselves
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

## The Weight Vector Lists Targets and Scores

The [Glossary: Weight Vector](https://docs.learnbittensor.org/resources/glossary#weight-vector)
describes a validator's submission as a list of miner targets paired with evaluation scores. Min
allowed weights sets how many entries that list must contain, not how those scores should be chosen
or ranked.

That form rule sits upstream of
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus). Consensus aggregates the
submitted vectors into a result, while the minimum count hyperparameter decides whether a submission
is structurally valid before that aggregation begins
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## Activity Cutoff and Validator Activity

Subnet [hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters) include
activity cutoff vocabulary for validator inactivity tolerance. When too many blocks have passed
since a validator's [last update](https://docs.learnbittensor.org/subnets/metagraph) relative to the
effective inactivity span, that validator is treated as inactive for the epoch pass and its stake is
masked out before stake-weighted consensus runs
([Implementation of the Yuma Consensus Epoch: Network State Collection](https://docs.learnbittensor.org/navigating-subtensor/epoch#1-network-state-collection),
[Subnet Hyperparameters: Activity Cutoff](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutoff)).

On dynamic-tempo subnets the fixed block hyperparameter is deprecated; the live inactivity span
comes from
[activity cutoff factor](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutofffactor)
and tempo instead
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

Min allowed weights and activity cutoff therefore govern different parts of the same submission
path. The minimum count rule shapes how many targets a valid vector must include, while activity
cutoff vocabulary names how long a validator may remain without an on-chain update before its stake
is masked inactive for consensus—not how early in the epoch a vector must arrive
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

## Distinction from Activity Cutoff

Min allowed weights sets the fewest miner targets a valid weight submission must include. Activity
cutoff vocabulary names how long a validator may remain without an on-chain update before its stake
is masked inactive for the pass—not an early-epoch submission deadline
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Subnet Hyperparameters: Activity Cutoff](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutoff),
[Subnet Hyperparameters: Activity Cutoff Factor](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutofffactor),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

Structural validity vocabulary and inactivity-mask vocabulary answer different submission questions.
A vector can meet the count floor yet still come from a validator whose stake is masked inactive
when last update exceeds the allowed span, and a recent last update does not relax the minimum count
requirement ([Subnet Metagraph](https://docs.learnbittensor.org/subnets/metagraph),
[Implementation of the Yuma Consensus Epoch: Network State Collection](https://docs.learnbittensor.org/navigating-subtensor/epoch#1-network-state-collection)).

- **Min allowed weights** — the fewest weights a submission must include.
- **Activity cutoff** — inactivity span before a stale validator is masked out of consensus.

## Distinction from Max Allowed UIDs

Min allowed weights and max allowed UIDs sit at opposite ends of the same weight submission. Min
allowed weights sets the fewest entries a validator must include, while max allowed UIDs sets the
ceiling on how many neurons a subnet holds — the population those weight entries can point at. The
required minimum therefore operates inside the available UID count: a validator must name at least
the minimum number of targets from the neurons the subnet actually has
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## Distinction from Weight Setting

Min allowed weights and weight setting act on the same submission as constraint and action. Min
allowed weights is the per-subnet hyperparameter that sets the fewest weights a validator must
assign, while weight setting is the `set_weights` action that submits the vector, so a
weight-setting call that includes fewer weights than the minimum is rejected and the constraint
shapes what a valid submission must contain
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Glossary: Weight Vector](https://docs.learnbittensor.org/resources/glossary#weight-vector),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Min allowed weights** — the fewest weights a submission must include.
- **Weight setting** — the action that submits the vector the minimum constrains.

## Distinction from Weights Version Key

Min allowed weights and the weights version key are different weight-submission hyperparameters. Min
allowed weights sets the minimum number of weights a validator must include when it sets weights,
while the weights version key sets the minimum version a `set_weights` call must carry to be
accepted ([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

- **Min allowed weights** — the fewest weights a submission must include.
- **Weights version key** — the minimum version a submission must carry.

## Distinction from Weights Rate Limit

Min allowed weights and weights rate limit are different weight-submission hyperparameters. Min
allowed weights sets the minimum number of weights a validator must include in a submission, while
weights rate limit sets how many blocks a validator must wait between weight commits
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

- **Min allowed weights** — the fewest weights a submission must include.
- **Weights rate limit** — the blocks a validator must wait before the next commit.

## Distinction from Validator Permit

Min allowed weights and a validator permit are two separate requirements behind a counting weight
submission. The permit is the on-chain flag granting the right to submit weights that take part in
consensus, while min allowed weights sets how many targets a submission must include to be valid
([Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

- **Validator permit** — whether a validator's weights may count in consensus.
- **Min allowed weights** — how many targets a valid submission must include.

## Chain Reads for netuid 1

Readers can verify live hyperparameter values for the documented example netuid with
`btcli subnet hyperparameters --netuid 1 --network finney`
([Subnet Hyperparameters: View hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#view-hyperparameters)).

That read path keeps live hyperparameter claims tied to a parseable netuid.

## Per-Subnet Live Value Boundary

Min allowed weights is per-subnet chain state. The count floor configured on one netuid governs how
many targets a validator's submission must include on that subnet, but the live minimum can differ
from reference defaults and from the floor on another netuid
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

This article's infobox uses netuid 1 as an example label when reading one subnet's hyperparameter
table on Finney mainnet. That example helps readers verify one row; it is not proof that every
subnet exposes the same live minimum
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

Min allowed weights governs weight-submission breadth; Yuma Consensus still converts validator
weights into emission shares each epoch on the active subnet
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Min allowed weights** — count floor for valid weight submissions on a subnet.
- **Per-subnet boundary** — live value is chain state on one netuid.

## Distinction from Yuma Consensus

Min allowed weights is the per-subnet hyperparameter that sets the minimum number of miner targets a
validator must include in a weight submission. It names a structural validity floor on the
submission form, not the settlement step that converts aggregated weights into emission shares
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Glossary: Weight Vector](https://docs.learnbittensor.org/resources/glossary#weight-vector)).

Yuma Consensus is the on-chain mechanism that runs at the epoch boundary on the selected netuid. It
reads the weight matrix from eligible validators whose submissions meet structural rules, applies
clipping and bonding, and converts the result into miner incentives and validator dividend shares
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Emission](https://docs.learnbittensor.org/learn/emissions)).

Meeting the count minimum does not prevent score clipping when values outlie consensus. Min allowed
weights gates submission breadth; Yuma still enforces alignment and allocates payouts from the
filtered matrix—not from the count floor alone
([Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism),
[Yuma Consensus: Clipping excess weights](https://docs.learnbittensor.org/learn/yuma-consensus#clipping-excess-weights)).

Readers should treat min allowed weights as a hyperparameter validity rule on one netuid, and Yuma
as the mechanism that settles eligible weight vectors into emissions.

- **Min allowed weights** — floor on how many miner targets a valid submission must include.
- **Yuma Consensus** — epoch-boundary settlement from eligible validator weights to emission shares.

Consensus clipping trims weights that depart from the stake-weighted agreement point, so a validator
can meet the count minimum and still see inflated values clipped: the hyperparameter constrains
submission breadth while clipping constrains how far any included score can depart from consensus
([Yuma Consensus: Clipping excess weights](https://docs.learnbittensor.org/learn/yuma-consensus#clipping-excess-weights),
[Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism)).

## Reader Boundary

This page defines the concept at a high level. It does not report the min-allowed-weights value set
on any particular subnet or any validator's current weight submission. It should not be read as
activity cutoff timing, proof that a submission influenced stake-weighted consensus, or a guarantee
of emission outcomes. Those are live chain state and should be checked for the relevant netuid. The
default of 1 is the documented value, and the setting is owner-controlled per subnet
([Subnet Hyperparameters: MinAllowedWeights](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#minallowedweights),
[Subnet Hyperparameters: View hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#view-hyperparameters)).
