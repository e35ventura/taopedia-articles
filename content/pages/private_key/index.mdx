# Private Key

A private key is the protected side of a cryptographic key pair in Bittensor wallet terminology. The
[Private Key glossary entry](https://docs.learnbittensor.org/resources/glossary#private-key) places
it in authorization context, paired with public key material that can be referenced more openly.

## What It Represents

Private key names one protected side of an
[EdDSA](https://docs.learnbittensor.org/resources/glossary#eddsa-cryptographic-keypairs) key pair. A
[public key](https://docs.learnbittensor.org/resources/glossary#public-key) is shareable material
used for verification, encryption, and account reference. A private key authorizes signed actions,
so the two terms should not be treated as interchangeable wallet labels
([Glossary: Private Key](https://docs.learnbittensor.org/resources/glossary#private-key),
[Glossary: Public Key](https://docs.learnbittensor.org/resources/glossary#public-key)).

In Bittensor wallet vocabulary, private key is a pair-side label, not a single secret per wallet.
Each coldkey and each hotkey is its own key pair with separate private and public material
([Wallets, Coldkeys and Hotkeys](https://docs.learnbittensor.org/keys/wallets)). One coldkey can
control multiple hotkeys, and each added hotkey brings its own private key rather than reusing the
coldkey's protected side.

Readers should separate three ideas that sound similar:

- **Private key** — the protected signing side inside one key pair.
- **Coldkey private key** — authorizes custody-side work such as transfers, stake moves, hotkey
  management, and subnet ownership actions.
- **Hotkey private key** — authorizes operational subnet work such as miner service and validator
  weight submission.

Subnet participation can require the hotkey private key even when no TAO transfer or stake movement
is involved, because operational signing is not the same as fund custody
([Glossary: Hotkey](https://docs.learnbittensor.org/resources/glossary#hotkey),
[Glossary: Coldkey](https://docs.learnbittensor.org/resources/glossary#coldkey)).

The public side is mathematically derived from the private key. Losing or exposing a private key
compromises the whole pair because the public side is computed from it, not stored as an independent
secret you can rotate separately
([Glossary: Public Key](https://docs.learnbittensor.org/resources/glossary#public-key)).

Private key vocabulary does not provide wallet creation steps, backup policy, or signing
instructions. Those belong to key-management and recovery guidance
([Working with Keys](https://docs.learnbittensor.org/keys/working-with-keys),
[Handle your Seed Phrase/Mnemonic Securely](https://docs.learnbittensor.org/keys/handle-seed-phrase)).

## Coldkey and Hotkey Private Keys Sign Different Work

[Wallets, Coldkeys and Hotkeys](https://docs.learnbittensor.org/keys/wallets) assigns different
authorization work to the two private keys inside a wallet. The coldkey private key is needed for
transferring TAO balances, managing stake, subnet management and governance actions, and managing
hotkeys. The hotkey private key is needed for miners to serve requests in subnets and for validators
to send requests to miners and submit weights to the chain.

Keeping that split explicit prevents reading every signed submission as coldkey fund authority.

## Hardware Signing Keeps the Private Key Off the Host

A private key does not have to reside on the same device that initiates a transaction. Hardware
wallets such as Ledger hold the private key and sign across a device boundary, while Polkadot Vault
keeps the key in an air-gapped signing environment and returns signed results through a QR workflow
rather than exposing the key to the host
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).

## Regeneration Restores One Pair at a Time

[Glossary: Regenerating a Key](https://docs.learnbittensor.org/resources/glossary#regenerating-a-key)
describes recovering wallet key material from recovery information for a specific key. That path
rebuilds access to one coldkey or hotkey pair rather than every key in a wallet automatically
([Working with Keys](https://docs.learnbittensor.org/keys/working-with-keys)).

Recovery material can restore a key; private key names the protected signing side once the pair
exists.

## Development Stage Context

Private keys apply across localnet, testnet, and mainnet, but the security consequence depends on
which network the associated wallet operates on. Keys controlling mainnet wallets authorize real TAO
operations and require the strongest protection
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

## Distinction from Mnemonic

A private key is the protected authorization side of a key pair. A mnemonic is recovery material
that can recreate wallet keys after loss
([Glossary: Private Key](https://docs.learnbittensor.org/resources/glossary#private-key),
[Glossary: Mnemonic](https://docs.learnbittensor.org/resources/glossary#mnemonic)).

- **Private key** — protected signing material inside an existing keypair.
- **Mnemonic** — recovery material that can regenerate wallet keys.

## Distinction from Wallet Address

Wallet address names a public-key-derived TAO destination. Private key names protected signing
material on the authorization side of the pair
([Glossary: Wallet Address](https://docs.learnbittensor.org/resources/glossary#wallet-address),
[Glossary: Private Key](https://docs.learnbittensor.org/resources/glossary#private-key)).

- **Private key** — protected signing side inside one key pair.
- **Wallet address** — public identifier derived from the pair's public side.

## Distinction from Public Key

Public key names shareable verification and account-reference material. Private key names the
protected side that authorizes signed actions
([Glossary: Public Key](https://docs.learnbittensor.org/resources/glossary#public-key),
[Glossary: Private Key](https://docs.learnbittensor.org/resources/glossary#private-key)).

- **Private key** — root secret that authorizes signed actions.
- **Public key** — derived shareable material used to verify and identify accounts.

## Distinction from EdDSA Cryptographic Keypairs

Private key names the protected signing side of a keypair. EdDSA keypairs name the algorithm context
for the pair rather than key-handling procedures
([Glossary: Private Key](https://docs.learnbittensor.org/resources/glossary#private-key),
[Glossary: EdDSA Cryptographic Keypairs](https://docs.learnbittensor.org/resources/glossary#eddsa-cryptographic-keypairs)).

- **Private key** — protected signing side inside the pair.
- **EdDSA cryptographic keypairs** — algorithm context for Bittensor public/private pairs.

## Distinction from Bittensor Wallet

A private key is one secret used for signing. A Bittensor wallet is the broader key container and
network identity that holds the coldkey and hotkey
([Glossary: Bittensor Wallet](https://docs.learnbittensor.org/resources/glossary#bittensor-wallet)).

- **Private key** — a single signing secret for one key pair.
- **Bittensor wallet** — the container that can hold several such keys.

## Distinction from Stake

A private key authorizes signed actions. Stake is the amount of currency tokens delegated to a
validator in a subnet ([Glossary: Stake](https://docs.learnbittensor.org/resources/glossary#stake)).

- **Private key** — authorizes actions but is not itself a balance.
- **Stake** — delegated token amount that influences consensus weight.

## Distinction from Seed Phrase Security

A private key is the cryptographic secret that signs for an address. Seed phrase security is the
operational discipline for safeguarding the mnemonic that can derive those keys
([Glossary: Private Key](https://docs.learnbittensor.org/resources/glossary#private-key),
[Handle your Seed Phrase/Mnemonic Securely](https://docs.learnbittensor.org/keys/handle-seed-phrase)).

- **Private key** — protected signing material for one key pair.
- **Seed phrase security** — practices protecting recovery words that can restore keys.

## Distinction from Yuma Consensus

Private keys enable wallet authorization. Yuma Consensus converts validator weight submissions into
emission shares on a subnet
([Glossary: Private Key](https://docs.learnbittensor.org/resources/glossary#private-key),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Private key** — protected key-pair side that authorizes wallet actions.
- **Yuma Consensus** — on-chain mechanism that turns validator weights into emission shares.

## Reader Boundary

Private key should not be read as a wallet address, a mnemonic, a subnet role, or a balance label.
It names the protected authorization side of a cryptographic key pair
([Glossary: Private Key](https://docs.learnbittensor.org/resources/glossary#private-key)).
