An archive node is a public Subtensor node that keeps the full Bittensor blockchain history. The
[Bittensor glossary](https://docs.learnbittensor.org/resources/glossary#archive-node) defines an
archive node as a public Subtensor node that stores the entire blockchain history so users and
applications can query historical data.

## Historical Data Role

The
[Subtensor Node Basics](https://docs.learnbittensor.org/subtensor-nodes#lite-node-vs-archive-node)
documentation explains that public Subtensor nodes synchronize with the Bittensor network, and that
lite nodes and archive nodes are two public node types. A lite node is optimized for quickly syncing
recent finalized state, while an archive node stores all blocks from genesis through the current
block.

That storage difference is the core of the concept. An archive node is useful when the question
depends on older chain state, historical events, or full state access. The same documentation names
block explorers, indexers, analytics, audits, and older-data queries as examples of workloads that
need archive-node style access.

In plain terms, an archive node trades storage and synchronization cost for historical completeness.
It is not just a faster endpoint or a general reliability label. It is the node type intended for
applications that need to look back through the chain rather than only follow the latest finalized
state.

## Boundary with Lite Nodes

Archive nodes and lite nodes both belong to the public Subtensor node family, but they serve
different access patterns. The [Subtensor Nodes](https://docs.learnbittensor.org/subtensor-nodes)
documentation describes lite nodes as using warp synchronization, retaining limited recent data, and
relying on lower storage requirements. That makes lite nodes suitable for many ordinary network
participants.

Archive nodes are heavier because they process and retain complete historical data. That makes them
better suited to systems that need old blocks, long-range state inspection, explorer views, or audit
records. Choosing between the two is therefore about query depth and storage requirements, not about
whether a node is part of Bittensor at all.

This distinction also keeps the term separate from a local blockchain. A local blockchain is an
isolated development environment, while an archive node is synchronized with a public Bittensor
network such as mainchain or testchain. Archive nodes are therefore public network infrastructure,
not private testing chains.

## Boundary with Neurons

The same Subtensor Nodes documentation states that a Subtensor node is different from a Bittensor
neuron. A neuron is a subnet miner or subnet validator inside a subnet. An archive node is part of
the blockchain access layer and stores chain data.

For readers, this prevents a common role mix-up. Running an archive node does not by itself make an
operator a subnet miner or subnet validator, and a subnet miner or validator does not automatically
provide archive-node history. The archive node answers chain-data questions; subnet participants
perform and evaluate subnet-specific work.

## Why It Matters

Archive nodes matter because many Bittensor questions are historical. A block explorer may need to
show older transactions. An indexer may need to rebuild derived tables from chain events. An audit
may need to verify how state changed over time. Those uses require more than the latest finalized
state.

The concept is therefore best read as an infrastructure role. Archive nodes support applications
that need full history, while lite nodes support lighter participation patterns where recent state
is enough. Both connect to Subtensor, but they make different tradeoffs.
