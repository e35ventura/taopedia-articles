# Can Not Set Root Network Weights

`CanNotSetRootNetworkWeights` means a weight-setting call targeted the root subnet instead of an
ordinary subnet. The standard-errors reference describes it as "Can not set weights for the root
network"
([Subtensor Standard Errors](https://docs.learnbittensor.org/subtensor-api/errors#cannotsetrootnetworkweights)).

The root subnet runs its own consensus path and is not a destination for ordinary validator weight
submissions
([Root Subnet / Subnet Zero](https://docs.learnbittensor.org/resources/glossary#root-subnetsubnet-zero)).

## What It Means

The `set_weights` extrinsic accepts a target `netuid` and writes the validator's scores into that
subnet's weight storage. `CanNotSetRootNetworkWeights` means the submitted `netuid` was the root
subnet, so the chain rejected the call and wrote no weights
([Subtensor Standard Errors](https://docs.learnbittensor.org/subtensor-api/errors#cannotsetrootnetworkweights)).

This is an early netuid guard on the weight-setting path. It runs before list-shape, registration,
rate-limit, and other later checks because the root subnet is never a valid target for these
submissions.

## Why It Appears

The check fires whenever a plain weight call, mechanism-weight call, or commit-reveal reveal routes
into weight storage with the root subnet as its target. A misconfigured client, copied extrinsic, or
automation defaulting to netuid zero can hit this error before any UID-list or stake validation
runs.

When debugging, confirm the submitted `netuid` is an ordinary subnet, not the root subnet. Then
compare direction against root-only operations: `NotRootSubnet` is the reverse check, rejecting
calls that require the root subnet when a non-root netuid was submitted
([Subtensor Standard Errors: NotRootSubnet](https://docs.learnbittensor.org/subtensor-api/errors#notrootsubnet)).

The practical meaning is narrow: the caller directed a weight-setting call at the root subnet. The
problem is not invalid UIDs, missing registration on a normal subnet, or a rate-limit failure on an
otherwise valid target.

## Distinction from Not Root Subnet

`CanNotSetRootNetworkWeights` and `NotRootSubnet` both check the relationship between a caller's
target netuid and the root subnet, but in opposite directions. `CanNotSetRootNetworkWeights` rejects
a weight-setting call when the target is the root subnet. `NotRootSubnet` rejects root-only
operations when the submitted netuid is something else
([Subtensor Standard Errors: NotRootSubnet](https://docs.learnbittensor.org/subtensor-api/errors#notrootsubnet)).

- **CanNotSetRootNetworkWeights** — the target netuid is the root subnet, which the weight-setting
  path does not accept.
- **NotRootSubnet** — the operation requires the root subnet, but the submitted netuid is something
  else.

## Reader Boundary

This page defines the meaning of the error label and the root-subnet rejection on weight-setting
paths. It does not describe how root-subnet consensus decides its own weights, subnet
deregistration, or the rest of the weight-setting validation sequence beyond this first rejection;
those are separate topics
([Root Subnet / Subnet Zero](https://docs.learnbittensor.org/resources/glossary#root-subnetsubnet-zero)).
