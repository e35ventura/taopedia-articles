# Tx Rate Limit

Tx rate limit is a chain parameter, listed in the documentation as `TxRateLimit`, that sets the
network's general transaction rate limit. The dedicated rate-limits reference describes it as the
default transaction rate limit, expressed in blocks, with the chain state variable named
`TxRateLimit` ([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits)).

## What It Controls

The parameter is a cooldown measured in blocks between rate-limited transactions from an account.
Although it is the network's general transaction rate limit, the documentation notes it currently
applies only to hotkey swaps, while other rate-limited transactions are handled by their own custom
limits ([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits)).

The rate-limits reference lists the current general transaction rate limit as 1 block, about 12
seconds at the documented block cadence. That makes it the short account-level gate in the hotkey
swap path, not the multi-day per-subnet cooldown
([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits),
[Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

When a transaction would breach the limit, the chain rejects it with the `TxRateLimitExceeded`
error. That error is the signal that the cooldown window for the general transaction rate limit has
not yet elapsed ([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits),
[Subtensor Standard Errors](https://docs.learnbittensor.org/subtensor-api/errors)).

Because the value is counted in blocks, the real-time cooldown depends on block time. The one-block
spacing it enforces is short relative to longer per-subnet windows
([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits)).

## Hotkey Swaps Carry a Second Limit

For hotkey swaps specifically, the general transaction rate limit is not the only gate. The
documentation describes hotkey swaps as subject to two separate rate limits that must both be
satisfied: the general transaction rate limit and a much longer per-subnet interval. The tx rate
limit is the short, network-wide half of that pair
([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits)).

## Per-Subnet Half for netuid 1

While the general transaction rate limit is network-wide, the second hotkey-swap limit is per
subnet, so it is observed against a specific netuid. For the documented example netuid 1 on Finney
mainnet, a hotkey swap must satisfy both the network-wide tx rate limit and netuid 1's own
per-subnet swap interval before it is accepted on that subnet
([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits)). The infobox uses netuid 1
only as an example label for that per-subnet half; the tx rate limit itself applies across the chain
rather than belonging to one subnet
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

## Documented Type, Default, and Setter

The [Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)
reference lists `TxRateLimit` under global root state variables as a `u64` with a documented default
of `1000` blocks. The value is changed through the `sudo_set_tx_rate_limit` extrinsic at root
permission. The reference lists no `btcli` setter for this global
([Subnet Hyperparameters: TxRateLimit](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#txratelimit)).

The constants reference exposes the startup default as
`api.consts.subtensorModule.initialTxRateLimit`, listed as `1000`. That genesis constant matches the
documented hyperparameter default above, but the rate-limits reference separately documents the
current live general transaction rate limit as `1` block on the connected network, so readers should
not treat the documented default, the genesis constant, and live `TxRateLimit` storage as
interchangeable
([Subtensor Constants: initialTxRateLimit](https://docs.learnbittensor.org/subtensor-api/constants#initialtxratelimit-u64),
[Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits),
[Subnet Hyperparameters: TxRateLimit](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#txratelimit)).

## Reading and Setting the Value

`TxRateLimit` is root-governed chain state rather than a per-subnet owner setting. Because it is
live chain state, the current value is read from the chain rather than assumed; the Bittensor SDK
exposes a chain query that returns the active transaction rate limit
([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits),
[SubtensorAPI](https://docs.learnbittensor.org/sdk/subtensor-api)).

## Distinction from Serving Rate Limit

Serving rate limit is a per-subnet limit on how often a miner can update its serving metadata. Tx
rate limit is the network-wide general transaction rate limit that currently governs hotkey swaps,
so one is per-subnet and the other applies across the chain
([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

- **Tx rate limit** — network-wide general transaction cooldown.
- **Serving rate limit** — per-subnet limit on miner serving-metadata updates.

## Distinction from Network Rate Limit

Network rate limit paces how often new subnets can be registered. Tx rate limit paces general
transactions from an account, so one governs subnet creation cadence and the other account-level
transaction spacing ([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

- **Tx rate limit** — cooldown between rate-limited account transactions.
- **Network rate limit** — wait between new subnet registrations.
