# Yuma Version

Yuma version is a per-subnet hyperparameter, listed in the documentation as `YumaVersion`, that
selects which [Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus) version a
subnet uses when processing validator weights. The reference describes it as toggling the consensus
mechanism between Yuma Consensus v2 and v3
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## What It Controls

The hyperparameter chooses the consensus implementation path for a subnet, not the subnet task,
miner incentives formula in the abstract, or the tempo at which epochs run. Validator weights still
feed into Yuma settlement on each epoch; the version flag decides whether that settlement follows
the v2 or v3 consensus rules on the selected netuid
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

Yuma Consensus v3 introduces bond-scaling refinements that make validator-miner bonds more
responsive to independent evaluation, while v2 follows the earlier bonding model. Enabling v3 on a
subnet therefore changes how bonds evolve inside consensus without replacing the broader epoch
structure
([How Yuma Consensus 3 Makes Bittensor More Fair](https://docs.learnbittensor.org/learn/yc3-blog),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

The flag is owner-tunable per subnet, so netuid 1 can run one version while another netuid runs the
other, and the live value is chain state rather than a network constant
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

## Documented Type and Default

The [Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)
reference lists `YumaVersion` as a `Bool` with a default of false and marks the permission required
to change it as subnet owner. With the default off, a subnet uses the v2 path unless an owner
enables v3 for that netuid
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

Because each subnet carries its own hyperparameters, the consensus version on one netuid can differ
from the documented default and from the version active on another subnet
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## Reading the Live Value for netuid 1

Yuma version is per-subnet chain state, so any live claim is tied to a specific netuid. For the
documented example netuid 1 on Finney mainnet, the flag appears in that subnet's hyperparameter
table, which the reference describes under viewing a subnet's hyperparameters
([Subnet Hyperparameters: View hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#view-hyperparameters)).
The infobox uses netuid 1 only as an example label; other subnets expose their own values
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

## Distinction from Yuma Consensus 3

Yuma version is the per-subnet hyperparameter that selects v2 or v3 consensus on a netuid. Yuma
Consensus 3 is the consensus refinement itself — the bond-scaling model that v3 applies when this
flag is enabled
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Yuma Consensus 3](https://docs.learnbittensor.org/learn/yc3-blog)).

- **Yuma version** — owner-settable toggle choosing v2 or v3 on a subnet.
- **Yuma Consensus 3** — the v3 bonding and consensus refinement that runs when v3 is selected.
