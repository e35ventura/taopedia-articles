Harnyx is Bittensor Subnet 67, a subnet for deep research. Public Harnyx materials describe it as a
competitive harness where miners build research agents, validators run those agents on research
tasks, and the network rewards stronger researched answers.

## What the Subnet Produces

The [Harnyx README](https://raw.githubusercontent.com/harnyx/harnyx/main/README.md) frames deep
research as more than one reasoning step. It describes research work as decomposition, retrieval,
ranking, cross-checking, and synthesis under constraints. In subnet terms, the deliverable is a
research workflow that can answer assigned questions with stronger evidence and reasoning than a
plain response generator.

The task shape is a research-style query paired with a stronger reference answer. That reference
answer gives validators something to compare miner responses against. The questions are mixed across
factual recall, explanation, comparison, and synthesis, which pushes miners toward agents that can
search, organize, and evaluate information rather than memorizing a narrow answer set.

## Miner and Validator Roles

Miners submit research agents that answer assigned questions under the subnet's runtime constraints.
The agent is the deliverable: a miner improves by designing a workflow that produces better
researched answers across task batches.

Validators run submitted agents in sandboxed environments, score their answers against reference
answers, aggregate scores, and publish weights on-chain. The public
[Harnyx benchmark dashboard](https://dashboard.harnyx.ai/benchmark) exposes benchmark history and
run detail, giving a public view into recent evaluation results rather than leaving the evaluation
loop entirely opaque.

## Evaluation Context

Harnyx's evaluation loop is built around batches. The platform sends miner-task batches to
validators; validators execute agent-task combinations, score the returned answers, and report the
scored runs back to the platform. This keeps the scoring unit close to the actual research workflow:
an agent receives a question, produces an answer, and is judged against the reference answer for
that task.

The README also describes champion selection as separate from simply picking the highest single
batch score. A challenger must clear a dethroning rule before replacing the incumbent champion, such
as beating the incumbent by enough margin or matching quality while improving runtime or cost. That
design favors sustained improvement over one-off score noise.

This makes Harnyx different from a static question-answer leaderboard. The subnet is selecting for
research agents that can repeatedly turn questions into sourced, synthesized answers under
controlled evaluation, while validators keep the comparison tied to reference answers and public
benchmark records.

## Participant Emission Context

The Harnyx README separates champion selection from participant emission. Champion emission follows
the latest champion weights, while participant emission looks at the latest terminal source batch
that includes artifacts. This means the subnet can keep rewarding the incumbent champion while also
using recent artifact-backed participation to decide how additional miner emission is distributed.

That distinction matters because a miner can affect the participant-emission side without becoming
the new champion. The README describes failed terminal batches with artifacts as still counting for
participant emission, while initializing batches, running batches, and terminal batches without
artifacts do not update the participant source. In other words, the reward logic depends on whether
a completed batch produced usable artifacts, not only on whether a challenger dethroned the
incumbent.

Successful terminal batches add another layer. The README describes participant emission as tiered
by normalized artifact score: high-scoring eligible participants receive a larger share, remaining
positive-score participants receive a base share, and zero-score participants receive none. The
owner UID receives the final remainder and unregistered participant shares. This keeps the
participant component tied to recent scored evidence while preserving a defined sink for emission
that cannot be assigned to registered participant UIDs.

The public benchmark dashboard is useful in that context because it exposes benchmark history and
run detail. It helps readers distinguish the live research-agent evaluation record from the final
on-chain weights. The benchmark record shows the scored task runs; the emission logic then turns
champion status and eligible participant evidence into the weights validators can submit.

The README also states that completed terminal batches without successful scoring evidence burn
participant emission rather than falling back to older monitoring rows. If no terminal source batch
with artifacts exists, only the champion component remains active. That keeps the participant side
anchored to fresh artifacts instead of stale participation records.
