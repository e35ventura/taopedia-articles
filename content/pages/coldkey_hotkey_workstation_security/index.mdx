# Coldkey and Hotkey Workstation Security

Coldkey and hotkey workstation security is the practice of matching Bittensor wallet operations to
the right device and key environment. The official
[Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)
guide frames this as a tiered risk model: public read-only work, hotkey operations, proxy coldkey
operations, and primary coldkey custody should not be treated as the same security situation.

## What It Represents

Workstation security is about **authority boundaries**, not only whether a machine is online. The
guide separates four tiers
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)):

- **Permissionless workstations** — read-only work on public chain data without loading private
  keys.
- **Hotkey workstations** — operational hosts that sign mining, validation, and weight-related work.
- **Proxy coldkey workstations** — internet-connected machines that act through scoped, optionally
  delayed proxies instead of holding the primary coldkey.
- **Primary coldkey custody** — the highest-risk tier that controls balances, stake, hotkey
  management, and governance-sensitive actions.

A permissionless device can inspect balances, stake, validators, and subnet state using public
information alone. If a task can be done without signing, it belongs in the lowest-risk tier
([Wallets, Coldkeys and Hotkeys in Bittensor](https://docs.learnbittensor.org/keys/wallets)).

The primary coldkey should remain in a hardware or offline signing environment whenever possible.
BTCLI and the SDK can run on connected machines, but loading primary coldkey authority into those
environments is the risk the guide narrows through proxy relationships
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).

Proxy scope and delay reduce authority and timing risk compared with exposing the primary coldkey on
the same host, but proxy separation is risk reduction rather than coldkey replacement. A delayed
proxy only helps when someone monitors pending announcements; without review, a delay may only
postpone unauthorized activity
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).

Hotkeys do not directly control the full coldkey balance, so a compromised hotkey is not the same as
a compromised primary coldkey. Operational hosts still need availability, monitoring, and a
mitigation plan when a hotkey may have leaked. The documented leak response is hotkey rotation
rather than continuing to sign with the suspected key; coldkey swap applies when the primary coldkey
itself must migrate
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security),
[Rotate or Swap your Coldkey](https://docs.learnbittensor.org/keys/coldkey-swap)).

Private keys should not live in code repositories, version control, build artifacts, or deployment
configs. Workstation security includes where key material is stored, not only which device signs
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).

Wallet applications are interfaces; the risk tier depends on whether the environment can only view
public information, sign with a hotkey, act through a scoped proxy, or hold primary coldkey custody
([Wallets, Coldkeys and Hotkeys in Bittensor](https://docs.learnbittensor.org/keys/wallets)).

## How Little the Primary Coldkey Has to Sign

The model is built so the highest-authority key is used as rarely as possible. The security guidance
states that only two operations strictly require the primary coldkey: creating the very first proxy
relationship on a new coldkey, and rotating to a new coldkey. Everything else, including rejecting a
pending proxy announcement, can be done through a NonTransfer proxy, which is what lets the coldkey
stay in offline custody for routine work
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).

The same guidance contrasts two offline signing devices for that custody. A Ledger used with a
compatible wallet app supports only a limited operation set, while Polkadot Vault keeps the key on
an air-gapped phone and exchanges transactions exclusively by QR code, and unlike Ledger it can
decode and sign any Subtensor extrinsic
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).

## Development Stage Context

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. Workstation
security examples should be read against that network boundary: localnet and testnet key exercises
do not carry the same custody stakes as mainnet, where tiers protect live TAO and stake
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks),
[Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).

## Distinction from Ledger Hardware Wallet

Workstation security and a Ledger hardware wallet are a model and a tool that supports it.
Workstation security is the practice of matching each operation to the right device and key
authority, while a Ledger is one hardware device used to keep the primary coldkey in offline signing
custody within that model
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security),
[Using Ledger Hardware Wallet](https://docs.learnbittensor.org/staking-and-delegation/using-ledger-hw-wallet)).

- **Workstation security** — the model of which authority belongs on which device.
- **Ledger hardware wallet** — one hardware device for offline coldkey custody.

## Distinction from Multisig

Workstation security and multisig reduce different risks. Workstation security limits where key
material lives and runs, while a multisig wallet requires several signers so no single device or
person can act alone for a shared high-authority coldkey
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security),
[Secure your Coldkey with a Multisig Wallet](https://docs.learnbittensor.org/keys/multisig)).

- **Workstation security** — where keys are allowed to live and sign.
- **Multisig** — requiring multiple signers so no single actor acts alone.

## Distinction from Encrypting the Hotkey

Workstation security and encrypting the hotkey protect operational keys at different layers. Coldkey
and hotkey workstation security is the practice of keeping the coldkey off internet-exposed machines
while hotkeys run on operational hosts, while encrypting the hotkey is at-rest protection that locks
the hotkey keyfile behind a password on whatever host holds it
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security),
[Glossary: Encrypting the Hotkey](https://docs.learnbittensor.org/resources/glossary#encrypting-the-hotkey)).

Encryption complements host separation rather than replacing the rule that coldkey material stays
off operational machines.

- **Workstation security** — where key material is allowed to live and run.
- **Encrypting the hotkey** — at-rest password protection for a stored hotkey keyfile.

## Distinction from Regenerating a Key

Workstation security keeps each operation on the device and authority tier that fits its risk, while
regenerating a key is the recovery process of recreating a lost or deleted coldkey or hotkey from
its associated mnemonic
([Glossary: Regenerating a Key](https://docs.learnbittensor.org/resources/glossary#regenerating-a-key)).

- **Workstation security** — a prevention practice about where keys may sign.
- **Regenerating a key** — a recovery step taken after a key is lost.

## Distinction from Wallet Address

Workstation security governs where signing authority lives, while a wallet address is the public,
public-key-derived identifier used as a destination for sending and receiving TAO
([Glossary: Wallet Address](https://docs.learnbittensor.org/resources/glossary#wallet-address)).

- **Workstation security** — protects the secret signing side across devices.
- **Wallet address** — the shareable public destination, safe to expose.

## Distinction from Yuma Consensus

Coldkey and hotkey workstation security matches wallet operations to device risk tiers so custody
keys stay separated from online operational keys. It names custody practice vocabulary, not the
on-chain step that turns validator weight submissions into emission shares
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).

Yuma Consensus is the on-chain process that converts submitted validator weights into emission
shares after evaluation completes
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Coldkey and hotkey workstation security** — tiered device-risk model for wallet keys.
- **Yuma Consensus** — on-chain weight aggregation that settles emissions.

## Reader Boundary

This article explains the security model, not a device-hardening checklist. It does not provide
commands, recovery procedures, proxy setup steps, or vendor-specific instructions. The core idea is
to keep observation, hotkey operation, proxy authority, and primary coldkey custody in different
risk categories
([Coldkey and Hotkey Workstation Security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).
