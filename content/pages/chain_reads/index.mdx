# Chain Reads

Chain reads are read-only interactions with Bittensor's blockchain layer, Subtensor. They let a
reader inspect public chain state without asking the runtime to record a change.

The official [Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees) page
separates free chain reads from state-changing actions that can carry fees. That distinction makes
chain reads a useful boundary concept for reading balances, subnet state, blocks, events, or other
public chain information without confusing observation with submission.

## Read-Only Boundary

A chain read answers a question about state that already exists on the connected chain. It does not
move tokens, alter stake, register a participant, change weights, or request any other state update.
Those actions belong to the submission side of the network.

This boundary matters because public chain information can often be inspected without exposing
signing authority. Reading a value from Subtensor is different from authorizing the chain to accept
a new action.

Reference: [Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)

## Fee Context

Bittensor's fee documentation identifies chain reads as free. In the same fee model, submitted
state-changing actions may carry base transaction fees, swap fees, or other action-specific costs
depending on what the runtime processes.

For Taopedia readers, the practical lesson is narrow: a read-only look at public chain state is not
the same kind of activity as a transaction-like action. Fee discussions should therefore name
whether the activity is only reading state or asking the chain to change it.

Reference: [Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)

## Relationship to Extrinsics

The official [Subtensor extrinsics](https://docs.learnbittensor.org/subtensor-api/extrinsics)
reference lists submitted runtime methods. An extrinsic is the action side of the distinction: it is
sent to the chain so the runtime can process a requested operation.

A chain read sits on the other side. It observes chain state without becoming a submitted
state-changing request. This is why an article about an extrinsic should discuss authority,
processing, and possible fees, while an article about a chain read should focus on what public state
is being observed.

References: [Subtensor extrinsics](https://docs.learnbittensor.org/subtensor-api/extrinsics),
[Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)

## Relationship to Storage

The official [Subtensor Storage](https://docs.learnbittensor.org/subtensor-api/storage) reference
organizes queryable runtime state by area. Storage entries are one way chain state is made available
for inspection.

This does not mean a storage reference is a tutorial, a live value, or a complete behavioral
description of the feature behind an entry. It is a map of public state that can be read in the
context of the current chain and runtime.

Reference: [Subtensor Storage](https://docs.learnbittensor.org/subtensor-api/storage)

## Network Context

A chain read is scoped to the network endpoint being inspected. The
[Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet contexts, and each one has its own state history.

For readers, this means a read from one network should not be treated as proof of the same value on
another network. A mainnet read, a testnet read, and a localnet read all use the same read-only
concept, but the result belongs to the chain that was actually inspected.

Reference: [Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)

## Reader Boundary

This article defines the concept, not a command sequence, endpoint recommendation, wallet guide, or
live-chain report. Exact storage names, runtime methods, and network values should be checked
against the current official references and the specific network being inspected.
