# BTCLI

BTCLI is the Bittensor command-line interface. The official
[Bittensor CLI Overview](https://docs.learnbittensor.org/btcli/overview) describes `btcli` as the
command-line way to interact with the Bittensor network and its subnets, including wallets, TAO
balances, transfers, staking, unstaking, node registration, governance functions, and related
operations.

For Taopedia readers, BTCLI is best understood as an interface layer. It does not define Bittensor's
consensus rules, wallet roles, or subnet economics by itself. Instead, it exposes actions and reads
that connect a user's local environment to [[subtensor|Subtensor]], wallets, subnets, and network
roles.

## Interface Role

BTCLI sits between a user and Bittensor's chain-facing workflows. A reader may use it to inspect
public chain information, manage wallet-related context, submit signed actions, or interact with
subnet and governance functions. The official
[BTCLI reference](https://docs.learnbittensor.org/btcli) is the current source for exact command
names and options.

This article does not reproduce that command reference. The more durable concept is that BTCLI
groups many Bittensor workflows behind one command-line surface, while the underlying authority
still comes from keys, balances, roles, and the selected network endpoint. A BTCLI result should
therefore be read in the context of the network it targets, such as mainnet, testnet, or a local
development chain.

## Command Families

The official reference organizes BTCLI into command families such as configuration, wallet, stake,
lock, sudo, subnets, weights, proxy, crowdloan, liquidity, axon, utilities, and view commands. Those
families are useful as a map of scope: BTCLI covers more than wallet transfers and less than the
entire Bittensor protocol.

For readers, a command family is a navigation aid rather than a permission guarantee. A read-only
wallet view, a stake movement, and a validator weight submission all pass through BTCLI, but they do
not carry the same risk or signing requirements.

## Wallet Context

BTCLI works closely with [[wallets|Bittensor Wallets]], coldkeys, and hotkeys. The official overview
lists wallet management, balances, transfers, staking, and unstaking among the tool's common uses,
while the wallet docs explain the coldkey and hotkey roles that give those actions their security
meaning.

This makes BTCLI a wallet interface, not a replacement for wallet security. A command that touches a
wallet is still governed by whether the relevant public key, hotkey private key, or coldkey private
key is present and appropriate for the action.

## Permissionless Reads

Some BTCLI activity is read-only. The official
[BTCLI Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions) explains that
some functions require no private key at all and can rely on public information. These reads can
inspect public wallet, subnet, miner, validator, balance, and stake information without authorizing
state changes.

For readers, this separates observation from control. Reading public chain state through BTCLI is
not the same as transferring TAO, changing stake, registering a hotkey, setting weights, or taking a
governance action.

## Signed Actions

Other BTCLI actions submit signed requests to the chain. The permissions guide distinguishes
coldkey-required actions from hotkey-required actions and explains that the key type changes the
risk model. Coldkeys are ownership-sensitive, while hotkeys support operational activity for miners
and validators.

This is why the same CLI can belong in different security contexts. A permissionless workstation, a
hotkey workstation, and a coldkey workstation may all run BTCLI, but they should not be treated as
equivalent environments. The tool surface is shared; the available authority is not.

## Resource and Role Checks

BTCLI also exposes workflows that depend on balances, fees, registration burns, validator permits,
subnet roles, or Senate participation. The permissions guide separates these requirements from the
simple question of whether a key can sign. A user can have the correct signer but still lack the
resource or network role needed for the requested action.

This distinction helps explain many failed or unavailable operations. A command-line interface can
prepare and submit a request, but Subtensor still enforces chain rules, balances, rate limits,
registration state, validator status, and governance eligibility.

## Reader Boundary

BTCLI should not be read as an installation guide, a complete command table, or a recommendation to
place sensitive keys on a general-purpose machine. The current command syntax, options, and
permission matrix belong in the official reference pages.

At Taopedia level, the useful summary is that BTCLI is the command-line interface for Bittensor
operations, and that each operation must still be interpreted through its network, wallet,
authority, resource, and role boundaries. The interface can expose protocol concepts such as
extrinsics, transaction fees, subnet hyperparameters, and validator weights, but each concept still
has its own chain-level meaning. [[btcli_permissions|BTCLI Permissions]] covers the narrower
authority model behind those actions.
