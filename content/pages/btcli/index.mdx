# BTCLI

BTCLI is the Bittensor command-line interface. The official
[Bittensor CLI Overview](https://docs.learnbittensor.org/btcli/overview) describes it as a way to
interact with the Bittensor network and its subnets from the command line. The overview places
wallets, balances, transfers, staking, unstaking, node registration, governance, and subnet activity
inside that command-line scope.

For readers, BTCLI is useful as an interface concept. It names one of the standard ways a user,
miner, validator, subnet creator, or governance participant can interact with Bittensor. It is not a
separate protocol layer and does not replace the chain rules, wallet model, or security requirements
behind each action.

## Interface Layer

BTCLI sits at the user-facing edge of Bittensor tooling. It can be used for public inspection tasks,
wallet-related tasks, staking-related tasks, subnet operations, and governance-adjacent workflows.
The exact current syntax belongs in the official reference pages, because command options and
subcommands can change as the tooling changes.

At Taopedia level, the durable idea is the boundary between interface and authority. BTCLI gives a
command-line surface for asking the network questions or submitting requests. The network still
decides what state exists, what actions are valid, which signatures are required, and whether the
account has the needed role or balance.

## Wallet Context

BTCLI is closely tied to the Bittensor wallet model. The official overview names wallet management,
balances, transfers, staking, and unstaking as common uses, while the official wallet docs explain
that Bittensor wallets use coldkey and hotkey roles. Those roles matter more than the fact that the
same local tool can display or initiate several different workflows.

This is why BTCLI should not be treated as a single permission level. A public wallet view, a hotkey
operation, and a coldkey-owned action can all be reached through the tool, but they represent
different kinds of authority. The relevant question is which key material or public information is
being used for the specific task.

## Read and Write Boundary

Some BTCLI uses are read-only. The official
[BTCLI Permissions Guide](https://docs.learnbittensor.org/btcli/btcli-permissions) explains that
some functions require no private key and can rely on public information. This makes BTCLI useful
for inspecting public wallet, subnet, validator, miner, balance, and stake information without
authorizing a state change.

Other uses submit signed actions. A signed action may affect balances, stake, hotkey associations,
subnet participation, validator behavior, or governance records. The difference between reading and
signing is therefore central to understanding BTCLI. The tool may be the same, but the risk changes
when a private key or chain-altering request is involved.

## Key Authority

The permissions guide separates coldkey authority, hotkey authority, and public-key use. Coldkey
authority is ownership-sensitive and covers high-impact wallet and staking actions. Hotkey authority
is operational and is associated with miner and validator activity. Public-key use supports
inspection without private signing authority.

That separation helps avoid a common mistake: assuming that a device capable of running BTCLI should
also hold every key. A command-line interface can exist on several workstation types, but a
permissionless workstation, a hotkey workstation, and a coldkey workstation have different security
profiles. The useful security question is which authority a task requires and whether that authority
belongs on the machine being used.

## Network Context

BTCLI commands are interpreted against a selected network or endpoint. The official documentation
uses network names and endpoints to distinguish mainnet, test, and local or custom contexts. A
result from one network should not be treated as a live fact about another network.

This matters when reading balances, subnet data, registrations, or governance state. The command
line may look similar across environments, but the underlying chain history, runtime state, and test
fixtures can be different. A careful article should name the network context when it makes a
specific factual claim.

## Resource and Role Requirements

BTCLI can expose workflows that require more than a key. The permissions guide notes that some
actions depend on available liquidity, stake, registration costs, validator permits, subnet roles,
or Senate participation. Having a signer is not always the same as being eligible to complete the
requested operation.

For readers, this means an unavailable action is not necessarily a local tool problem. The chain may
reject or block a request because the account lacks a role, lacks the necessary balance, is outside
a rate-limit window, or does not satisfy another runtime condition.

## Reader Boundary

BTCLI should be read as the command-line interface for Bittensor operations, not as the complete
source of Bittensor behavior. The official reference and permissions pages are the right place for
current command names, options, and exact requirements.

This article provides the concept boundary only: BTCLI is the interface; Bittensor wallets,
Subtensor state, network context, key authority, balances, roles, and runtime rules determine what a
specific BTCLI action can actually do.
