Proxy wallets are a Bittensor security pattern where one account is allowed to act on behalf of
another account. The [Proxies overview](https://docs.learnbittensor.org/keys/proxies) describes the
protected account as the safe wallet and the acting account as the proxy wallet.

The goal is controlled delegation. A user can keep the more sensitive wallet in a higher-security
environment while allowing a separate proxy account to perform selected operations under a narrow
permission scope
([Proxies overview](https://docs.learnbittensor.org/keys/proxies),
[Wallets, Coldkeys and Hotkeys](https://docs.learnbittensor.org/keys/wallets)).

## Why Proxies Matter

The [wallets guide](https://docs.learnbittensor.org/keys/wallets) explains that Bittensor wallets
use coldkey and hotkey roles for different kinds of authority. Proxy wallets add another layer: a
safe wallet can delegate limited action authority to a proxy account rather than being used directly
for every supported operation.

The security value comes from limits. The
[Proxies overview](https://docs.learnbittensor.org/keys/proxies) describes proxy types that restrict
which categories of calls a proxy can make. It also describes optional delay and announcement
behavior, which can give the safe wallet holder time to reject a pending proxy action.

Proxy wallets reduce key exposure rather than eliminate all risk. The security gain depends on how
narrowly the proxy's authority is scoped and whether the safe wallet holder monitors proxy actions
([Proxies overview](https://docs.learnbittensor.org/keys/proxies),
[Coldkey and hotkey workstation security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).

## Safe Wallet and Proxy Wallet

The safe wallet is the account being protected. The
[Working with proxies](https://docs.learnbittensor.org/keys/proxies/working-with-proxies) guide
emphasizes that the safe wallet and proxy wallet are separate accounts and that both require careful
key handling.

The proxy wallet is the account granted delegated authority. A proxy relationship is most useful
when its scope matches the intended operational task. The safe wallet remains the ownership anchor
that controls assets and can revoke proxy authority, while the proxy wallet holds delegated
operating access constrained by the proxy type
([Working with proxies](https://docs.learnbittensor.org/keys/proxies/working-with-proxies),
[Proxies overview](https://docs.learnbittensor.org/keys/proxies)).

## Scoped Permissions

The [Proxies overview](https://docs.learnbittensor.org/keys/proxies) groups proxy permissions into
narrow categories rather than granting blanket control of the safe wallet. A broad proxy can mirror
most safe-wallet authority, while narrower staking-only or governance-only permissions limit what the
acting account may do on behalf of the protected wallet.

Choosing the narrowest permission that still covers the intended task reduces blast radius if a
proxy key is misused. Some proxy types also support optional delay and announcement behavior, which
can give the safe wallet holder time to reject a pending action before it executes
([Proxies overview](https://docs.learnbittensor.org/keys/proxies)).

## Proxies and Staking

Staking activity is a common reason a coldkey must sign online. The proxy pattern lets a separate
account perform staking-related actions under a narrow permission scope while the coldkey remains in
a higher-security environment ([Proxies overview](https://docs.learnbittensor.org/keys/proxies),
[Staking and delegation overview](https://docs.learnbittensor.org/staking-and-delegation/delegation)).

Official wallet-security prose treats scoped proxies as a way to limit coldkey exposure during
repeated staking actions. A staking-scoped proxy still requires careful key handling, but it
reduces how much custody authority is exposed when staking activity is frequent
([Coldkey and hotkey workstation security](https://docs.learnbittensor.org/keys/coldkey-hotkey-security)).

## Announcement and Delay

Some proxy configurations announce an upcoming action before executing it after a configured delay
([Proxies overview](https://docs.learnbittensor.org/keys/proxies)). That pattern can give the safe
wallet holder review time, but the delay only helps when someone is actively watching for pending
announcements ([Working with proxies](https://docs.learnbittensor.org/keys/proxies/working-with-proxies)).

Announcement and delay are part of the proxy security model rather than automatic protection. They
reduce surprise execution; they do not replace narrow scoping, proxy key hygiene, or the safe wallet's
ability to revoke delegated authority.

## Related Wallet Concepts

Proxy wallets should be read beside nearby custody vocabulary rather than as a stand-alone permission
to ignore other wallet design choices. A coldkey remains the custody anchor that controls balances and
owns hotkeys, while a proxy wallet names scoped delegation that reduces how often that coldkey must
sign directly
([Wallets, Coldkeys and Hotkeys](https://docs.learnbittensor.org/keys/wallets),
[Glossary: Coldkey](https://docs.learnbittensor.org/resources/glossary#coldkey)).

Coldkey swap is a different idea: it permanently migrates controlling coldkey identity rather than
granting temporary scoped permission
([Coldkey Swap](https://docs.learnbittensor.org/keys/coldkey-swap)). Multisig wallets require shared
approval from multiple signers rather than one scoped acting account
([Secure your Coldkey with a Multisig Wallet](https://docs.learnbittensor.org/keys/multisig)). Pure
proxies are keyless stand-ins used mainly for multisig continuity when membership rotates
([Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies)). Staking
proxy attacks name misuse risk when a staking-scoped proxy is compromised
([Avoid Staking Proxy Attacks](https://docs.learnbittensor.org/learn/avoid-staking-proxy-attacks)).

## Distinction from Yuma Consensus

Proxy wallets let one Bittensor account perform scoped actions on behalf of a protected account.
They name delegated signing vocabulary, not subnet settlement after validator evaluation
([Proxies overview](https://docs.learnbittensor.org/keys/proxies),
[Working with proxies](https://docs.learnbittensor.org/keys/proxies/working-with-proxies)).

Yuma Consensus is the on-chain process that converts submitted validator weights into emission
shares after evaluation completes. A proxy may submit allowed calls for a safe wallet; Yuma Consensus
names how weights become emission shares on a subnet
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Emission](https://docs.learnbittensor.org/learn/emissions)).

Readers should keep proxy delegation vocabulary separate from settlement vocabulary. Proxy wallets
answer who may act for a protected account; Yuma Consensus answers how validator weights become
emission shares in a subnet
([Proxies overview](https://docs.learnbittensor.org/keys/proxies),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

## Reader Boundary

Proxy wallet should not be read as coldkey replacement, multisig threshold control, or proof of full
wallet authority. It names scoped delegation where a separate account can submit limited call types
on behalf of a protected coldkey ([Proxies overview](https://docs.learnbittensor.org/keys/proxies)).
