# Proxy Wallets

Proxy wallets are delegated accounts that can perform permitted Bittensor actions for another
account. The official [Proxies overview](https://docs.learnbittensor.org/keys/proxies) describes
this as a way to let one wallet act on behalf of another, while the
[wallets guide](https://docs.learnbittensor.org/keys/wallets) frames wallets as the tools that sign
transactions, access TAO, and manage stake. For Taopedia readers, the main idea is simple: a proxy
can reduce how often a high-value coldkey needs to be active for routine operations.

## What Proxy Wallets Do

A proxy relationship separates the protected account from the account used for selected actions. The
protected account is often called the real account or safe wallet, while the proxy account is the
delegated account. Once the relationship exists, the proxy can submit calls on behalf of the real
account only within the permissions granted to it.

This makes proxies different from sharing a seed phrase or moving all authority into a hot wallet.
The [Proxies overview](https://docs.learnbittensor.org/keys/proxies) ties the model to coldkey
security: the valuable wallet can remain in safer storage while a separate account handles a narrow
operational role.

## Permission Boundaries

Proxy security depends on permission scope. Bittensor proxy relationships use `ProxyType` to filter
which calls the delegated account can make. The official proxy documentation lists scopes such as
staking, transfer, registration, hotkey swap, child-key management, owner operations, and broader
non-transfer or unrestricted modes.

The important Taopedia distinction is least privilege. A proxy should be scoped to the actions it
actually needs, because an unrestricted proxy has much more authority than a staking-only or
registration-only proxy. The official docs warn that proxies only improve security when their scope
and delay settings are chosen carefully.

## Delays And Revocation

Proxy relationships can also use delays. With a non-zero delay, a proxy action must be announced
before it can execute, giving the protected account time to review and reject an unwanted action.
This is why the [wallets guide](https://docs.learnbittensor.org/keys/wallets) describes proxies as
limited, delayed operations that can help protect a coldkey.

The real account retains control over the relationship. According to the
[Proxies overview](https://docs.learnbittensor.org/keys/proxies), it can remove a proxy entry and
disable the delegated account's ability to act on its behalf.

## Coldkeys, Hotkeys, And Operations

Proxy wallets fit into the same security model as [[wallets_coldkey_hotkey|coldkeys and hotkeys]].
Coldkeys control sensitive wallet authority, while hotkeys are used for miner and validator
operations. A proxy adds another account relationship for cases where a coldkey should stay offline
or in a more protected environment, but selected wallet operations still need to happen.

Common examples include staking operations, subnet operations, and organizational delegation. Those
use cases are described in the official proxy documentation, and they belong beside
[[coldkeys|Coldkeys]], [[hotkeys|Hotkeys]], and [[staking_and_delegation|Staking and Delegation]] as
part of Bittensor operational security.

## Security Context

A proxy wallet is not a substitute for secure key handling. It narrows which account needs to be
active for a task, but the delegated account still signs transactions within the authority it has
been given. If the proxy has broad permissions or no delay, compromise of the proxy account can
still be serious.

For that reason, proxy-wallet claims should specify the protected account, the delegated account,
the permission scope, and whether a delay is used. Without those details, "using a proxy" is too
vague to describe the actual security boundary.
