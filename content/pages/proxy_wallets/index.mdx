Proxy wallets are a Bittensor security pattern where one account is allowed to act on behalf of
another account. The [Proxies overview](https://docs.learnbittensor.org/keys/proxies) describes the
protected account as the safe wallet or real account, and the acting account as the proxy wallet.

## What It Represents

The goal is controlled delegation. A user can keep the more sensitive wallet in a higher-security
environment while allowing a separate proxy account to perform selected operations under a scoped
proxy type such as `NonTransfer`, `Staking`, or `Governance`
([Proxies overview](https://docs.learnbittensor.org/keys/proxies)).

Readers should separate two "proxy" ideas that sound similar:

- **Proxy wallet** — scoped delegation where one account performs limited operations for a protected
  coldkey.
- **Pure proxy** — keyless stand-in account that keeps a multisig member slot stable when signers
  rotate.

Proxy wallets answer routine delegated access. Pure proxies answer stable shared-wallet membership
([Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies)).

Scoped authority reduces coldkey exposure, but limited permission is not the same as no risk. A
compromised proxy can still perform the actions its proxy type allows, which is why
[staking proxy attacks](https://docs.learnbittensor.org/learn/avoid-staking-proxy-attacks) name
misuse of narrowly scoped staking authority rather than full-wallet compromise
([Proxies overview](https://docs.learnbittensor.org/keys/proxies)).

[Managing Your Stakes](https://docs.learnbittensor.org/staking-and-delegation/managing-stake-sdk)
describes proxy-based staking as the recommended approach for mainnet, in contrast to signing
staking actions directly from a coldkey.

Proxy examples depend on which network you connect to. Delegation state from one environment should
not be read as production behavior on another
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

## An Account Is Capped at Twenty Proxies

The number of proxies an account can delegate to is bounded. The proxies documentation states that
each account can register up to 20 proxies in total, so authority cannot be spread across an
unlimited set of delegate keys, and a single account can hold at most 75 pending announcements at a
time ([Proxy Accounts](https://docs.learnbittensor.org/keys/proxies)).

The same documentation also notes who absorbs the cost: by default the delegate, not the protected
account, pays the transaction fees for the proxy calls it submits
([Proxy Accounts](https://docs.learnbittensor.org/keys/proxies)).

Beyond those per-call fees, registering proxies also reserves a refundable deposit. The constants
reference lists `api.consts.proxy.proxyDepositBase` as `60000000` rao (about 0.06 TAO) plus
`api.consts.proxy.proxyDepositFactor` as `33000000` rao (about 0.033 TAO) for each proxy, so the
reserved amount grows with the number of proxies and is returned once they are removed
([Subtensor Constants: proxyDepositBase](https://docs.learnbittensor.org/subtensor-api/constants#proxydepositbase-u64),
[Proxy Accounts](https://docs.learnbittensor.org/keys/proxies)).

Delayed proxy calls use a separate announcement deposit. The same constants reference lists
`api.consts.proxy.announcementDepositBase` as `36000000` rao (about 0.036 TAO) and
`api.consts.proxy.announcementDepositFactor` as `68000000` rao (about 0.068 TAO). Those values
belong to pending proxy announcements, not to the count of registered proxy delegates
([Subtensor Constants: announcementDepositBase](https://docs.learnbittensor.org/subtensor-api/constants#announcementdepositbase-u64),
[Working with Proxies](https://docs.learnbittensor.org/keys/proxies/working-with-proxies)).

## A Proxy Type Bounds Authority by Amount and Immediacy

Beyond naming a permission category, a proxy type can also limit the size and the timing of what a
proxy may do. The working-with-proxies guidance notes that a SmallTransfer proxy only authorizes
transfer amounts that do not exceed 0.5 TAO, whereas the most permissive case is a proxy with type
Any and a delay of zero, which can immediately perform any operation on behalf of the safe wallet.
The configured delay is the counterweight to that reach: a non-zero delay creates a window during
which the safe wallet can cancel transactions that implement attacks before they execute
([Working with Proxies](https://docs.learnbittensor.org/keys/proxies/working-with-proxies)).

`NonTransfer` is a narrower authority pattern than `Any`. Batch-transaction guidance recommends it
for batch staking because it blocks balance transfers and coldkey swaps while still allowing batch
wrappers, so it can support grouped staking workflows without granting full transfer authority
([Batch Transactions](https://docs.learnbittensor.org/learn/batch-transactions),
[Proxies overview](https://docs.learnbittensor.org/keys/proxies)).

## Delay Protects Pending Actions, Not Removal

Optional delay and announcement behavior can give the safe wallet holder time to reject a pending
proxy action before it executes
([Working with Proxies](https://docs.learnbittensor.org/keys/proxies/working-with-proxies)).

That delay governs how soon a proxy may act after a call is announced. It does not notify the holder
automatically. Delay protection therefore requires active monitoring rather than assuming the chain
will block misuse on its own
([Working with Proxies](https://docs.learnbittensor.org/keys/proxies/working-with-proxies)).

Readers should not confuse proxy-action delay with removal timing. Delay is a control on pending
proxy work; removal is a separate cut-off step when authority should end.

## Removal Revokes Authority Immediately

Once compromise is suspected, the guidance is to rotate or remove the affected proxy rather than
treating limited authority as a reason to wait
([Avoid Staking Proxy Attacks](https://docs.learnbittensor.org/learn/avoid-staking-proxy-attacks),
[Working with Proxies](https://docs.learnbittensor.org/keys/proxies/working-with-proxies)).

Proxy removal is immediate and independent of any configured delay. Removing a proxy revokes the
proxy account's permission to act on the primary account right away, even when that proxy was
originally set up with a delay before it could act
([Working with proxies](https://docs.learnbittensor.org/keys/proxies/working-with-proxies)).

A protected account does not have to wait out a proxy's delay window to cut off further misuse.
Assume relevant activity occurred until verified otherwise when a staking or other scoped proxy may
have been exposed.

## Distinction from Coldkey

A coldkey controls TAO balances and owns hotkeys. A proxy wallet is the delegated-authority pattern
that lets a separate account perform limited operations without exposing the coldkey directly
([Glossary: Coldkey](https://docs.learnbittensor.org/resources/glossary#coldkey),
[Proxies overview](https://docs.learnbittensor.org/keys/proxies)).

- **Coldkey** — the custody anchor that controls balances and owns hotkeys.
- **Proxy wallet** — scoped delegation that limits how often the coldkey must sign directly.

## Distinction from Coldkey Swap

A proxy wallet grants scoped authority without changing which coldkey controls the wallet. Coldkey
swap migrates on-chain identity to a new coldkey address
([Coldkey Swap](https://docs.learnbittensor.org/keys/coldkey-swap),
[Proxies overview](https://docs.learnbittensor.org/keys/proxies)).

- **Proxy wallet** — delegated permission without changing coldkey ownership.
- **Coldkey swap** — permanent migration of the controlling coldkey and its hotkey state.

## Distinction from Multisig

A proxy account acts for a safe wallet under a scoped proxy type. A multisig wallet requires
approvals from multiple signers before action
([Proxies overview](https://docs.learnbittensor.org/keys/proxies),
[Secure your Coldkey with a Multisig Wallet](https://docs.learnbittensor.org/keys/multisig)).

- **Proxy wallet** — scoped delegation where one account acts for another under a proxy type.
- **Multisig** — shared-approval custody where multiple signers must approve before action.

## Distinction from Pure Proxies

Proxy wallets delegate limited authority for day-to-day operations. Pure proxies are keyless
stand-ins used mainly in multisig structures to keep an address stable when membership changes
([Proxies overview](https://docs.learnbittensor.org/keys/proxies),
[Understanding Pure Proxies](https://docs.learnbittensor.org/keys/proxies/pure-proxies)).

- **Proxy wallets** — delegated authority from a protected account to a less sensitive one.
- **Pure proxies** — keyless stand-ins that preserve multisig address stability.

## Distinction from Staking Proxy Attacks

Staking proxy attacks name the risk when delegated staking authority is misused. Proxy wallets name
the scoped-delegation pattern that can reduce coldkey exposure when configured narrowly
([Avoid Staking Proxy Attacks](https://docs.learnbittensor.org/learn/avoid-staking-proxy-attacks),
[Proxies overview](https://docs.learnbittensor.org/keys/proxies)).

- **Staking proxy attacks** — misuse of delegated staking authority on a compromised proxy key.
- **Proxy wallet** — scoped delegation that can limit how often the coldkey signs staking actions.

## Reader Boundary

Proxy wallet should not be read as coldkey replacement, multisig threshold control, or proof of full
wallet authority. It names scoped delegation where a separate account can submit limited call types
on behalf of a protected coldkey ([Proxies overview](https://docs.learnbittensor.org/keys/proxies)).
