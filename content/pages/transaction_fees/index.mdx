# Transaction Fees

Transaction fees are costs the Bittensor chain can attach to submitted state-changing actions
([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)).

The term belongs to submitted-action cost vocabulary. It should be read separately from chain reads,
swap fees, and every other economic effect that can surround a transaction.

## Base Fee Context

The official fee documentation describes base transaction fees as having weight and length
components ([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)).

Weight is tied to computational load, while length is tied to submitted action size. This base-fee
context belongs to the chain action being submitted, not to passive observation.

That makes the base fee a submitted-action cost concept. The fee page can support claims about
weight and length components, while the extrinsics reference supports the submitted-action side of
the same boundary ([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees),
[Subtensor extrinsics](https://docs.learnbittensor.org/subtensor-api/extrinsics)).

## Chain Reads

The same source identifies chain reads as free
([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)).

That distinction matters because reading chain state does not ask Subtensor to record a state
change. Fee language should therefore stay attached to submitted actions rather than being applied
to every form of chain inspection.

Read-only inspection belongs with chain-read and storage vocabulary, not with transaction-fee
vocabulary. This keeps observation separate from submitted state-changing actions
([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees),
[Subtensor Storage](https://docs.learnbittensor.org/subtensor-api/storage)).

## Swap Fee Boundary

The fee documentation treats swap fees as separate from base transaction fees
([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)).

A stake-related action can therefore involve more than one cost concept. The base fee belongs to the
submitted chain action, while a swap fee belongs to the liquidity-linked part of the action.

That boundary helps readers avoid treating every cost in a stake-related action as the same fee.
Base transaction fees and swap fees may appear near each other, but the official fee page presents
them as distinct categories
([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)).

## Batch Context

Batch transaction fees are described as aggregating the fee behavior of inner calls and adding
batch-wrapper overhead ([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees),
[Batch Transactions](https://docs.learnbittensor.org/learn/batch-transactions)).

This means grouped submissions should still be read through their components. Grouping calls does
not erase the fee behavior of fee-bearing activity inside the batch.

The batch source is useful when the article needs the grouping context, while the fee source is
useful when the article needs the cost categories that can apply to the inner calls
([Batch Transactions](https://docs.learnbittensor.org/learn/batch-transactions),
[Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)).

## Recycling Context

The recycling and burning glossary entry describes collected transaction fees as recycled tokens
deducted from the issuance record for future emission
([Recycling and burning](https://docs.learnbittensor.org/resources/glossary#recycling-and-burning)).

That places transaction fees near issuance-accounting vocabulary. It does not make every fee claim
the same as a generic burn claim.

For reader-facing prose, recycling is the accounting destination for collected fees, not a reason to
rename the submitted-action fee itself
([Recycling and burning](https://docs.learnbittensor.org/resources/glossary#recycling-and-burning),
[Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)).

## Network Context

Bittensor documentation separates mainnet, testnet, and localnet contexts
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

Fee examples should keep the selected network attached when the claim depends on observed behavior.
The article-level concept can be stable while exact observed outcomes remain environment-specific.

This matters for examples because a fee observation belongs to the network context where the
submitted action was evaluated. The network source gives the environment boundary, while the fee
source gives the fee categories
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks),
[Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)).

## Reader Boundary

The official fee page supports claims about fee categories, free reads, batch behavior, and fee
recycling ([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)).

It is not a permanent quote for every action and not a calculator. Exact cost claims need the
submitted action, network context, and source used for that observation.

The stable article-level point is that transaction fees are cost vocabulary for submitted
state-changing actions. Read-only chain inspection, swap-fee context, batch grouping, and recycling
all add nearby boundaries without replacing that core meaning
([Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees),
[Subtensor extrinsics](https://docs.learnbittensor.org/subtensor-api/extrinsics)).
