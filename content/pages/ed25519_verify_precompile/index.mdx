# Ed25519 Verify Precompile

The Ed25519 verify precompile is a built-in contract on the Bittensor EVM that lets smart contracts
verify Ed25519 signatures. Official documentation describes it as allowing EVM smart contracts to
verify Ed25519 signatures, which are commonly used in Substrate-based chains like Bittensor.

References:
[Ed25519 Verify Precompile](https://docs.learnbittensor.org/evm-tutorials/ed25519-verify-precompile)

## What It Solves

The precompile bridges identity between the Substrate and EVM sides of Bittensor. EVM uses the H160
address format and cannot act directly on Substrate SS58 addresses, so proving control of a
Substrate key from inside an EVM contract needs help. The documentation explains that the precompile
lets the owner of a coldkey send an EVM transaction with a signed message that serves as proof of
ownership.

References:
[Ed25519 Verify Precompile](https://docs.learnbittensor.org/evm-tutorials/ed25519-verify-precompile),
[Glossary: EdDSA Cryptographic Keypairs](https://docs.learnbittensor.org/resources/glossary#eddsa-cryptographic-keypairs)

## The Verify Function

The documentation describes a `verify` function that takes the hashed message, the Ed25519 public
key, and the signature split into its two halves, the `r` commitment and the `s` response, each as a
fixed-size value. It returns a boolean indicating whether the signature is valid for that message
and public key. The contract therefore checks a signature rather than producing one.

Reference:
[Ed25519 Verify Precompile](https://docs.learnbittensor.org/evm-tutorials/ed25519-verify-precompile)

## Precompile Address

Like other EVM precompiles, this function lives at a fixed address rather than being deployed by a
user. The documentation gives its address as `0x0000000000000000000000000000000000000402`, so a
contract calls that address to reach the verify logic.

Reference:
[Ed25519 Verify Precompile](https://docs.learnbittensor.org/evm-tutorials/ed25519-verify-precompile)

## Use Case

A common use the documentation gives is verifying coldkey ownership before transferring to someone.
Because a direct SS58 transfer is not EVM-compatible, a contract can instead ask the signer to prove
they control the Substrate key, then act on that verified ownership. This connects EVM contract
logic to Substrate identity without moving the key itself.

References:
[Ed25519 Verify Precompile](https://docs.learnbittensor.org/evm-tutorials/ed25519-verify-precompile),
[Glossary: SS58 Encoded](https://docs.learnbittensor.org/resources/glossary#ss58-encoded)
