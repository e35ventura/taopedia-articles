# Metagraph Precompile

The Metagraph Precompile is a Bittensor-specific EVM precompile that lets smart contracts read
metagraph information from Bittensor. The official precompile documentation describes it as
read-only access to metagraph data about neurons, their relationships, and network state.

For Taopedia readers, the important idea is not how to call the interface. The concept is that a
contract running in Bittensor EVM can inspect selected Bittensor subnet state without that read
being the same thing as changing validator weights, registering a participant, or modifying subnet
configuration.

References:
[Metagraph Precompile](https://docs.learnbittensor.org/evm-tutorials/metagraph-precompile),
[Bittensor EVM: Examples and Precompiles](https://docs.learnbittensor.org/evm-tutorials/examples)

## Precompile Context

A precompile is a built-in smart-contract interface exposed by the EVM runtime rather than an
ordinary contract deployed by an application developer. The official Bittensor EVM precompile page
lists both standard Ethereum precompiles and Bittensor-specific precompiles.

The Metagraph Precompile belongs to the Bittensor-specific group. That means it exists to expose
Bittensor chain concepts to smart contracts running inside Bittensor EVM, not to define a new subnet
or replace the native metagraph vocabulary.

References:
[Bittensor EVM: Examples and Precompiles](https://docs.learnbittensor.org/evm-tutorials/examples),
[Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)

## What It Exposes

The metagraph is the structured view of subnet neuron state. The official metagraph documentation
describes it as a snapshot of subnet state at a particular block height, including information about
neurons and incentive-related values in a selected subnet context.

The Metagraph Precompile exposes that kind of state to EVM contracts. It is therefore best read as a
bridge from Bittensor subnet state into smart-contract logic, rather than as a separate scoring
system.

References: [The Subnet Metagraph](https://docs.learnbittensor.org/subnets/metagraph),
[Metagraph Precompile](https://docs.learnbittensor.org/evm-tutorials/metagraph-precompile)

## Read-Only Boundary

The read-only boundary is central. A contract can use the precompile to inspect metagraph
information, but reading state is different from submitting a state-changing Bittensor action. This
keeps the Metagraph Precompile conceptually closer to chain inspection than to registration,
staking, subnet management, or weight submission.

That distinction matters because Bittensor has several kinds of authority. Native wallet actions may
require hotkey or coldkey authority. EVM contract calls may involve an EVM account. A read-only
precompile access path should not be mistaken for either native wallet authority or a write
operation.

References:
[Metagraph Precompile](https://docs.learnbittensor.org/evm-tutorials/metagraph-precompile),
[Transaction Fees in Bittensor](https://docs.learnbittensor.org/learn/fees)

## Relationship to Metagraph

The metagraph is the data concept. The Metagraph Precompile is one EVM-facing access path to that
concept. A reader should keep those layers separate: the metagraph describes subnet state, while the
precompile describes how a smart contract can read some of that state from the EVM side.

This relationship is useful for contract design because contracts may need Bittensor context. It
does not change how subnet participants are identified, how validators evaluate miners, or how Yuma
Consensus turns weights into incentive outcomes.

References: [The Subnet Metagraph](https://docs.learnbittensor.org/subnets/metagraph),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)

## Relationship to Bittensor EVM

Bittensor EVM smart contracts execute on the Bittensor blockchain through an Ethereum Virtual
Machine-compatible runtime. The official EVM overview emphasizes that these contracts run on
Bittensor, not on Ethereum mainnet.

That chain context matters for the Metagraph Precompile. It is not a general Ethereum metagraph
tool. It is part of the Bittensor EVM surface for contracts that need Bittensor-specific state.

References: [Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials),
[Metagraph Precompile](https://docs.learnbittensor.org/evm-tutorials/metagraph-precompile)

## Relationship to Other Precompiles

The official precompile list separates the Metagraph Precompile from other Bittensor-specific
precompiles such as staking, subnet, neuron, and signature-verification interfaces. That separation
helps readers avoid treating every precompile as one broad permission layer.

At a concept level, the Metagraph Precompile is about reading subnet state. Other precompiles may
serve different contract-facing purposes. The name of the precompile should therefore be read with
the Bittensor concept it exposes, not just with the fact that it appears in the EVM precompile
catalog.

Reference:
[Bittensor EVM: Examples and Precompiles](https://docs.learnbittensor.org/evm-tutorials/examples)

## Interpretation Boundary

The Metagraph Precompile is not a dashboard, a validator scoring rule, or a guarantee that a
contract has complete off-chain knowledge about a subnet. It is an EVM-facing read path for
Bittensor metagraph state.

It also should not be read as a setup guide. Exact function signatures, addresses, and integration
steps belong in the official Bittensor EVM documentation. This article defines the term so readers
can understand what kind of bridge it creates between smart contracts and subnet state.
