# Weight Matrix

A weight matrix is the subnet-level collection formed from validator weight vectors. It organizes
validator-assigned weight vectors so Yuma Consensus can process them as structured consensus input
([Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

The term separates one validator's vector from the combined input set. One vector represents one
validator's relative evaluation of miner work; the matrix is the organized collection of those
vectors for the subnet consensus process.

That collection makes the term useful when the subject is subnet-level consensus input. A single
validator vector can explain one validator's view, while the matrix shows the set of validator
vectors available for Yuma processing
([Glossary: Weight Vector](https://docs.learnbittensor.org/resources/glossary#weight-vector),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

## Input Collection

Each validator [weight vector](https://docs.learnbittensor.org/resources/glossary#weight-vector) is
one evaluator's relative scores for miner work. The weight matrix arranges those vectors together so
Yuma Consensus can compare and aggregate validator signals as a group
([Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix)).

The matrix is an input structure, not a separate scoring rule. Reading across a row recovers one
validator's full vector; reading down a column gathers every validator's weight for a single miner.
That per-miner column is the direction consensus reduces when it forms a result for each miner
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

The practical reading is collection-first: a matrix belongs with the subnet and
[incentive mechanism](https://docs.learnbittensor.org/resources/glossary#incentive-mechanism) whose
validators produced the vectors. The same matrix shape can appear across subnets, but the miner work
and scoring rules give the entries their meaning
([Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism),
[Consensus-Based Weights](https://docs.learnbittensor.org/concepts/consensus-based-weights)).

When a subnet runs
[multiple incentive mechanisms](https://docs.learnbittensor.org/resources/glossary#multiple-incentive-mechanisms),
each mechanism can keep its own matrix for independent consensus calculations
([Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets)).

## Reading Order Through Yuma

A useful way to read weight-matrix vocabulary is as the first step in a fixed processing order, not
as the final reward result.

The matrix stacks independently submitted validator rows into subnet-wide input. Pre-consensus
filtering then removes ineligible rows, such as self-weights and submissions from validators without
a [validator permit](https://docs.learnbittensor.org/resources/glossary#validator-permit)
([Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch)).

Clipping compares surviving matrix values against the per-miner
[consensus score](https://docs.learnbittensor.org/resources/glossary#consensus-score) benchmark.
Outlier weights are trimmed before they count toward later miner-side
[rank](https://docs.learnbittensor.org/resources/glossary#rank) and
[trust](https://docs.learnbittensor.org/resources/glossary#trust) readings, and before bond
adjustment feeds validator-side outcomes
([Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping)).

That order keeps vocabulary straight: the matrix names grouped validator input; consensus score,
rank, trust, and validator trust name later results produced from that input
([Glossary: Validator Trust](https://docs.learnbittensor.org/resources/glossary#validator-trust)).

## Miner Trust Versus Validator Trust

Readers often conflate [trust](https://docs.learnbittensor.org/resources/glossary#trust) and
[validator trust](https://docs.learnbittensor.org/resources/glossary#validator-trust) because both
are read after Yuma processes the matrix. They answer different sides of the same clipping pass.

Trust is miner-side vocabulary. It describes how much validator support a miner retained after
outlier weights were trimmed away. Lower trust means more of the miner's pre-filter support was
removed when validator signals disagreed
([Glossary: Trust](https://docs.learnbittensor.org/resources/glossary#trust),
[Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping)).

Validator trust is validator-side vocabulary. It summarizes how much of a validator's submitted
weights survived clipping and still counted toward the consensus outcome
([Glossary: Validator Trust](https://docs.learnbittensor.org/resources/glossary#validator-trust)).

The matrix names neither trust term. It is only the stacked validator input before those post-filter
readings exist.

## How One Row Joins the Matrix

Each validator shapes one matrix row through
[weight setting](https://docs.learnbittensor.org/resources/glossary#weight-setting). The
subnet-level matrix is formed by collecting those rows for the current consensus pass, not by any
single participant publishing the full table
([Glossary: Weight Vector](https://docs.learnbittensor.org/resources/glossary#weight-vector),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

Whether a row enters the pass also depends on eligibility rules. Documentation describes removing
self-assigned weights, dropping weights tied to neurons before their latest registration, and
requiring a [validator permit](https://docs.learnbittensor.org/resources/glossary#validator-permit)
for counting submissions
([Implementation of the Yuma Consensus Epoch](https://docs.learnbittensor.org/navigating-subtensor/epoch)).

Subnet [hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters) also set an
activity cutoff in blocks within each epoch. A validator that misses that early submission window
sits out the current pass rather than joining that round of aggregation
([Subnet Hyperparameters: Activity Cutoff](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#activitycutoff)).

For readers, that means the matrix is both a data shape and a participation outcome. A row can be
absent because the validator never submitted, submitted too late, or submitted weights that
pre-consensus filtering removed before aggregation began.

## What Changes Between Raw Matrix and Final Outcomes

The matrix is only the starting collection. Several documented steps sit between stacked validator
rows and the miner and validator outcomes readers see in metagraph or emission vocabulary.

Pre-consensus filtering removes rows or cells that should not count, such as self-weights and
submissions from validators without permits. Clipping then compares surviving values against the
per-miner consensus benchmark and trims weights that exceed what stake-weighted agreement supports.

After clipping, miner-side vocabulary reads aggregated standing from the filtered columns. Validator
bonds update from clipped matrix values, and validator-side dividends later pair those bonds with
miner incentive outcomes from the same pass
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Subnet Metagraph](https://docs.learnbittensor.org/subnets/metagraph)).

That progression is why matrix documentation should not be read as rank, trust, dividend, or
incentive vocabulary. Those labels describe credited results produced after Yuma processes the
matrix, while the matrix itself names the grouped validator input at the start of the pass
([Glossary: Rank](https://docs.learnbittensor.org/resources/glossary#rank),
[Glossary: Incentives](https://docs.learnbittensor.org/resources/glossary#incentives),
[Glossary: Emission](https://docs.learnbittensor.org/resources/glossary#emission)).

When a subnet runs multiple incentive mechanisms, each mechanism can keep its own matrix through
that full path. Two matrices on the same netuid can therefore represent different evaluation
settings even if they share the same tempo cadence
([Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets),
[Glossary: Multiple Incentive Mechanisms](https://docs.learnbittensor.org/resources/glossary#multiple-incentive-mechanisms)).

Readers comparing environments should also keep network context attached. A matrix example from
localnet, testnet, or mainnet shows grouped validator input for that environment only and should not
be treated as proof of production matrix state elsewhere
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

[Tempo](https://docs.learnbittensor.org/resources/glossary#tempo) provides the recurring interval
when accumulated emissions are distributed and Yuma runs on the matrix assembled for that window.
[Commit Reveal](https://docs.learnbittensor.org/concepts/commit-reveal) can delay when freshly set
weights become visible to other validators, but it does not change what the matrix collection names
at a consensus step: grouped validator input for the selected pass
([Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix)).

A matrix example also needs mechanism context on multi-mechanism subnets. Without naming which
evaluation setting produced the rows, readers can mistake one mechanism's input for the whole subnet
consensus picture
([Glossary: Multiple Incentive Mechanisms](https://docs.learnbittensor.org/resources/glossary#multiple-incentive-mechanisms),
[Multiple Incentive Mechanisms Within Subnets](https://docs.learnbittensor.org/subnets/understanding-multiple-mech-subnets)).

## Filtering and Output Terms

The weight matrix and
[consensus score](https://docs.learnbittensor.org/resources/glossary#consensus-score) describe
different parts of the same Yuma process. The matrix collects validator weight vectors; consensus
score is the stake-weighted benchmark derived from that grouped input when clipping outlier weights
([Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix),
[Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping)).

[Rank](https://docs.learnbittensor.org/resources/glossary#rank),
[trust](https://docs.learnbittensor.org/resources/glossary#trust), and
[validator trust](https://docs.learnbittensor.org/resources/glossary#validator-trust) are later
consensus terms read after that filter step, not synonyms for the matrix itself
([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

## Timing and Mechanism Scope

Tempo and Commit Reveal add timing detail around validator weights. Tempo provides the block-based
cadence for subnet epochs, while Commit Reveal can delay visibility of newly set validator weights
([Glossary: Tempo](https://docs.learnbittensor.org/resources/glossary#tempo),
[Commit Reveal](https://docs.learnbittensor.org/concepts/commit-reveal)).

Those timing concepts do not replace the matrix. They explain when related validator-weight signals
are processed or revealed, while the weight matrix names the structured collection itself.

## Development Stage Context

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. For weight matrix
on a subnet such as netuid 1, that sequence changes how readers should interpret grouped
validator-vector collections, mechanism-scoped matrix examples, and the tempo window that assembles
them.

In localnet, weight-matrix examples can be tested in an isolated environment. Local validator
vectors reflect local chain configuration rather than production subnet consensus input.

On testnet, a weight matrix can be observed in a shared, non-production network. Testnet matrix
readings on a selected netuid and incentive mechanism are separate from mainnet matrix state
([Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix)).

On mainnet, a weight matrix describes live grouped validator-weight input for Yuma Consensus on the
production Bittensor network.

The [Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet. A weight-matrix example from one environment should not be
read as representing production consensus input on another network.

## Yuma Resolves the Matrix Into Emission Shares

[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus) resolves the matrix of
validator rankings into two emissions vectors, one for miners and one for validators. The
[Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix) names
the grouped validator inputs; those inputs feed the on-chain step that allocates subnet
[emissions](https://docs.learnbittensor.org/resources/glossary#emission).

That keeps input and payout vocabulary separate. The matrix is structured consensus input; miner and
validator emission shares are among the outputs Yuma produces from that input.

On the miner branch, filtered matrix columns are aggregated into miner-side standing and then into
credited [incentives](https://docs.learnbittensor.org/resources/glossary#incentives) for the epoch.
On the validator branch, smoothed bonds built from matrix history are paired with those miner
outcomes to credit validator-side
[dividends](https://docs.learnbittensor.org/resources/glossary#emission)
([Yuma Consensus: Miner emissions](https://docs.learnbittensor.org/learn/yuma-consensus#miner-emissions),
[Yuma Consensus: Validator emissions](https://docs.learnbittensor.org/learn/yuma-consensus#validator-emissions)).

Readers should keep those branches separate from the matrix label itself. The matrix names validator
input at the start of the pass; incentive and dividend vocabulary names credited role outcomes after
Yuma finishes processing that input
([Emission: Distribution](https://docs.learnbittensor.org/learn/emissions#distribution)).

## Kappa Clips Matrix Values Before Rank

Before rank and trust are computed, Yuma Consensus compares matrix values against a stake-weighted
[consensus score](https://docs.learnbittensor.org/resources/glossary#consensus-score) benchmark. The
hyperparameter kappa sets how much validator stake must support a weight level before that level
becomes the clipping ceiling for a miner
([Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

When a submitted weight exceeds the clipped benchmark, neither the miner nor the submitting
validator receives emissions for the excess portion. The matrix therefore supplies raw input;
clipping turns that input into the post-filter signal that later drives rank and incentive
allocation.

## Bond Weights Adjust From Clipped Matrix Values

[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus) documentation describes bond
weights as a blend of a validator's submitted weight and the consensus benchmark when a submission
exceeds that benchmark. Those adjusted values update validator-miner
[bonds](https://docs.learnbittensor.org/resources/glossary#validator-miner-bonds) that later factor
into validator dividend allocation.

That step sits between raw matrix input and validator-side payout. The matrix gathers submitted
weights; clipping and bond adjustment translate those inputs into the bond terms used in validator
emissions.

## Distinction from Weight Vector

A weight vector is one validator's submitted scores for miners on a subnet. The weight matrix is the
subnet-level collection that stacks those vectors into the structured input Yuma Consensus processes
([Glossary: Weight Vector](https://docs.learnbittensor.org/resources/glossary#weight-vector),
[Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix)).

- **Weight vector** — one validator's row of miner scores.
- **Weight matrix** — the assembled collection of validator rows for one pass.

## Distinction from Weight Setting

A weight matrix and weight setting describe consensus input as collection and source action. Weight
setting is the per-validator `set_weights` action that submits one validator's weight vector, while
the weight matrix is the subnet-level collection that stacks those submitted vectors into the
structured input Yuma Consensus processes
([Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix),
[Glossary: Weight Vector](https://docs.learnbittensor.org/resources/glossary#weight-vector),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Weight setting** — the action each validator uses to submit its weight vector.
- **Weight matrix** — the subnet-level stack of those vectors used as consensus input.

## Distinction from Consensus Score

A weight matrix stacks validator vectors into subnet-wide consensus input. Consensus score is the
stake-weighted agreement benchmark Yuma Consensus derives from that grouped input when clipping
outlier weights on the selected subnet
([Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix),
[Glossary: Consensus Score](https://docs.learnbittensor.org/resources/glossary#consensus-score),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Weight matrix** — assembled validator input entering consensus.
- **Consensus score** — stake-weighted clipping benchmark derived from that input.

## Distinction from Rank

A weight matrix collects validator weight vectors as structured input for Yuma Consensus. Rank is
the miner-side standing read after that grouped input is processed on the selected subnet
([Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix),
[Glossary: Rank](https://docs.learnbittensor.org/resources/glossary#rank),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Weight matrix** — assembled validator input entering consensus.
- **Rank** — miner-side standing after that input is processed.

## Distinction from Trust

A weight matrix stacks validator weight vectors into the grouped input Yuma Consensus processes.
Trust and validator trust are both post-matrix outcomes, but they answer different sides of the same
clipping pass. Trust names how much miner-side support survived clipping on the selected subnet,
while validator trust names how closely each validator's submitted weights aligned with the
resulting consensus benchmark
([Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix),
[Glossary: Trust](https://docs.learnbittensor.org/resources/glossary#trust),
[Glossary: Validator Trust](https://docs.learnbittensor.org/resources/glossary#validator-trust),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Weight matrix** — all validators' weight vectors stacked as consensus input.
- **Trust** — miner-side support preservation after clipping.
- **Validator trust** — per-validator alignment with consensus after clipping.

## Distinction from Yuma Consensus

A weight matrix is the subnet-level collection of validator weight vectors available at one
consensus step. Yuma Consensus is the process that turns that matrix into miner incentives and
validator dividends through filtering, bonding, and emission allocation
([Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Weight matrix** — combined validator weight vectors at one consensus step.
- **Yuma Consensus** — aggregation that turns those vectors into emission shares.

## Reader Boundary

Weight matrix names consensus input terminology. It describes the organized validator-vector
collection before Yuma Consensus filtering and aggregation
([Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

The central point is that the matrix organizes validator weight vectors for consensus. Later results
depend on how Yuma Consensus filters and aggregates that organized input.

Readers should not treat the matrix as a profitability estimate, a miner ranking, or proof that any
one validator's raw scores will survive clipping unchanged. It is input vocabulary for one pass on a
selected subnet and mechanism, and live outcomes still depend on stake weight, eligibility rules,
and the clipping and bonding steps that follow
([Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism),
[Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping)).
