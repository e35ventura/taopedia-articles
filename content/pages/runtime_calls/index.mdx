# Runtime Calls

Runtime calls are runtime API methods exposed by Bittensor's Subtensor runtime. The generated
Subtensor reference presents them through paths shaped like `api.call.<RuntimeApi>.<method_name>`
([Runtime Calls](https://docs.learnbittensor.org/subtensor-api/runtime)).

The term belongs to Subtensor reference vocabulary. It names a runtime API surface, not a submitted
transaction, emitted event, stored value, or general node RPC method.

## Reference Surface

The runtime-call listing groups methods by runtime API family. Each entry keeps the API family,
method name, return type, interface label, and short summary together
([Runtime Calls](https://docs.learnbittensor.org/subtensor-api/runtime)).

That makes runtime calls useful as a lookup surface. A reader can identify which runtime API family
owns a method before comparing it with nearby Subtensor references.

The path shape matters because it keeps the method out of ordinary transaction vocabulary. A runtime
call can expose runtime information without being the same thing as an extrinsic submitted for block
inclusion.

## Runtime API Families

Runtime calls are organized by API family rather than by user workflow. The generated listing
includes families such as `AccountNonceApi`, `NeuronInfoRuntimeApi`, `StakeInfoRuntimeApi`,
`SubnetInfoRuntimeApi`, and `TransactionPaymentApi`
([Runtime Calls](https://docs.learnbittensor.org/subtensor-api/runtime)).

Those names locate the call in runtime metadata. They do not, by themselves, explain every concept
behind the returned value.

For reader-facing prose, the family name is the first scope cue. A stake-related runtime call, a
subnet-information call, and a transaction-payment call can all be runtime calls while pointing to
different parts of the Subtensor system.

## Runtime Calls and Extrinsics

Runtime calls and extrinsics are separate Subtensor reference surfaces. Runtime calls are exposed as
`api.call.*` methods, while extrinsics are runtime actions exposed through `api.tx.*` paths and can
be submitted to the chain ([Runtime Calls](https://docs.learnbittensor.org/subtensor-api/runtime),
[Subtensor extrinsics](https://docs.learnbittensor.org/subtensor-api/extrinsics)).

That distinction keeps read-oriented runtime API language separate from action submission language.
An extrinsic name identifies an action surface, while a runtime call name identifies a runtime API
method surface.

The two surfaces can still appear near the same concept. A runtime call can help describe runtime
information around an area that also has extrinsics, storage entries, events, or errors.

## Runtime Calls, Storage, and Events

Storage entries, events, and runtime calls answer different reference questions. Storage entries
name readable state surfaces, events name emitted runtime records, and runtime calls name exposed
runtime API methods ([Subtensor Storage](https://docs.learnbittensor.org/subtensor-api/storage),
[Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events),
[Runtime Calls](https://docs.learnbittensor.org/subtensor-api/runtime)).

The same runtime area can have more than one surface. A reader might see a storage entry for state,
an event for a recorded runtime occurrence, and a runtime call for a method exposed by runtime API
metadata.

Keeping the surfaces separate prevents one label from doing too much. Runtime-call vocabulary
identifies the API method surface; storage, events, extrinsics, and errors provide neighboring
chain-reference context.

## RPC Contrast

RPC methods are another generated reference surface, but they are exposed through `api.rpc.*`
namespaces rather than `api.call.*` runtime API paths
([RPC](https://docs.learnbittensor.org/subtensor-api/rpc),
[Runtime Calls](https://docs.learnbittensor.org/subtensor-api/runtime)).

The distinction is useful when a page mentions node-facing methods and runtime API methods together.
RPC vocabulary names JSON-RPC methods available on the Subtensor node, while runtime-call vocabulary
names runtime API methods exposed by the Subtensor runtime.

## Network Context

The runtime-call reference is generated from connected Subtensor runtime metadata. Bittensor also
separates mainnet, testnet, and localnet as network contexts
([Runtime Calls](https://docs.learnbittensor.org/subtensor-api/runtime),
[Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

That means concrete examples need their network context attached. The method vocabulary can be
stable as a reference surface, while the returned value belongs to the network and chain context
where it was observed.
