# Bittensor Platform Components

Bittensor platform components are the major pieces readers need to keep separate
([Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction)).

Those pieces include subnets, blockchain state, tokens, roles, tools, and network environments
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)). Each piece
answers a different question. The page is a map, not a replacement for the detailed mechanism
articles.

## Development Stage Context

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. For Bittensor
platform components, that sequence changes how readers should interpret subnets, roles, tools, and
chain-state examples.

In localnet, platform pieces can be developed and tested in an isolated environment. Localnet
subnet, node, and token examples do not represent production system behavior.

On testnet, subnets, validators, miners, and tooling can be exercised in a shared non-production
network. Testnet component interactions are separate from mainnet state.

On mainnet, platform components describe the live production system readers observe on the public
network. Which subnet, role, tool, or chain surface applies depends on the production context being
discussed ([Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction)).

The [Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet. A platform-component example from one environment should
not be read as representing production system behavior in another environment.

## Distinction from Subtensor

Bittensor platform components and Subtensor name an overview map and one chain layer within it.
Platform components keeps subnets, chain state, tokens, roles, tools, and network environments in
one orientation frame, while Subtensor names Bittensor's layer 1 blockchain and system of record for
transactions and rankings
([Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction),
[Glossary: Subtensor](https://docs.learnbittensor.org/resources/glossary#subtensor),
[Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

- **Bittensor platform components** — the high-level map across subnets, chain, tokens, roles,
- **Subtensor** — the layer 1 chain that records state and runs consensus.

## Distinction from Subnets

Platform components and subnets sit at different levels of scope. This article orients readers
across the major Bittensor pieces, while subnets name the competitive markets where miners and
validators interact under a subnet protocol
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets),
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction)).

- **Bittensor platform components** — orientation across chain, tooling, subnet, and role layers.
- **Subnets** — specialized work markets with miners, validators, and incentive mechanisms.

## Distinction from Yuma Consensus

Bittensor platform components is a high-level map across subnets, chain state, tokens, roles, tools,
and network environments. Yuma Consensus is the mechanism that aggregates validator weights into
emission shares each tempo

## Distinction from Bittensor Tools

Bittensor platform components is the high-level map across subnets, chain, tokens, roles, tools, and
networks. Bittensor tools names the interface layer — SDK, terminal, wallet, and user-facing
surfaces ([Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction),
[Bittensor Tools](https://docs.learnbittensor.org/concepts/tools)).

Map vocabulary orients readers across layers; tools vocabulary names the interface surfaces they use
([Bittensor Tools: SDK](https://docs.learnbittensor.org/concepts/tools#bittensor-sdk)).

- **Bittensor platform components** — orientation map across major system pieces.
- **Bittensor tools** — SDK, terminal, wallet, and user-facing interface layer.

## Reader Boundary

Bittensor platform components should not be read as a single application, product tier, or
installable "platform." The phrase names the separate pieces a reader keeps distinct — subnets, the
Subtensor chain, TAO and subnet alpha tokens, role families, tools, and network environments — when
deciding which part of the system a statement is about
([Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction),
[Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

The stable point is that "components" is orientation vocabulary, not a component itself: a claim
about consensus, emissions, staking, or subnet design belongs to that component's focused article
rather than to this map
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).
