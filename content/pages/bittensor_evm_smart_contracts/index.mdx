# Bittensor EVM Smart Contracts

Bittensor EVM smart contracts are Ethereum Virtual Machine-compatible contracts that execute on
Subtensor. The [Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)
material places the EVM runtime inside Bittensor rather than on Ethereum mainnet.

## Runtime Compatibility

The EVM runtime gives Bittensor an Ethereum-compatible contract environment. Compatibility means
Ethereum-style contract patterns and tooling expectations can be represented, while execution still
belongs to Bittensor's chain context
([Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)).

This is the main reader distinction: EVM describes the execution model, not a move to Ethereum
mainnet.

## Subtensor Context

Subtensor remains the base layer for the activity. The
[Subtensor glossary entry](https://docs.learnbittensor.org/resources/glossary#subtensor) names
Subtensor as Bittensor's layer 1 blockchain and system of record, and Bittensor EVM contract
execution sits within that environment.

Readers should therefore keep the two layers separate. Subtensor provides the Bittensor chain
context; EVM compatibility describes the smart-contract runtime available within that context.

## Interface Context

Ethereum JSON-RPC compatibility gives familiar interface expectations for EVM-style interaction.
That interface layer should be read separately from settlement context: using an Ethereum-shaped
interface does not make a contract an Ethereum-mainnet contract
([Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)).

The interface helps readers understand how applications can communicate with the EVM side of
Bittensor. It does not change the fact that the contract is part of the Bittensor environment.

## Address Format Context

Bittensor EVM material distinguishes SS58-style Bittensor addresses from Ethereum-style H160
addresses. The
[H160 address glossary entry](https://docs.learnbittensor.org/resources/glossary#h160-address) keeps
the Ethereum-format address concept separate from Bittensor address context.

For readers, address-format compatibility is a way to represent accounts for EVM interaction. It
should not be read as proof that every Bittensor address behaves like an Ethereum address in every
setting.

## Smart Contracts and Subnets

EVM smart contracts are not the same thing as subnet incentive mechanisms. Subnets define markets
for useful work, while EVM contracts are application-layer programs running in the Bittensor
environment. The
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets) material
gives the miner-validator market frame that remains separate from EVM contract execution.

## Most EVM Contracts Deploy Without Rewriting

[Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials) documentation states
that users can deploy most EVM smart contracts on Subtensor without changing the contract code. That
portability names the deployment step, not a move to Ethereum mainnet: familiar Ethereum-style
contract patterns can be represented on Bittensor while execution and chain history still belong to
[Subtensor](https://docs.learnbittensor.org/resources/glossary#subtensor).

The same overview treats that compatibility as one capability inside a Bittensor-hosted EVM runtime.
Readers can therefore separate contract source portability from settlement location. A contract
written for Ethereum-style tooling may deploy on Subtensor without a rewrite, yet its effects still
record on the Bittensor chain rather than on Ethereum.

## Address Conversion Does Not Create Signing Keys

Bittensor EVM documentation explains that an
[H160 address](https://docs.learnbittensor.org/resources/glossary#h160-address) and an SS58 address
can be converted between representations, but that conversion does not yield the corresponding
private key. A native Bittensor wallet therefore cannot authorize EVM smart-contract activity from a
converted display address alone, and an EVM wallet cannot authorize native Subtensor actions through
the same kind of mapping
([Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials),
[Convert Ethereum H160 Address to Substrate SS58](https://docs.learnbittensor.org/evm-tutorials/convert-h160-to-ss58)).

That signing boundary sits beside address-format compatibility. Two addresses may look related after
conversion, yet control still depends on which key material created the account in its own wallet
model. Address conversion helps readers connect account views; it does not merge the two signing
authorities.

## Metagraph Precompile Queries Stay Read-Only

Bittensor EVM documentation describes a metagraph precompile that lets smart contracts query
[metagraph](https://docs.learnbittensor.org/resources/glossary#metagraph) information such as neuron
stakes, ranks, trust scores, and consensus values. The
[Metagraph Precompile](https://docs.learnbittensor.org/evm-tutorials/metagraph-precompile) page
states that its functions are read-only operations that do not modify chain state
([The Subnet Metagraph](https://docs.learnbittensor.org/subnets/metagraph)).

That read-only boundary matters when a contract example inspects subnet neuron metrics from inside
the EVM layer. The precompile supplies observation vocabulary for current metagraph fields; the
query itself does not count as a state-changing subnet action. Reading metagraph data through a
contract therefore stays separate from submitting native subnet operations that change recorded
state.

## EVM Contracts, H160 Addresses, and Token Bridging Pipeline

Bittensor EVM smart contracts sit inside a wider account-and-asset pipeline on one chain. The useful
order for readers is Subtensor as base layer, EVM contract execution through Ethereum JSON-RPC,
[H160 address](https://docs.learnbittensor.org/resources/glossary#h160-address) account context for
EVM wallets, and [token bridging](https://docs.learnbittensor.org/evm-tutorials/bridge-vtao) that
moves the same TAO between SS58 and H160 account formats so it can interact with those contracts
([Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)).

Contract deployment is the application step in that pipeline. Most Ethereum-style contract source
can deploy on Subtensor without a rewrite, yet settlement and history still belong to Bittensor
rather than Ethereum mainnet
([Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)).

H160 addresses name the EVM-side wallet format, while SS58 addresses name native Bittensor wallet
context. Conversion between representations can help a transfer or account view cross that boundary,
but it does not produce the corresponding private key, so wallet control still follows whichever key
material can sign in the intended environment
([Convert Ethereum H160 Address to Substrate SS58](https://docs.learnbittensor.org/evm-tutorials/convert-h160-to-ss58),
[Glossary: SS58 Encoded](https://docs.learnbittensor.org/resources/glossary#ss58-encoded)).

Token bridging connects TAO across those account contexts on the same Bittensor blockchain. The
[Token Bridging](https://docs.learnbittensor.org/evm-tutorials/bridge-vtao) documentation describes
moving the same TAO between SS58 and H160 formats and representing staked TAO as vTAO inside the EVM
layer. Bridging therefore names how TAO reaches H160 context for contract use, not a transfer to a
separate Ethereum network.

The metagraph precompile adds a read-only observation step for contracts that need current subnet
neuron metrics. It lets an EVM contract inspect fields such as stake, rank, trust, and consensus on
a subnet such as netuid 1 without submitting native state-changing subnet actions
([Metagraph Precompile](https://docs.learnbittensor.org/evm-tutorials/metagraph-precompile)).

For readers, EVM vocabulary names contract execution and wallet context on Bittensor. H160 and
bridging vocabulary names how accounts and TAO connect to that layer. Subnet incentive mechanisms
and Yuma Consensus reward math remain separate native processes even when a contract reads metagraph
data through the precompile
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

## Development Stage Context

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. For Bittensor EVM
smart contracts, that sequence changes how readers should interpret contract deployment, address
conversion, bridging, and metagraph-precompile examples on a subnet such as netuid 1
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

In localnet, EVM contract examples can be tested in an isolated environment. Localnet deployment,
H160 conversion, and token bridging on netuid 1 reflect local chain configuration rather than
production Bittensor EVM state.

On testnet, EVM contract activity can be exercised in a shared non-production network. Testnet
contract history, bridged TAO representation, and metagraph-precompile reads on netuid 1 are
separate from mainnet chain state.

On mainnet, Bittensor EVM smart contracts describe live production contract execution on Subtensor,
where bridged TAO, H160 wallet context, and read-only metagraph queries on subnets such as netuid 1
concern the active network
([Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)).

The [Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet. An EVM example from one environment should not be read as
representing production contract behavior in another environment.

## Reader Boundary

Bittensor EVM smart contracts should be read as EVM-compatible execution on Subtensor, not as
Ethereum mainnet settlement, a subnet scoring model, or proof that address conversion creates
signing keys ([Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

When concrete contract behavior matters, readers should look at the contract, network, address
format, and interface context together rather than relying on the EVM label alone.
