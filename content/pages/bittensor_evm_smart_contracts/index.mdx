# Bittensor EVM Smart Contracts

Bittensor EVM smart contracts are Ethereum Virtual Machine-compatible contracts that execute on
Subtensor. The [Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)
material places the EVM runtime inside Bittensor rather than on Ethereum mainnet.

## Runtime Compatibility

The EVM runtime gives Bittensor an Ethereum-compatible contract environment. Compatibility means
Ethereum-style contract patterns and tooling expectations can be represented, while execution still
belongs to Bittensor's chain context
([Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)).

This is the main reader distinction: EVM describes the execution model, not a move to Ethereum
mainnet.

## Subtensor Context

Subtensor remains the base layer for the activity. The
[Subtensor glossary entry](https://docs.learnbittensor.org/resources/glossary#subtensor) names
Subtensor as Bittensor's layer 1 blockchain and system of record, and Bittensor EVM contract
execution sits within that environment.

Readers should therefore keep the two layers separate. Subtensor provides the Bittensor chain
context; EVM compatibility describes the smart-contract runtime available within that context.

## Interface Context

Ethereum JSON-RPC compatibility gives familiar interface expectations for EVM-style interaction.
That interface layer should be read separately from settlement context: using an Ethereum-shaped
interface does not make a contract an Ethereum-mainnet contract
([Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)).

The interface helps readers understand how applications can communicate with the EVM side of
Bittensor. It does not change the fact that the contract is part of the Bittensor environment.

## Address Format Context

Bittensor EVM material distinguishes SS58-style Bittensor addresses from Ethereum-style H160
addresses. The
[H160 address glossary entry](https://docs.learnbittensor.org/resources/glossary#h160-address) keeps
the Ethereum-format address concept separate from Bittensor address context.

For readers, address-format compatibility is a way to represent accounts for EVM interaction. It
should not be read as proof that every Bittensor address behaves like an Ethereum address in every
setting.

## Smart Contracts and Subnets

EVM smart contracts are not the same thing as subnet incentive mechanisms. Subnets define markets
for useful work, while EVM contracts are application-layer programs running in the Bittensor
environment. The
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets) material
gives the miner-validator market frame that remains separate from EVM contract execution.

## Network Context

Examples involving EVM smart contracts should stay attached to the network environment where they
run. Mainnet, testnet, and localnet are separate Bittensor contexts, and behavior observed in one
environment should not stand in for another network's chain history
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks),
[Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)).

This keeps examples from sounding broader than they are. The EVM concept can be stable while a
particular contract deployment, interface endpoint, or test result belongs to one environment.

## Application Layer on Subtensor

The official [Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials) material
describes the EVM runtime as an application layer on top of the Bittensor blockchain. That placement
keeps contract execution inside Bittensor while marking the EVM as the program layer above Subtensor
settlement.

The same page notes that most EVM smart contracts can be deployed on Subtensor without changing
their code. Deployment compatibility therefore covers familiar Ethereum-style contract patterns,
while chain history and settlement still belong to Bittensor.

References: [Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials),
[Glossary: Smart Contract](https://docs.learnbittensor.org/resources/glossary#smart-contract)

## Two Wallet Signing Paths

Official Bittensor EVM material distinguishes Bittensor wallets from EVM wallets by what each one
can sign. Wallets created through the Bittensor toolchain can sign native Subtensor transactions
through BTCLI and the Bittensor SDK, while EVM wallets created through clients such as MetaMask sign
EVM smart-contract interactions on the same chain
([Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials)).

That split matters when an example mentions staking, subnet registration, or another native action.
The capability may still exist on Bittensor, but the wallet that can authorize it depends on whether
the workflow uses native Subtensor signing or EVM contract signing.

For readers, wallet choice is part of the signing context, not only the address format being
displayed.

References: [Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials),
[Wallets, Coldkeys and Hotkeys](https://docs.learnbittensor.org/keys/wallets)

## Precompiles Reach Native Subtensor Features

Beyond user-deployed contracts, Bittensor EVM includes precompiled smart contracts that expose
native Subtensor features to Solidity code. The
[Bittensor EVM: Examples and Precompiles](https://docs.learnbittensor.org/evm-tutorials/examples)
page lists standard Ethereum precompiles alongside Bittensor-specific ones for staking, subnet
management, neuron operations, and metagraph queries.

Those precompiles sit at fixed addresses in the EVM runtime and let contract code reach Subtensor
state without treating every deployed contract as the subnet incentive mechanism itself.

References:
[Bittensor EVM: Examples and Precompiles](https://docs.learnbittensor.org/evm-tutorials/examples),
[Glossary: Precompile](https://docs.learnbittensor.org/resources/glossary#precompile)

## Practical Limits

The term is best read as EVM-compatible execution on Bittensor. It does not mean Ethereum custody,
Ethereum mainnet settlement, or a subnet scoring model
([Bittensor EVM Smart Contracts](https://docs.learnbittensor.org/evm-tutorials),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

When a concrete contract behavior matters, readers should look at the contract, network, address
format, and interface context together rather than relying on the EVM label alone.
