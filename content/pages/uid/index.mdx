# UID

A UID is the unique identifier assigned to each participant position in a Bittensor subnet. Each
miner or validator registered to a subnet holds a UID that identifies their position within that
subnet's participant set
([Glossary: UID slot](https://docs.learnbittensor.org/resources/glossary#uid-slot),
[Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

UID is identifier vocabulary. It names the number, not the position structure itself. UID slot is
the related term for the participant position that the UID identifies.

## Subnet-Specific Scope

UIDs are subnet-specific. The same UID number can appear in different subnets while referring to
different participants. A UID identifies a position within one subnet's participant set, not a
network-wide identity
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

Netuid identifies the subnet itself, while UID identifies a participant within that subnet
([Glossary: Netuid](https://docs.learnbittensor.org/resources/glossary#netuid)). The two terms
answer different questions about the same subnet context.

## Registration and UIDs

A participant receives a UID by registering to a subnet. Registration assigns a UID to a hotkey,
placing that participant into a UID slot within the subnet's capacity
([Glossary: Register](https://docs.learnbittensor.org/resources/glossary#register)).

That means a UID is earned through registration, not self-assigned. If the subnet is at capacity,
registration replaces the lowest-ranked existing participant through the immunity and deregistration
rules.

## Metagraph Context

The metagraph records each subnet's participant set. UIDs appear in metagraph data as identifiers
for the miners and validators indexed in that subnet's state
([Glossary: Metagraph](https://docs.learnbittensor.org/resources/glossary#metagraph)).

Reading a UID from metagraph data gives a position identifier within the subnet's current
participant set. The position's associated state — stake, rank, trust — is indexed by that UID.

## Reader Boundary

UID is concept vocabulary for subnet participant identification. It should not be read as a network
address, a balance container, or a cross-subnet identity
([Glossary: UID slot](https://docs.learnbittensor.org/resources/glossary#uid-slot)).

UIDs can change through deregistration. A UID that identifies one participant today may identify a
different participant in the same subnet after a registration event
([Understanding Subnets](https://docs.learnbittensor.org/subnets/understanding-subnets)).

## One Hotkey Binds to One UID Within a Subnet

Official [Wallets, Coldkeys and Hotkeys in Bittensor](https://docs.learnbittensor.org/keys/wallets)
documentation explains how operational keys relate to subnet participation. Within one subnet, each
UID must be tied to its own hotkey. The same hotkey cannot occupy two UID positions in the same
participant set at once.

That rule shapes how UID ownership should be read. A UID still names a participant position inside
one subnet, but the hotkey names which operational key currently holds that position
([Glossary: Hotkey](https://docs.learnbittensor.org/resources/glossary#hotkey),
[Glossary: UID Slot](https://docs.learnbittensor.org/resources/glossary#uid-slot)). Two different
UID numbers in the same subnet therefore imply two different hotkeys, not one shared key carrying
both slots.

The same wallet guidance also allows one hotkey to be reused across different subnets. A participant
may hold separate UIDs in separate subnet markets, but each assignment still comes from its own
registration inside that subnet rather than from one hotkey claiming multiple slots in the same
market.

References:
[Wallets, Coldkeys and Hotkeys in Bittensor](https://docs.learnbittensor.org/keys/wallets),
[Glossary: UID Slot](https://docs.learnbittensor.org/resources/glossary#uid-slot)

## Active Status Is Separate From the UID Number

Official [Glossary: Active UID](https://docs.learnbittensor.org/resources/glossary#active-uid)
defines an active UID as a UID slot treated as active within a specific subnet, allowing the
associated hotkey to participate as a subnet miner or subnet validator. Receiving a UID through
registration and being active in subnet state are therefore different readings of the same slot.

Registration vocabulary assigns the identifier. Active UID vocabulary names whether that slot
currently satisfies the subnet participation condition being observed. Subnet metagraph
documentation describes participant snapshots that include activity-related fields for neurons in a
selected subnet ([The Subnet Metagraph](https://docs.learnbittensor.org/subnets/metagraph)).

Subnet hyperparameter documentation also ties activity timing to configurable cutoff settings rather
than to the registration moment alone
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)). UID
language should therefore keep the assigned number and the active flag as separate ideas. A UID can
identify a position while later subnet state shows whether that position still counts as active.

References: [Glossary: Active UID](https://docs.learnbittensor.org/resources/glossary#active-uid),
[The Subnet Metagraph](https://docs.learnbittensor.org/subnets/metagraph)

## Immunity Period Starts at UID Assignment

Official [Understanding Neurons](https://docs.learnbittensor.org/learn/neurons) documentation lists
registration and UID assignment as the first steps in the neuron lifecycle, followed by an immunity
period during which a newly registered neuron is protected from ordinary pruning. The
[Glossary: Immunity Period](https://docs.learnbittensor.org/resources/glossary#immunity-period)
defines that grace window as protection from deregistration due to poor performance while a new
participant establishes itself.

Mining documentation also notes that when a subnet miner registers a hotkey and receives a UID, the
associated immunity period begins at that entry moment
([Mining in Bittensor](https://docs.learnbittensor.org/miners)). That timing is different from the
capacity-replacement case where a full subnet must displace an existing slot holder. A fresh UID
holder is not immediately exposed to every performance-based replacement rule.

Immunity therefore belongs to the interval right after UID assignment. The new slot holder has time
to begin producing and being evaluated before the usual low-performance displacement path applies in
the ordinary way.

References: [Understanding Neurons](https://docs.learnbittensor.org/learn/neurons),
[Glossary: Immunity Period](https://docs.learnbittensor.org/resources/glossary#immunity-period)
