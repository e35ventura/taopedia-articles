# Mempool Visibility

Mempool visibility is the exposure of pending transaction details before block inclusion
([Glossary: Mempool](https://docs.learnbittensor.org/resources/glossary#mempool),
[MEV Shield](https://docs.learnbittensor.org/concepts/mev-shield/)).

The term belongs to pre-inclusion transaction risk. It describes what can be visible while a
transaction is waiting, before the later block record, event record, or storage state gives readers
post-inclusion evidence.

## Pending Window

The mempool glossary entry places pending and unconfirmed transactions before block inclusion
([Glossary: Mempool](https://docs.learnbittensor.org/resources/glossary#mempool)).

Mempool visibility asks what information can be observed during that waiting period. The concept is
about exposure before inclusion. Whether the transaction later appears in a block belongs to block
history and the runtime records produced after inclusion
([Glossary: Block](https://docs.learnbittensor.org/resources/glossary#block),
[Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events)).

That makes timing part of the definition. A pending transaction can be visible at a different moment
than the final block record, so mempool visibility should be read as a before-block concept rather
than a complete transaction-history concept.

## MEV Risk Context

The MEV glossary entry connects maximal extractable value to transaction ordering and information
available before inclusion
([MEV](https://docs.learnbittensor.org/resources/glossary#mev-maximal-extractable-value)).

That makes mempool visibility a safety concept. If sensitive pending details are visible before a
block is produced, another observer may have information that matters for ordering-sensitive
behavior.

The visibility part is one ingredient in the risk. MEV vocabulary focuses on value that can come
from ordering, inclusion, or exclusion choices, while mempool visibility focuses on the information
available before those choices settle into block history
([MEV](https://docs.learnbittensor.org/resources/glossary#mev-maximal-extractable-value),
[Glossary: Block](https://docs.learnbittensor.org/resources/glossary#block)).

For readers, exposure and outcome stay separate. Visible pending information can create a risk
window even when the final block record still needs to be checked through block, event, or storage
references.

## MEV Shield Boundary

MEV Shield documentation describes encrypted mempool protection for sensitive transaction contents
while they are pending ([MEV Shield](https://docs.learnbittensor.org/concepts/mev-shield/)).

That makes MEV Shield a visibility protection. Shielding changes what can be seen during the pending
window; block production and runtime processing still determine the later record
([MEV Shield](https://docs.learnbittensor.org/concepts/mev-shield/),
[Glossary: Block](https://docs.learnbittensor.org/resources/glossary#block)).

The protection scope is therefore specific. MEV Shield belongs beside mempool visibility because it
addresses sensitive pending contents, while events and storage remain the better references for what
the chain recorded afterward.

## Block Inclusion Boundary

A block is the chain data unit that contains transactions and has a block hash
([Glossary: Block](https://docs.learnbittensor.org/resources/glossary#block)).

This boundary matters because pending visibility and final chain history answer different questions.
Mempool visibility concerns the pre-inclusion window; block evidence concerns inclusion and ordering
after the chain records the transaction.

The block boundary also gives readers a clean transition point. Before inclusion, the relevant
question is what pending information can be observed. After inclusion, the relevant question moves
to the block record and any runtime records connected to that transaction
([Glossary: Block](https://docs.learnbittensor.org/resources/glossary#block),
[Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events)).

## Recorded Evidence Context

Pending visibility is not the same thing as recorded chain state. Chain events and storage are
better sources for what happened after inclusion, while mempool visibility concerns what could be
observed beforehand ([Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events),
[Subtensor Storage](https://docs.learnbittensor.org/subtensor-api/storage)).

Events name runtime records emitted during processing, and storage exposes readable state surfaces.
Those references can confirm recorded activity or state context after inclusion, while mempool
visibility remains about the earlier exposure window
([Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events),
[Subtensor Storage](https://docs.learnbittensor.org/subtensor-api/storage)).

The practical reading order is exposure first, then recorded evidence. A pending-window observation
can explain why a risk existed, and later chain references explain what the runtime recorded.

## Network Boundary

Bittensor documentation separates mainnet, testnet, and localnet contexts
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

A mempool visibility example from one environment should not be treated as proof about another
environment. Localnet examples can show controlled behavior, testnet examples can show shared
non-production conditions, and mainnet references need separate support from mainnet-specific
material.

This matters for safety interpretation. A local or testnet example can illustrate the vocabulary of
pending visibility, while a mainnet safety discussion needs sources that match the network context
being discussed.

## Reader Boundary

Mempool visibility should be read as pre-inclusion exposure vocabulary. It identifies what can be
visible while a transaction is pending, before the final block and related runtime records provide
post-inclusion context
([Glossary: Mempool](https://docs.learnbittensor.org/resources/glossary#mempool),
[Glossary: Block](https://docs.learnbittensor.org/resources/glossary#block),
[Subtensor Events](https://docs.learnbittensor.org/subtensor-api/events)).

The neighboring concepts complete the picture. MEV Shield describes a protection around pending
contents, block records describe inclusion, and storage or events describe later runtime evidence
([MEV Shield](https://docs.learnbittensor.org/concepts/mev-shield/),
[Subtensor Storage](https://docs.learnbittensor.org/subtensor-api/storage)).
