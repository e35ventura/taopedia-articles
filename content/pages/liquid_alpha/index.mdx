# Liquid Alpha

Liquid alpha is the name the documentation gives to the consensus-based weights feature that lets a
subnet vary the smoothing factor used when validator bonds are updated, rather than holding that
factor at a single fixed value. The smoothing factor is the alpha (α) term in the exponential moving
average that the protocol applies to each validator-miner bond from one epoch to the next.

References:
[Consensus-based Weights / Liquid Alpha](https://docs.learnbittensor.org/concepts/consensus-based-weights),
[Glossary: Validator-Miner Bonds](https://docs.learnbittensor.org/resources/glossary#validator-miner-bonds)

## Bonds and the EMA

A bond represents the investment a validator has made in evaluating a particular miner, and the
protocol smooths each bond across epochs with an exponential moving average so that a single epoch
does not dominate the value. In that moving average, the alpha term controls how much weight the
current epoch carries relative to the accumulated history: a larger alpha reacts faster to the
latest epoch, while a smaller alpha keeps more of the prior value. Liquid alpha is concerned with
how that single alpha term is chosen.

References:
[Glossary: Validator-Miner Bonds](https://docs.learnbittensor.org/resources/glossary#validator-miner-bonds),
[Glossary: Exponential Moving Average](https://docs.learnbittensor.org/resources/glossary#exponential-moving-average-ema)

## What Liquid Alpha Changes

When liquid alpha is disabled, the bonds moving average uses a fixed alpha for the subnet. When it
is enabled, the documentation describes the alpha as varying between a lower and an upper bound that
the subnet configures, so the smoothing responds to conditions rather than staying constant. The
stated motivation is that a validator's dividends become better correlated with the performance of
the miner it is setting weights on, which helps validators identify well-performing miners and bond
to them more quickly.

Reference:
[Consensus-based Weights / Liquid Alpha](https://docs.learnbittensor.org/concepts/consensus-based-weights)

## The alpha_low and alpha_high Bounds

The two bounds are set by an extrinsic that the current Subtensor runtime restricts to the subnet
owner or root, and only when liquid alpha is already enabled for that subnet. In the runtime,
alpha_low and alpha_high are stored as unsigned 16-bit integers, where the full integer range maps
onto the interval between 0 and 1. The implementation requires both alpha_low and alpha_high to be
at least one fortieth of the maximum 16-bit value, which is 1638 and corresponds to roughly 0.025 of
full scale, and it requires alpha_low to be less than or equal to alpha_high. Because the check uses
"less than or equal to," the two bounds are allowed to be equal.

References:
[Subtensor: do_set_alpha_values in run_epoch.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/epoch/run_epoch.rs),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)

## A Per-Subnet Setting

Liquid alpha is configured per subnet, identified by its netuid. The enable flag and the two bounds
are subnet-scoped, so one subnet can turn the feature on with its own bounds while another leaves it
off, in the same way other consensus-related hyperparameters apply to a single subnet at a time. The
runtime enforces this by requiring the feature to be enabled for the specific subnet before its
bounds can be set.

References:
[Subtensor: do_set_alpha_values in run_epoch.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/epoch/run_epoch.rs),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)

## Reader Boundary

This page defines the concept at a high level. It does not report whether liquid alpha is currently
enabled on any particular subnet, nor the current alpha_low and alpha_high values in force, because
those are live hyperparameter state that the subnet owner can change and that should be read for the
relevant subnet with the Bittensor CLI when current data is needed. The numeric rule described here,
the one-fortieth minimum on each bound and the requirement that alpha_low not exceed alpha_high, is
a constraint enforced by the runtime rather than a live reading.

Reference:
[Subtensor: do_set_alpha_values in run_epoch.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/epoch/run_epoch.rs)
