# Kappa

Kappa is a per-subnet hyperparameter that sets the consensus majority ratio Yuma Consensus uses when
deriving the stake-weighted clipping threshold for miner weights
([Subnet Hyperparameters: Kappa](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#kappa),
[Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping)).

## What It Controls

Kappa sets how much of a subnet's validator stake must support a weight level before that level
becomes the clipping ceiling during Yuma Consensus. With the default kappa near 0.5, at least half
of stake-weighted validator support must agree that a miner deserves weight above a given level
before more generous weights are left unclipped
([Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping),
[Subnet Hyperparameters: Kappa](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#kappa)).

## Distinction from Min Allowed Weights

Kappa and min allowed weights operate at different stages of the weight path. Min allowed weights is
an owner-settable floor on how many miner targets a validator must include in a structurally valid
submission, while kappa is a root-level stake fraction that sets the consensus clipping ceiling
during Yuma settlement
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Subnet Hyperparameters: Kappa](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#kappa)).

A validator can meet the count minimum and still see individual weight values clipped when they
depart from the stake-weighted agreement benchmark kappa helps define. Min allowed weights therefore
gates submission breadth before aggregation begins; kappa shapes how aggressively weights are
trimmed once eligible submissions enter Yuma Consensus
([Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping),
[Glossary: Weight Vector](https://docs.learnbittensor.org/resources/glossary#weight-vector)).

Readers should treat min allowed weights as a structural validity rule on one netuid and kappa as a
clipping parameter inside settlement, not as interchangeable submission gates
([Understanding Incentive Mechanisms](https://docs.learnbittensor.org/learn/anatomy-of-incentive-mechanism)).

- **Min allowed weights** — floor on how many targets a valid submission must include.
- **Kappa** — stake-weighted majority ratio used when deriving the consensus clipping ceiling.

## How Kappa Derives the Benchmark

Documentation describes kappa as the stake fraction Yuma uses when deriving each miner's clipping
benchmark from validator-submitted weights. For each miner column, that process finds the maximum
weight level still backed by at least the configured fraction of stake-weighted validator support
([Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping),
[Subnet Hyperparameters: Kappa](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#kappa)).

The resulting per-miner value is what
[consensus score](https://docs.learnbittensor.org/resources/glossary#consensus-score) vocabulary
names as the benchmark individual weights are capped to during clipping. Kappa supplies the stake
fraction input; consensus score names the benchmark output for each miner column
([Glossary: Consensus Score](https://docs.learnbittensor.org/resources/glossary#consensus-score),
[Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping)).

The stored `u16` is scaled to that fraction by dividing by the type maximum, so the raw
hyperparameter and the stake fraction used in the derivation are the same value expressed at
different scales
([Subnet Hyperparameters: Kappa](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#kappa)).

## Default and Representation

The documentation lists kappa as a `u16` value with a default of 32767, which is approximately 0.5
once normalized against the maximum of that type. That places the default near the halfway point of
stake-weighted agreement. The value actually in force is per-subnet chain state and can differ from
the documented default
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

The constants reference exposes the startup value as `api.consts.subtensorModule.initialKappa`,
listed as `32767`, the raw form of the approximately 0.5 default above. That constant names the
launch value, while the live `Kappa` storage value is the root-settable value a subnet uses after
launch
([Subtensor Constants: initialKappa](https://docs.learnbittensor.org/subtensor-api/constants#initialkappa-u16),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

Documentation also marks kappa as a root-level parameter rather than one subnet owners set directly.
That means governance and updates happen at the root level even though each netuid stores its own
hyperparameter row
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

## Documented Setter

Kappa is changed through the `sudo_set_kappa` extrinsic, exposed in tooling as
`btcli sudo set --param kappa`, and the reference marks the permission required to set it as root
rather than subnet owner
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

The root permission sets kappa apart from owner-settable hyperparameters such as
`min_allowed_weights` or the liquid-alpha bounds. A subnet owner cannot change kappa for their own
subnet with an ordinary `btcli sudo set` call; the update has to be authorized at the root level
even though each netuid keeps its own stored kappa row
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).

The live kappa in force on a subnet is per-netuid chain state, so any real-time claim is tied to a
specific netuid. For the documented example netuid 1 on Finney mainnet, the value can be read from
that subnet's hyperparameter table with `btcli subnet hyperparameters --netuid 1 --network finney`,
which keeps the kappa claim reproducible against a parseable netuid
([Subnet Hyperparameters: View hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#view-hyperparameters)).

## Configured Per Subnet

Each netuid carries its own kappa value in subnet hyperparameter state. The ratio on netuid 1
applies only when Yuma Consensus runs on that subnet and can differ from the documented default and
from kappa on another netuid
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Subnet Hyperparameters: Kappa](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#kappa)).

Examples that name netuid 1 illustrate one subnet's hyperparameter table. They should not be read as
proof that every subnet shares the same live kappa value
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

## Distinction from Clipping

Kappa is the stake fraction used to derive the consensus clipping ceiling. Clipping is the Yuma step
that trims individual validator weights above the stake-weighted agreement benchmark
([Subnet Hyperparameters: Kappa](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#kappa),
[Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping)).

Kappa sets how much stake-weighted validator support must back a weight level before clipping leaves
higher weights in place. Clipping then trims individual ratings that still exceed that benchmark.

- **Kappa** — stake fraction that sets the consensus clipping ceiling input.
- **Clipping** — trimming weights that exceed the stake-weighted agreement benchmark.

## Distinction from Consensus Score

Kappa is the subnet hyperparameter that sets the stake fraction used when deriving each miner's
clipping benchmark. Consensus score names that resulting per-miner benchmark—the agreement level
individual weights are capped to during clipping—not a separate median computed afterward
([Subnet Hyperparameters: Kappa](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#kappa),
[Glossary: Consensus Score](https://docs.learnbittensor.org/resources/glossary#consensus-score),
[Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping)).

- **Kappa** — stake fraction input to the per-miner clipping benchmark.
- **Consensus score** — resulting per-miner benchmark used during clipping.

## Distinction from Bonds Penalty

Kappa sets the stake fraction used to derive the consensus clipping ceiling. Bonds penalty sets how
costly it is to post weights above that benchmark during bonding
([Subnet Hyperparameters: Kappa](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#kappa),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Kappa** — stake fraction for the consensus clipping ceiling.
- **Bonds penalty** — penalty magnitude on weights above that benchmark.

## Distinction from Validator Permit

Kappa is the root-level stake fraction that sets the consensus clipping ceiling in Yuma Consensus. A
validator permit is the per-subnet permission flag that records whether a UID may submit counting
weights
([Subnet Hyperparameters: Kappa](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#kappa),
[Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus)).

- **Kappa** — stake-weighted majority threshold for consensus clipping.
- **Validator permit** — subnet-level right to submit weights that can enter aggregation.

A low-stake permitted validator has less influence on the stake-weighted clipping threshold kappa
defines, but kappa is not an individual validator stake cutoff—permit decides who may submit
weights, while kappa sets how stake-backed agreement defines the clipping ceiling
([Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit),
[Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping)).

## Distinction from Yuma Consensus

Kappa is the per-subnet hyperparameter that sets the stake-weighted majority ratio Yuma uses when
deriving the consensus clipping threshold. It names one clipping parameter inside settlement, not
the full mechanism that credits emission shares
([Subnet Hyperparameters: Kappa](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#kappa),
[Yuma Consensus: Clipping](https://docs.learnbittensor.org/learn/yuma-consensus#clipping)).

Yuma Consensus is the on-chain mechanism that reads the weight matrix, applies kappa and
consensus-score clipping, runs bonding, and then credits miner incentives and validator dividends at
the epoch boundary ([Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Glossary: Weight Matrix](https://docs.learnbittensor.org/resources/glossary#weight-matrix),
[Emission: Distribution](https://docs.learnbittensor.org/learn/emissions#distribution)).

The validator permit section above covers who may submit counting weights. Kappa vocabulary names
the stake fraction for that clipping threshold; Yuma vocabulary names the full settlement pass
([Glossary: Validator Permit](https://docs.learnbittensor.org/resources/glossary#validator-permit)).

Readers should not read kappa as a payout quote or miner rank label. It configures inclusion inside
Yuma; outcomes still depend on the weight matrix processed on the relevant netuid
([Glossary: Consensus Score](https://docs.learnbittensor.org/resources/glossary#consensus-score)).

- **Kappa** — consensus majority ratio hyperparameter for the clipping threshold.
- **Yuma Consensus** — on-chain mechanism that uses validator weights to determine emission shares
  ([Yuma Consensus: Validator emissions](https://docs.learnbittensor.org/learn/yuma-consensus#validator-emissions)).

## Distinction from Epoch

Kappa and an epoch operate at different layers of consensus. Kappa is the majority-threshold
hyperparameter Yuma Consensus uses to decide the consensus weight at each UID, while an epoch is the
recurring block interval over which weights are gathered and that consensus computation runs
([Subnet Hyperparameters: Kappa](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#kappa),
[Yuma Consensus](https://docs.learnbittensor.org/learn/yuma-consensus),
[Glossary: Epoch](https://docs.learnbittensor.org/resources/glossary#epoch)).

Subnet hyperparameters documentation also lists `tempo` as the per-netuid block interval between
weight-setting windows. Kappa names the stake-majority ratio read when clipping runs inside those
windows—not the interval length that tempo or epoch hyperparameters define
([Subnet Hyperparameters: Tempo](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#tempo),
[Subnet Hyperparameters: Kappa](https://docs.learnbittensor.org/subnets/subnet-hyperparameters#kappa)).

- **Kappa** — the majority-threshold hyperparameter used within consensus.
- **Epoch** — the recurring interval over which consensus runs.

## Reader Boundary

This page defines the concept at a high level. It does not report the kappa value set on any
particular subnet or the current consensus outcome of an epoch. Those are live chain state and
should be checked for the relevant netuid. The 32767 figure, about 0.5 normalized, is the documented
default, and the parameter is governed at the root level
([Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters)).
