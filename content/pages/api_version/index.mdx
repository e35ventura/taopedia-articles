# Api Version

Api version is a contracts pallet runtime constant, listed in the chain's constants metadata as
apiVersion, with the value 4 and the summary "The version of the HostFn APIs that are available in
the runtime"
([Subtensor API Constants: apiVersion](https://docs.learnbittensor.org/subtensor-api/constants#apiversion-u16)).
It names which version of the contracts host-function API the runtime currently exposes.

## What It Means

Contracts call into the runtime through a set of host functions, and that interface has a version.
Api version names the version the runtime makes available, currently 4
([Subtensor API Constants: apiVersion](https://docs.learnbittensor.org/subtensor-api/constants#apiversion-u16)).
It is a single version number that applies across the whole chain rather than being configured for
individual contracts, and it identifies the API surface rather than measuring any size or count.

## Distinction from Max Code Len

Api version and max code len are both contracts pallet constants, but they describe different
things. Api version is a version identifier for the host-function interface, while max code len is a
byte-length limit on a contract's code, capped at 131072 bytes
([Subtensor API Constants: maxCodeLen](https://docs.learnbittensor.org/subtensor-api/constants#maxcodelen-u32)).
One names which interface version is available; the other bounds how large a contract may be. They
are unrelated kinds of value.

## Distinction from Max Delegate Dependencies

The same holds against max delegate dependencies, a count limit of 32 locked dependencies per
contract
([Subtensor API Constants: maxDelegateDependencies](https://docs.learnbittensor.org/subtensor-api/constants#maxdelegatedependencies-u32)).
Api version is not a cap at all: it does not limit a quantity but records the version of the API
surface. Reading it tells a reader which host-function version is in effect, not how much of
something a contract may use.

## Why an API Version Is Tracked

Contracts are written against a particular version of the host-function interface, so recording
which version the runtime exposes lets a reader tell which interface generation is in effect. A
version number gives that interface a clear identity as it evolves across runtime upgrades
([Subtensor API Constants: apiVersion](https://docs.learnbittensor.org/subtensor-api/constants#apiversion-u16)).
Because it is a single value for the whole chain, every contract sees the same host-function API
version rather than a per-contract one. The number changing is a signal that the interface
generation the runtime offers has moved on.

## Reader Boundary

Api version is a single network-wide constant applied uniformly, and it reflects the current runtime
configuration; the version advances only through a runtime upgrade. It names the available
host-function API version and does not describe which specific host functions exist or what any of
them does
([Subtensor API Constants: apiVersion](https://docs.learnbittensor.org/subtensor-api/constants#apiversion-u16)).
