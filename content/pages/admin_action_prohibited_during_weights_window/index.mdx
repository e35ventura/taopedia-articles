# Admin Action Prohibited During Weights Window

`AdminActionProhibitedDuringWeightsWindow` is a documented Subtensor standard error raised when an
administrative hyperparameter change is submitted while the admin freeze window is active. The
standard-errors reference describes it as "Admin operation is prohibited during the protected
weights window"
([Subtensor Standard Errors](https://docs.learnbittensor.org/errors/subtensor#adminactionprohibitedduringweightswindow)).

## What It Means

Subnet hyperparameter setters in the admin-utils pallet call `ensure_admin_window_open` before
writing changes. That helper delegates to `is_in_admin_freeze_window`, which returns true in two
cases and causes `AdminActionProhibitedDuringWeightsWindow` when the window is open
([Subtensor source: misc.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/utils/misc.rs)).

First, when a subnet has a pending manual epoch trigger stored in `PendingEpochAt` and the current
block is still before that target block, the freeze is active for the entire countdown. Subtensor
source comments describe this as arming the freeze immediately when the manual trigger is set
([Subtensor source: misc.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/utils/misc.rs)).

Second, when no such pending trigger applies, the freeze covers the final `AdminFreezeWindow` blocks
before the next automatic epoch on the subnet's tempo schedule
([Subtensor source: misc.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/utils/misc.rs),
[Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits)).

The error is a timing gate on authorized admin extrinsics, not a rejection of the submitted
parameter value itself.

## Why It Appears

This error appears when an admin hyperparameter extrinsic is signed while either freeze condition is
true. Calls that land in the final blocks before an automatic epoch boundary, or during the full
countdown after a manual epoch trigger has been armed, can fail even when the caller is otherwise
permitted to change the parameter
([Subtensor source: misc.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/utils/misc.rs)).

When debugging, rule out authorization failures first. `BadOrigin` and `NotSubnetOwner` mean the
signer lacks the required root or subnet-owner permission for the extrinsic. Only after
authorization passes does `ensure_admin_window_open` evaluate the freeze timing
([Subtensor Standard Errors: BadOrigin](https://docs.learnbittensor.org/errors/subtensor#badorigin),
[Subtensor Standard Errors: NotSubnetOwner](https://docs.learnbittensor.org/errors/subtensor#notsubnetowner)).

The practical fix is timing: wait until the pending epoch has fired and `PendingEpochAt` clears, or
until a new tempo cycle begins after the automatic-epoch freeze has lifted
([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits)).

## Distinction from Activity Cutoff Too Low

`AdminActionProhibitedDuringWeightsWindow` and `ActivityCutoffTooLow` can both appear on
hyperparameter setters, but they reject different problems. The weights-window error is a timing
gate tied to epoch scheduling. `ActivityCutoffTooLow` is a value floor on the legacy activity cutoff
setter that runs only after authorization and timing checks have already passed
([Activity Cutoff Too Low](https://docs.learnbittensor.org/errors/subtensor#activitycutofftoolow),
[Subtensor source: admin-utils lib.rs](https://github.com/opentensor/subtensor/blob/main/pallets/admin-utils/src/lib.rs)).

- **AdminActionProhibitedDuringWeightsWindow** — the call arrived while the admin freeze window is
  active.
- **ActivityCutoffTooLow** — the submitted cutoff value is below the configured minimum.

## Distinction from Owner Hyperparameter Rate Limit

`AdminActionProhibitedDuringWeightsWindow` and the owner hyperparameter rate limit both restrict
when subnet hyperparameters can change, but along different axes. The rate limit is a per-parameter
cooldown measured in tempos between repeated changes to the same setting. The admin freeze window is
a short blackout around epoch boundaries that blocks admin changes regardless of which parameter is
involved ([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits)).

- **AdminActionProhibitedDuringWeightsWindow** — when the epoch freeze window is active.
- **Owner hyperparameter rate limit** — how soon the same hyperparameter can be changed again.

## Reader Boundary

This page defines the meaning of the error label and the two conditions checked by
`is_in_admin_freeze_window`. It does not describe the live `AdminFreezeWindow` value on a network,
how manual epoch triggers are set, or every extrinsic that calls the helper; those are documented
separately ([Rate Limits](https://docs.learnbittensor.org/learn/chain-rate-limits),
[Subtensor source: misc.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/utils/misc.rs)).
