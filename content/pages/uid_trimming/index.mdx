# UID Trimming

UID trimming is a Bittensor subnet management concept. It describes reducing the number of neuron
UIDs registered on a subnet and then compressing the remaining UIDs so the subnet keeps consecutive
indexing.

The official [UID Trimming](https://docs.learnbittensor.org/subnets/uid-trimming) documentation
frames the feature as a way for subnet owners to reduce a subnet's registered UID count while
preserving high-performing and immune neurons. For Taopedia readers, the key idea is that trimming
is a controlled reduction of occupied subnet positions, not a general score change or a routine
reward adjustment.

Reference: [UID Trimming](https://docs.learnbittensor.org/subnets/uid-trimming)

## Subnet Capacity Context

Each subnet has a participant set made up of UID slots. A UID slot identifies a miner or validator
position inside one subnet. When a subnet's allowed UID count changes downward, some occupied
positions may need to be removed so the remaining set fits the new size.

UID trimming is the feature that performs that reduction. It belongs to the same broad capacity
context as registration, deregistration, and subnet hyperparameters, but it has its own trigger: a
subnet owner reduces the allowed UID count and the chain determines which UIDs can remain.

References: [Glossary: UID Slot](https://docs.learnbittensor.org/resources/glossary#uid-slot),
[Subnet Hyperparameters](https://docs.learnbittensor.org/subnets/subnet-hyperparameters),
[UID Trimming](https://docs.learnbittensor.org/subnets/uid-trimming)

## Emission-Based Selection

The official UID trimming page describes selection in terms of emission scores. During trimming,
UIDs are ordered by emission performance, and lower-emission UIDs are considered first for removal.

This makes trimming different from an arbitrary manual deletion. The reduction follows a chain rule
based on recorded subnet performance signals and protection rules. A low-emission UID is more
exposed to trimming than a high-emission UID, but eligibility still depends on immunity and owner
protection boundaries.

Reference:
[UID Trimming: Emission-Based Selection](https://docs.learnbittensor.org/subnets/uid-trimming#emission-based-selection)

## Protection Boundaries

The UID trimming documentation identifies protected categories that should not be removed by the
ordinary trimming path. Recently registered UIDs can have temporal immunity, and owner-owned UIDs
can receive owner-related protection. The page also describes higher-emission UIDs as safer than
low-emission UIDs in the selection order.

These protections are important because trimming is not meant to remove every participant below a
new count indiscriminately. It reduces the registered set while respecting rules that preserve
protected participants and keep stronger performers ahead of weaker ones.

References:
[UID Trimming: Protection from Trimming](https://docs.learnbittensor.org/subnets/uid-trimming#protection-from-trimming),
[Glossary: Immunity Period](https://docs.learnbittensor.org/resources/glossary#immunity-period)

## UID Compression

After trimming, the remaining UIDs are compressed so the subnet keeps consecutive numbering. The
official page describes this as maintaining consecutive indexing after some UIDs have been removed.

That compression is easy to misunderstand. It means a surviving participant's numeric UID can move
because the positions are packed together after removal. The identity and role context of the
participant should therefore be read with the current subnet state, not with an assumption that an
old UID number remains permanently attached.

Reference: [UID Trimming](https://docs.learnbittensor.org/subnets/uid-trimming)

## Participant Impact

For a participant whose UID is trimmed, the effect is more than receiving fewer emissions. The
official page says a trimmed UID's neuron data is permanently deleted from the blockchain and that a
participant must register again to participate after being trimmed.

This places UID trimming in the subnet participation lifecycle. It is a removal event for selected
UIDs, followed by a fresh-registration path if the participant wants to re-enter. It is not simply a
temporary inactivity label.

Reference:
[UID Trimming: What Happens When Your UID Gets Trimmed](https://docs.learnbittensor.org/subnets/uid-trimming#what-happens-when-your-uid-gets-trimmed)

## Relationship to Deregistration

UID trimming and deregistration both involve removal from a subnet participant set, but they name
different contexts. Deregistration is the broader term for removing a subnet miner or validator from
a subnet, often discussed when a full subnet accepts a new registration and an eligible
low-performing participant loses a slot.

UID trimming is specifically about reducing the registered UID set to a smaller allowed count and
compressing the remaining UIDs afterward. For readers, deregistration names the removal outcome,
while UID trimming names a particular subnet-management path that can produce removals.

References:
[Glossary: Deregistration](https://docs.learnbittensor.org/resources/glossary#deregistration),
[UID Trimming](https://docs.learnbittensor.org/subnets/uid-trimming)

## Relationship to Immunity Period

An immunity period is a post-registration protection window. The UID trimming documentation uses
that same idea when it says recently registered UIDs can be temporally immune from trimming.

For readers, immunity period supplies a timing boundary. A participant may be new enough that the
ordinary low-emission trimming path should skip it, even if its current emission score would
otherwise place it near the bottom of the removal order.

References:
[Glossary: Immunity Period](https://docs.learnbittensor.org/resources/glossary#immunity-period),
[UID Trimming: Protection from Trimming](https://docs.learnbittensor.org/subnets/uid-trimming#protection-from-trimming)

## Rate-Limit Context

The official UID trimming page links trimming to a chain rate limit, meaning the operation cannot be
repeated without regard for chain pacing. This is consistent with Bittensor's broader use of
block-based rate limits to prevent repeated sensitive actions from happening too frequently.

For readers, the rate-limit point is conceptual: trimming is not a rapid, continuous pruning loop.
It is a paced subnet-management action with chain-enforced timing constraints. Exact block counts
and current operational details should be checked in the official docs when performing the action.

References: [UID Trimming](https://docs.learnbittensor.org/subnets/uid-trimming),
[Rate Limits in Bittensor](https://docs.learnbittensor.org/learn/chain-rate-limits)

## Interpretation Boundary

This article defines UID trimming as a concept. It is not a command guide, owner-operation
checklist, fee quote, source-code walkthrough, or live subnet-state report. It does not say which
UIDs on a current subnet will be trimmed.

The stable reader-facing boundary is that UID trimming reduces a subnet's registered UID set,
protects immune and stronger-performing participants according to the documented rules, removes
selected UIDs, and compresses the remaining UID numbering.
