# Expired Weight Commit

`ExpiredWeightCommit` is a documented Subtensor standard error. The standard-errors reference
describes it as "Attempted to reveal weights that are expired"
([Subtensor Standard Errors](https://docs.learnbittensor.org/errors/subtensor#expiredweightcommit)).

## What It Means

A validator that has opted into the commit-reveal scheme first submits a hash commitment over its
planned weight vector, then later submits the actual weights together with the salt it used to
produce the commitment
([Concepts: Commit-Reveal](https://docs.learnbittensor.org/concepts/commit-reveal)).

`ExpiredWeightCommit` means the runtime recomputed the hash from the reveal's
`(uids, values, salt, version_key)` and found that the only stored commitment on the subnet whose
hash matched is one whose commit epoch has already exceeded the subnet's reveal period. The runtime
therefore rejects the reveal and discards the expired commitment
([Subtensor Standard Errors](https://docs.learnbittensor.org/errors/subtensor#expiredweightcommit),
[Subtensor source: weights.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/subnets/weights.rs)).

## Why It Appears

The reveal path is implemented as `internal_reveal_weights`, which is reached from both
`do_reveal_weights` and `do_batch_reveal_weights`. After verifying the caller and that commit-reveal
is enabled for the subnet, it pulls the caller's stored commit queue and walks it from the front,
popping any commit whose commit epoch has expired under the subnet's reveal period and recording its
hash in a local `expired_hashes` set
([Subtensor source: weights.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/subnets/weights.rs)).

`is_commit_expired` is the predicate that drives that walk: a commit at `commit_epoch` is expired
when the current epoch exceeds `commit_epoch + reveal_period`
([Subtensor source: weights.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/subnets/weights.rs)).

After pruning, the runtime recomputes the reveal's hash and looks for it in the remaining
non-expired commits. If the hash is in `expired_hashes` but in no remaining commit, the runtime
raises `ExpiredWeightCommit`. The same fallback path appears in `do_batch_reveal_weights`, where
each individual reveal that resolves only to an expired commit raises the same error
([Subtensor source: weights.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/subnets/weights.rs)).

For a reader, the practical meaning is simple: the validator is trying to reveal against a
commitment that was made too long ago for the subnet to honor. The runtime refuses the reveal
instead of letting weights land through a stale commitment
([Subtensor source: weights.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/subnets/weights.rs)).

## Distinction from Invalid Reveal Commit Hash Not Match

`ExpiredWeightCommit` and `InvalidRevealCommitHashNotMatch` both fire from the same final fallback
in `internal_reveal_weights` after the recomputed reveal hash fails to match any remaining
non-expired commit. They distinguish what kind of mismatch occurred: the hash matched a just-pruned
expired commit (`ExpiredWeightCommit`), or it matched no commit at all
(`InvalidRevealCommitHashNotMatch`)
([Subtensor Standard Errors: InvalidRevealCommitHashNotMatch](https://docs.learnbittensor.org/errors/subtensor#invalidrevealcommithashnotmatch),
[Subtensor source: weights.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/subnets/weights.rs)).

- **ExpiredWeightCommit** — the reveal's hash matches a stored commit, but that commit is past the
  subnet's reveal period and has just been pruned.
- **InvalidRevealCommitHashNotMatch** — the reveal's hash matches no stored commit at all on the
  subnet.

## Reader Boundary

This page defines the meaning of the `ExpiredWeightCommit` error label and the `is_commit_expired`
predicate that drives the pruning step inside `internal_reveal_weights`. It does not describe the
broader commit-reveal scheme, the rules that determine when commit-reveal is enabled on a subnet, or
the version-key and rate-limit checks that surround the reveal call; those are separate conditions
with their own articles
([Concepts: Commit-Reveal](https://docs.learnbittensor.org/concepts/commit-reveal),
[Subtensor source: weights.rs](https://github.com/opentensor/subtensor/blob/main/pallets/subtensor/src/subnets/weights.rs)).
