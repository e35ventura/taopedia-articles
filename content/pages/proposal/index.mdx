# Proposal

A proposal is the governance item that the Triumvirate puts forward for Senate review. It is the
object being considered in Bittensor governance, separate from the bodies that create, review, or
execute governance actions
([Glossary: Proposal](https://docs.learnbittensor.org/resources/glossary#proposal),
[Governance Overview](https://docs.learnbittensor.org/governance)).

## Governance Role

Bittensor governance separates proposal creation from proposal review. The Triumvirate originates
proposals, while the Senate approves or rejects them before privileged changes can proceed
([Governance Overview](https://docs.learnbittensor.org/governance),
[Glossary: Triumvirate](https://docs.learnbittensor.org/resources/glossary#triumvirate)).

That makes a proposal the item moving between governance roles. The Triumvirate is the origin body;
the Senate is the review body; the proposal is the plan or action placed in front of that review
process.

A proposal should be separated from the bodies that handle it. The Triumvirate is the body that
originates proposals, and the Senate is the body that reviews them
([Glossary: Triumvirate](https://docs.learnbittensor.org/resources/glossary#triumvirate),
[Senate](https://docs.learnbittensor.org/governance/senate)).

The proposal is the governance item moving through those roles. Treating the proposal as the same
thing as the Triumvirate or Senate would blur the distinction between an item under review and the
governance bodies that act on it.

## Proposal Hash

A proposal hash is the identifier used to reference a proposal during voting
([Glossary: Proposal Hash](https://docs.learnbittensor.org/resources/glossary#proposal-hash)).

The distinction matters because the hash is not the same as the governance item itself. The proposal
is the item under review, while the hash is the reference used to point to that item in governance
records and voting context.

## Review Flow

The governance overview presents proposals as part of a bicameral process involving the Triumvirate
and Senate ([Governance Overview](https://docs.learnbittensor.org/governance)). A proposal can be
created, reviewed by senators, voted on, and then finalized through the governance process if it has
the required support.

For a reference page, the useful boundary is the stage being discussed. A proposed action, an
approved proposal, and an executed change are related states, but they do not mean the same thing.

Proposal language should keep status separate from reference. A proposal can be the same governance
item across creation, review, voting, and finalization, while its status changes as it moves through
the governance process ([Governance Overview](https://docs.learnbittensor.org/governance),
[Senate](https://docs.learnbittensor.org/governance/senate)).

This is why proposal hashes are useful beside proposal vocabulary. The hash can keep references to
the same item aligned, but the surrounding governance context is still needed to say whether the
proposal is under review, approved, rejected, or already applied
([Glossary: Proposal Hash](https://docs.learnbittensor.org/resources/glossary#proposal-hash)).

## Relationship to Subtensor

Subtensor is Bittensor's layer-one blockchain and system of record
([Glossary: Subtensor](https://docs.learnbittensor.org/resources/glossary#subtensor)). Proposals
belong near Subtensor vocabulary because accepted governance actions can affect privileged Subtensor
behavior through the governance process
([Governance Overview](https://docs.learnbittensor.org/governance)).

That relationship does not make every Subtensor change a proposal. Proposal language should be used
when the focus is the governance item submitted for Senate review.

## Network Context

Bittensor documentation separates localnet, testnet, and mainnet environments
([Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks)).

Proposal examples should keep that environment boundary attached. A localnet or testnet example can
illustrate governance mechanics, but it is not evidence of a mainnet governance outcome or
production parameter change.

## Reader Boundary

A proposal is not the entire governance system, a Senate vote, a proposal hash, or an already
executed change. It is the governance item submitted into review
([Glossary: Proposal](https://docs.learnbittensor.org/resources/glossary#proposal),
[Governance Overview](https://docs.learnbittensor.org/governance)).

When the focus is the voting body, Senate is the more precise term. When the focus is the origin
body, Triumvirate is more precise. When the focus is the identifier used during voting, proposal
hash is more precise.

A proposal should not be described as a completed network change unless the governance context says
that the process reached that state. The governance overview distinguishes the item submitted for
review from the later process steps that can follow approval
([Governance Overview](https://docs.learnbittensor.org/governance)).

This boundary keeps proposal wording from sounding stronger than the evidence supports. A proposal
can name a requested privileged action, while approval status and applied network effects require
the relevant governance context rather than the proposal term alone.

## Development Stage Context

The
[Introduction to Bittensor](https://docs.learnbittensor.org/learn/introduction#subnet-development)
describes subnet development as moving from localnet to testnet and then mainnet. For Proposal, this
sequence gives readers a boundary for interpreting proposal examples and governance-state notes.

Localnet examples are isolated and reflect local chain state, so they are useful for controlled
experiments rather than evidence of live Bittensor behavior. Testnet examples add shared
non-production conditions, which can reveal integration behavior without touching mainnet state.

On mainnet, Proposal examples should be read as proposal behavior on the production Bittensor
network.

The [Bittensor Networks](https://docs.learnbittensor.org/concepts/bittensor-networks) reference
separates mainnet, testnet, and localnet, so outcomes from one environment should not be treated as
proof of behavior in another.

## Lifecycle Stage Scope

A proposal is not the same as an executed change. The governance overview distinguishes proposal
creation, Senate review, voting, finalization, and application, while proposal hashes identify
proposal records during that process
([Governance Overview](https://docs.learnbittensor.org/governance),
[Glossary: Proposal hash](https://docs.learnbittensor.org/resources/glossary#proposal-hash)).

A proposal reference should say which lifecycle stage is being discussed. A visible proposal, an
approved proposal, and an applied proposal are different states in the governance flow.
